# 0067. 값 객체가 거부할 때 틀린 필드를 함께 알리고 정규화가 그 필드로 문제 값을 정하기로 결정

## Context

뺀 항목은 격리 기록에 "문제가 된 값"(`ExcludedValue`)과 함께 남는다 ([ADR-0054](0054-exclusion-kind-by-value-only.md)).
값 검증은 값을 담는 객체의 생성자가 `require` 로 한다 ([ADR-0041](0041-validate-in-constructors.md)). 그 거부는 `IllegalArgumentException` 과 사유 문장뿐이라, 받는 쪽은 무엇이 틀렸는지를 문장 말고는 알 수 없었다.

그래서 두 정규화가 서로 다른 우회를 쓰고 있었다.

- **목록 쪽** (`CatalogNormalizer.valueOf`) — 사유 **문장을 문자열로 비교**해 문제 값을 정했다. 문장을 고치거나 검사를 더하면 조용히 `OTHER` 로 떨어진다. 독립 검토가 결함으로 지적했다
- **재고·요금 쪽** (`AvailabilityNormalizer`) — 금액 객체 `Money` 가 금액과 통화를 함께 검사해서, 통화만 먼저 검사하려고 **금액 0짜리 `Money` 를 만들었다 버렸다**. 사용자가 "왜 그렇게 하느냐"고 물었다

## Options

- **(가) 값 객체가 검사를 나눠, 거부할 때 틀린 필드를 담아 던진다** ← 채택 — 객체를 만들어 보고 되면 쓰고 안 되면 예외라는 방식은 그대로다. 받는 쪽은 문장이 아니라 필드로 가른다.
  대신 값 객체마다 필드 목록과 거부 예외가 하나씩 는다
- **(나) 통화를 별도 값 객체(`Currency`)로 나눈다** — 금액·통화 구분 문제는 해결된다. 대신 목록 쪽 문자열 비교는 그대로 남고, 구분을 위해 클래스를 만드는 것이 된다
- **(다) 지금대로 둔다** — 코드가 늘지 않는다. 대신 위 두 우회가 남는다

필드와 예외를 둘 곳
- **(ㄱ) 값 객체 안에 둔다** (`Money.Field`, `Money.Rejected` 처럼) ← 채택 — 패키지 방향([ADR-0059](0059-quarantine-package.md))을 건드리지 않는다. `mapping` 은 다른 패키지를 보지 않아 공용 예외를 둘 자리가 없다
- **(ㄴ) 공용 예외 하나를 한 패키지에 둔다** — 종류가 하나라 간단하다. 대신 `mapping` 이 그 패키지를 보게 되어 방향이 바뀐다

## Decision

- `Money`, `NormalizedHotel`, `NormalizedRoomType` 이 검사를 필드별로 나누고, 거부할 때 `Rejected(field, message)` 를 던진다. `Rejected` 는 `IllegalArgumentException` 을 상속해, 사유 문장만 쓰던 곳(400 응답 등)은 그대로 동작한다
- `CatalogNormalizer` 는 두 객체의 `Rejected` 만 받고 필드를 `when` 으로 문제 값에 옮긴다. `when` 이 필드를 빠짐없이 다뤄야 컴파일되므로, 검사가 늘어 필드가 생기면 여기서 드러난다
- 목록 쪽은 **그 객체의 거부만 받는다.** 다른 예외는 우리 코드의 결함이라 항목 사유로 삼키지 않는다. 전에는 모든 `IllegalArgumentException` 을 항목 사유로 받았다
- `AvailabilityNormalizer` 는 금액 0짜리 `Money` 를 만들지 않는다. 요금을 만드는 단계에서 `Money.Rejected` 의 필드가 통화면 `CURRENCY`, 금액이면 `RATE` 로 남긴다. 통화 값이 아예 없는 경우는 전처럼 `CURRENCY` 다

## Consequences

**얻는 것**
- 사유 문장을 고쳐도 격리 기록의 문제 값이 바뀌지 않는다
- 검사를 더하면 컴파일러가 문제 값을 정하라고 알린다
- 통화만 검사하려고 쓰지 않을 객체를 만들지 않는다

**잃는 것**
- 값 객체 셋에 필드 목록과 거부 예외가 하나씩 는다. 검사가 `require` 한 줄에서 `if … throw` 로 길어진다
- `AvailableRoomType` 같은 다른 값 객체는 여전히 `require` 다. 거부 원인이 하나뿐이라 정규화 단계가 문제 값을 정해도 모자라지 않아 바꾸지 않았다. 원인이 둘 이상이 되면 같은 방식으로 바꾼다

## Discussion

- **AI 주장과 근거** — AI 는 처음에 통화를 별도 값 객체로 나누자고 권했다(나)
- **사용자 판단** — 사용자가 "검사를 여러 개 두고 금액 검사, 통화 검사가 각각 다른 예외나 코드를 반환하면 되지 않느냐, 왜 새 클래스까지 만들어야 하느냐"고 물었다.
  AI 가 클래스는 필요 없고, 코드를 담는 방식이면 목록 쪽 문자열 비교 결함까지 같은 방식으로 고쳐진다고 답했다. (가)로 진행했다

## Verification

금액 객체가 틀린 필드를 알려 주는지
  → `MoneyTest.거부할 때 금액과 통화 중 무엇이 틀렸는지 알려 준다`

재고·요금 쪽이 통화 형식 오류를 통화로, 음수 금액을 요금으로 기록하는지
  → `AvailabilityNormalizerTest.통화 형식이 틀리면 요금이 아니라 통화 문제로 기록한다`
  → `AvailabilityNormalizerTest.금액이 음수면 요금 문제로 기록한다`

목록 쪽이 필드마다 문제 값을 정하고 `OTHER` 로 떨어지지 않는지
  → `CatalogNormalizerTest.값 객체가 거부한 필드마다 격리 기록의 문제 값이 정해진다`
