# 0044. 판매 조건을 요금이 가지되 조건 묶음을 별도 값 객체로 두기로 결정

## Context

[ADR-0042](0042-rate-as-tax-included-total.md) 가 요금을 세금 포함 총액 하나로 정하면서, 요금에 붙는 판매 조건을 어디에 둘지를 넘겼다.

확인한 사실

| 사실 | 어디서 |
|---|---|
| 실제로 오는 판매 조건은 **조식 포함 여부 하나뿐**이다 | 두 공급사의 재고·요금 응답 |
| 그 값은 **숙소 목록 API 에는 없고 재고·요금 응답에만** 있다. 스펙이 요금에 딸린 정보라고 적고 있다 | 공급사 스펙 |
| **같은 객실이라도 공급사마다 다를 수 있다.** 실제로 같은 이름의 숙소를 A 는 조식 없이, B 는 조식 포함으로 준다 | Mock 이 흉내 내는 응답 |
| **취소·환불 필드는 공급사가 주지 않는다** | 공급사 스펙에 없음 |
| 업계에서는 한 객실 타입에 조건이 다른 요금이 여러 개 붙고, 요금마다 취소 조건이 따라붙는다 | [요금 표시 조사](../research/rate-display.md) |

마지막 줄은 업계 관행이지 우리 입력이 아니다. Feature Spec 의 Q4 서술에 "무료 취소"가 들어가 있었는데,
조사에서 본 것을 요구사항처럼 옮긴 것이라 이 결정과 함께 바로잡는다.

## Options

- **(가) 요금 값 객체 안에 필드로 둔다** — 타입이 늘지 않는다. 대신 조건이 늘 때마다 요금 값 객체를 연다
- **(나) 조건 묶음을 별도 값 객체로 두고 요금이 그것을 가진다** ← 채택 — 조건이 늘어도 금액 타입과 요금 타입은 바뀌지 않는다.
  대신 지금 조건이 하나뿐이라 필드 하나짜리 타입이 생긴다
- **(다) 표준 모델에 두지 않고 검색 응답에만 싣는다** — 응답을 만드는 쪽이 공급사 응답을 다시 들여다봐야 한다. 어댑터가 흡수한 것을 다시 꺼내는 셈이라 [ADR-0031](0031-supplier-adapter-boundaries.md) 과 어긋난다

## Decision

- **판매 조건은 별도 값 객체로 묶는다.** 지금 담는 것은 조식 포함 여부 하나다
- **요금은 금액과 판매 조건을 가진다.** 금액은 액수와 통화를 묶은 값이다(ADR-0042)
- **층은 셋까지.** 금액 · 조건 묶음 · 그 둘을 가진 요금이다. 요금과 조건을 다시 묶는 넷째 층은 두지 않는다
- **한 객실 타입에 요금이 여러 개 붙는 확장은 목록으로 연다.** 상위 객체를 두어 여는 것이 아니다

**이유**

- 스펙이 조식 포함 여부를 요금에 딸린 정보로 말하고, 같은 객실이라도 공급사마다 다르다. 객실 타입이 아니라 요금 단위에 붙는 것이 맞다
- 조건이 늘면 그 묶음 안에서 흡수된다. 금액 타입과 요금 타입을 열지 않는다
- 요금이 이미 금액과 조건을 묶는 자리다. 위에 하나를 더 두면 층만 늘고 확장이 쉬워지지는 않는다.
  실제로 올 법한 확장(요금 여러 개)은 컬렉션이 받는다

## Consequences

**얻는 것**
- 조건이 늘어날 때 고칠 타입이 하나다
- 금액 타입이 판매 조건을 모른다. 금액만 다루는 곳에서 조건이 따라오지 않는다
- 같은 객실 타입을 공급사마다 다른 조건으로 파는 상황이 모델에 그대로 담긴다

**잃는 것**
- **지금 조건이 하나라 필드 하나짜리 타입이 생긴다.** 조건이 끝내 늘지 않으면 껍데기로 남는다.
  과제 범위에서는 늘어날 조건이 스펙에 없다
- 이름이 겹쳐 읽힐 수 있다. 요금 안에 금액이 있어 "요금의 금액의 액수" 처럼 세 번 타고 들어간다

**넘기는 것**
- 한 객실 타입에 요금 여러 개를 실제로 다룰지. 지금 두 공급사는 객실 타입마다 요금을 하나씩만 준다
- 요금 타입의 이름을 판매 단위임이 더 드러나게 바꿀지. 위의 "이름이 겹쳐 읽힌다" 가 걸리면 그때 본다

## Discussion

- **AI 주장과 근거** — (가)를 권했다. 조건이 하나뿐이라 필드 하나를 감싸는 타입을 미리 만드는 것이 지금 규모에 과하다고 보았다
- **반박** — 사용자가 확장성을 챙기고 싶다며 (나)를 골랐고, 요금 안에 조건이 들어가는 것이 어색하면 둘을 묶는 상위 객체를 두자고 물었다
- **검증 결과** — 상위 객체는 두지 않기로 했다. 요금을 "금액" 으로 읽으면 어색하지만 "팔리는 단위" 로 읽으면 요금이 이미 묶는 자리다.
  확장 지점을 나눠 보면 조건 증가는 조건 묶음이, 요금 여러 개는 컬렉션이 받는다. 상위 객체가 받는 것은 없었다
- **그래서 어떻게 바뀌었나** — (나)로 가되 층을 셋으로 정했다. 이름의 뜻이 흔들리지 않게 [용어](../glossary.md) 를 함께 만들었다

## Verification

조식 포함 여부가 요금에 붙어 응답에 나가는지. 같은 숙소라도 공급사에 따라 다르게 나가는지.
검색을 구현할 때 확인하고 그 테스트 이름을 여기에 적는다.
