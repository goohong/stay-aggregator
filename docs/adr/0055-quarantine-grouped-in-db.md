# 0055. 제외한 항목을 같은 문제끼리 그룹화해 DB 에 남기기로 결정

## Context

요구사항의 선택 항목인 "정규화 실패 데이터 격리"를 하기로 했다. 변환하지 못한 것을 버리지 않고 남겨 나중에 분석할 수 있게 하는 일이다.
지금은 제외 사유를 로그 한 줄로만 남긴다 ([ADR-0039](0039-catalog-sync-remaining.md)).

[ADR-0054](0054-exclusion-kind-by-value-only.md) 가 무엇을 같은 문제로 볼지 정했다. 공급사, 숙소 코드, 객실 타입 코드, 문제가 된 값이 같으면 같은 문제다.
[격리 방식 조사](../research/failed-data-quarantine.md) 에서 확인했듯 같은 문제는 새로 쌓지 않고 한 기록으로 그룹화해 센다.

남은 것은 어디에 두느냐다.

## Options

- **(가) DB 테이블에 같은 문제마다 한 행을 두고 갱신한다** ← 채택 — 저장소 안에서 조회·분석할 수 있고 재시작해도 남는다.
  같은 문제는 행을 고치기만 하므로 행 수가 매핑 크기를 넘지 않는다. 대신 뺀 항목이 있는 검색은 요청 경로에서 DB 에 쓴다
- **(나) 구조화된 로그 한 줄** — 검색 경로에 DB 쓰기가 늘지 않는다.
  대신 그룹화와 조회를 로그 수집 체계에 맡기게 되고, 그것은 이 저장소 밖이다. "버리지 않고 분석한다"를 저장소 안에서 보일 수 없다
- **(다) 메모리에 최근 것만 둔다** — 쓰기 비용이 거의 없다. 대신 재시작하면 사라져 "버리지 않는다"와 어긋난다

## Decision

- **테이블 하나에 같은 문제마다 한 행**을 둔다. 같은 문제가 다시 오면 새 행을 만들지 않고 그 행을 갱신한다
- 행이 갖는 것: 공급사, 숙소 코드, 객실 타입 코드, 문제가 된 값, **횟수, 처음 본 시각, 마지막 시각, 마지막 사유 문장, 마지막 원본**
- **목록 동기화와 검색 모두에서 남긴다.** 두 흐름 모두 제외 항목을 만든다
- 매핑에 없어 뺀 것도 남긴다(값은 `매핑`). 응답 건수에서 빼는 규칙은 그대로다 ([ADR-0046](0046-supplier-status-in-search-response.md))
- **원본은 우리가 읽어 들인 항목 하나를 JSON 으로 남긴다.** 어댑터가 공급사 응답에서 꺼낸 그 항목(`Fetched…`)이다.
  공급사 HTTP 본문은 숙소 50개가 한 덩어리라 항목 하나를 떼기 어렵고, 본문을 어댑터 밖으로 들고 나오면 경계가 바뀐다
- **응답을 먼저 보내고 기록은 뒤에서 쓴다.** 격리는 분석을 위한 부가 기록이지 응답의 일부가 아니다. 쓰는 일이 실패해도 검색과 동기화는 실패시키지 않고 로그로 남긴다
- **오래된 기록은 목록 동기화가 돌 때 지운다.** 마지막으로 본 시각이 보관 기간보다 오래된 행이다. 이미 도는 주기 작업에 붙여 새 스케줄을 만들지 않는다.
  보관 기간의 값은 선택 항목을 마친 뒤 다른 값들과 함께 정한다

**이유**

- 요구가 "버리지 않고 추후 분석"이라 저장소 안에서 조회할 수 있어야 한다. 로그는 그 분석을 저장소 밖에 맡긴다
- 같은 문제를 그룹화해 갱신하므로 사용자가 짚은 "같은 잘못된 요청이 계속 오면 계속 쌓이지 않느냐"가 해결된다. 행 수는 서로 다른 문제의 수이지 검색 횟수가 아니다
- 정상인 검색에는 뺀 항목이 없어 쓰기가 일어나지 않는다

## Consequences

**얻는 것**
- 무엇이 몇 번, 언제부터 언제까지 빠졌는지를 조회로 볼 수 있다
- 같은 문제가 반복돼도 행이 늘지 않는다
- 운영자가 공급사에 연락할 때 마지막 원본을 근거로 보여줄 수 있다

**잃는 것**
- **뺀 항목이 있는 검색은 뒤에서 DB 에 쓴다.** 응답은 늦어지지 않지만, 공급사가 응답 전체를 다르게 보내기 시작하면 검색마다 여러 행을 갱신해
  [ADR-0021](0021-block-on-virtual-threads.md) 이 적은 "DB 커넥션 풀로 몰린다"에 더해진다
- **앱이 내려가는 순간 쓰지 못한 기록은 사라진다.** 분석용 횟수 기록이라 받아들인다
- 원본이 공급사가 보낸 원문 그대로는 아니다. 규약에 없어 받지 않은 필드는 남지 않는다
- 목록 동기화를 꺼 두면 오래된 기록도 지워지지 않는다
- 같은 행을 여러 검색이 동시에 갱신하면 횟수가 어긋나지 않게 DB 가 한 문장으로 더해야 한다
- 기록이 실패해도 응답은 나가므로 기록이 빠질 수 있다

**다시 볼 것**
- 보관 기간의 값
- 검색 경로의 쓰기가 실제로 문제가 되면 쓰기를 모아 뒤에서 하는 방식

## Discussion

- **AI 주장과 근거** — 처음에 (가)를 권하며 "뺀 항목이 있을 때만 쓴다"를 근거로 들었다
- **반박** — 사용자가 물었다. "잘못된 요청이 동일하게 계속 들어와도 갱신이 아니고 계속 쌓이지 않아?"
- **검증 결과** — 맞다. AI 는 같은 문제가 매번 새 행이 되는 것을 보지 못했다. 조사해 보니 업계는 같은 문제를 그룹화해 센다.
  그리고 그룹화하려면 사유를 종류로 나눠야 해서 ADR-0054 를 먼저 정했다
- **사용자 판단** — (가)로 정했다. 이어서 원본은 읽어 들인 항목 하나, 정리는 목록 동기화 때로 정했다
- **기록 시점** — AI 는 "응답 전에 쓰고 실패는 무시"를 권하며 "테스트에서 바로 확인할 수 있다"를 근거로 들었다.
  사용자가 "나중에 쓰는 게 낫지 않아? 응답이 먼저니까?" 라고 물었고, 따져 보니 AI 의 근거는 설계 근거가 아니라 작업 편의였다. 응답을 먼저 보내기로 바꿨다

## Verification

같은 문제가 여러 번 오면 한 행에 횟수가 늘고, 마지막 사유·원본이 바뀌고 처음 본 시각은 그대로인지
  → `QuarantineIntegrationTest.같은 문제가 여러 번 오면 한 행에 횟수가 늘고 마지막 사유와 원본이 바뀐다`

코드가 비어 있는 문제끼리도 그룹화되는지 (`UNIQUE NULLS NOT DISTINCT`)
  → `QuarantineIntegrationTest.코드가 비어 있는 문제끼리도 한 행으로 그룹화된다`

오래된 행만 지우는지
  → `QuarantineIntegrationTest.마지막으로 본 시각이 기준보다 오래된 행만 지운다`
  → 목록 동기화가 부르는 자리: `CatalogSyncService.syncAll` 의 `quarantine.purgeExpired()`

기록이 뒤에서 쓰이는지, 검색에서 뺀 항목이 남는지
  → `QuarantineIntegrationTest.기록은 뒤에서 쓰여 곧 남는다`
  → `SearchServiceIntegrationTest.스펙과 달라 뺀 항목은 격리 기록에 남는다`

기록이 실패해도 응답이 나가는지
  → `QuarantineRecorder.record` 가 가상 스레드에서 쓰고 예외를 잡아 로그만 남긴다. 실패를 일부러 만드는 테스트는 없다
