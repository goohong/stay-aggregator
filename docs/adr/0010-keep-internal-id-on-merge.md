# 0010. 같은 숙소를 병합해도 내부 식별자 유지

## Context

두 공급사가 같은 숙소를 각자의 코드로 팔 수 있다. 이 둘을 알려주는 공통 키는 없어서
합치려면 숙소명 같은 정보로 추정해야 한다. 합치지 않고 공급사 상품마다 다른 내부 식별자를
주는 것이 기본 동작이고, 병합은 선택 항목이지만 이 프로젝트는 하기로 했다.

내부 식별자는 우리가 발급하고, 공급사를 호출할 때는 쓰지 않는다. 검색 응답을 받는 쪽이
그 식별자를 들고 있다가 상세·찜·예약 같은 요청을 다시 보낼 때 쓴다. 그리고 같은 공급사
상품은 다시 조회해도 항상 같은 내부 식별자로 돌아와야 한다.

## Options

- **(가) 병합해도 내부 식별자는 그대로 두고, 같은 숙소라는 묶음 정보를 덧붙인다** ← AI 추천 —
  공급사 상품의 식별자가 병합 전후로 바뀌지 않는다. 잘못 합쳤으면 묶음만 떼면 된다.
  대신 응답에 묶음과 공급사 상품이라는 두 층이 생긴다.
- **(나) 병합하면 한쪽 식별자로 통일한다** — 응답의 식별자가 한 층이라 단순하다.
  대신 병합하는 순간 한쪽 상품의 식별자가 바뀌고, 잘못 합쳤을 때 되돌리기 어렵다.
- **(다) 병합 결과를 저장하지 않고 응답을 만들 때만 묶는다** — 저장 구조를 건드리지 않는다.
  대신 이름이나 묶는 규칙이 바뀌면 묶이는 결과가 흔들린다.

## Decision

**(가)** 를 택한다. 내부 식별자는 공급사 상품 하나를 가리키고, 한 번 발급하면 바꾸지 않는다.
병합은 그 위에 묶음 정보를 더하는 방식으로만 한다.

**이유** — 예약은 결국 특정 공급사 상품에 걸어야 한다. 응답을 받은 쪽이 들고 있는 식별자가
공급사 상품 하나를 계속 가리키고 있어야, 그 식별자로 어느 공급사에 무엇을 예약할지 알 수 있다.

## Consequences

**얻는 것**
- 병합 여부와 무관하게 "같은 공급사 상품은 항상 같은 내부 식별자"가 지켜진다
- 병합 추정이 틀려도 공급사 상품 식별자는 영향을 받지 않는다

**잃는 것**
- 검색 응답에 묶음을 어떻게 보여줄지 한 번 더 정해야 한다 (응답 스키마를 정할 때)
- 묶음 정보를 어디에 어떤 형태로 둘지는 병합을 설계할 때 따로 정해야 한다

## Discussion

- **AI 주장과 근거** — 처음에는 테이블 구조로 접근했다. "공급사 코드와 내부 식별자를 한 테이블에 두면
  숙소 하나에 공급사 둘을 붙일 자리가 없으니, 내부 숙소 테이블과 매핑 테이블을 나눠야 한다"고 했다
- **반박** — "행 두 개를 들고 있으면 되는 거 아니냐, DB 에서까지 합쳐져 있어야 하냐"는 질문을 받았다.
  이어서 기본 키를 자연 키로 둘지 자동 증가로 둘지까지 내려가자, "ERD 를 짜려던 게 아니라 결정을
  먼저 하려던 것"이라는 지적을 받았다
- **검증 결과** — 한 테이블로도 병합이 가능했고, "자리가 없다"는 주장은 내부 식별자를 기본 키로
  가정한 데서 나온 틀린 말이었다. 또 테이블·키 구조는 결정이 아니라 그 뒤의 설계였다. 결정에
  해당하는 질문은 "병합하면 이미 발급한 식별자를 바꿀 것인가" 하나였다
- **그래서 어떻게 바뀌었나** — 질문을 결정 수준으로 다시 세웠다. 사용자는 처음에 (나)를 떠올렸으나,
  내부 식별자를 받는 쪽이 그것으로 예약까지 한다는 점을 확인하고 (가)를 택했다. 결정 근거도 AI 가 든
  "되돌리기 쉽다"보다 사용자가 든 "예약 대상이 공급사 상품이다"가 더 정확했다

## Verification

아직 구현 전이다. 병합을 구현할 때 "병합 후에도 공급사 상품의 내부 식별자가 그대로인지" 확인하는
테스트를 추가하고 이 절에 이름을 적는다.
