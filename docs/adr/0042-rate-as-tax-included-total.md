# 0042. 요금은 세금 포함 기간 전체 총액 하나로 담기로 결정

## Context

두 공급사가 요금을 다르게 준다. Mock 이 흉내 내는 응답 형태로 보면 이렇다.

| | 공급사 A | 공급사 B |
|---|---|---|
| 기준 | 날짜별 1박 금액 | 기간 전체 총액 |
| 세금 | 날짜마다 따로 온다 | 포함 여부만 온다. 세금액은 없다 |
| 통화 | 객실 타입 단위로 온다 | 같다 |
| 재고 | 요금과 같은 자리에 온다 | 요금과 분리된 목록으로 온다 |

**한쪽 방향만 계산된다.** A 는 날짜별 금액을 더해 총액을 만들 수 있다. B 는 총액만 주므로 1박 금액을 되돌릴 수 없다.
총액을 박수로 나눌 수는 있지만 그 값으로 팔렸다는 근거가 없다.

요구사항은 무엇을 표준으로 삼고 무엇을 버릴지 판단하고 그 근거를 README 에 적으라고 한다. 요금 필드 구성은 직접 설계할 대상이다.

확인한 사실 (자세한 출처는 [요금 표시 조사](../research/rate-display.md))

| 사실 | 원문 |
|---|---|
| 한국은 소비자가 가격을 처음 보는 화면부터 총액을 표시하게 한다. 총액은 거부할 수 없는 모든 비용의 합이고 숙박의 봉사료·세금이 예시로 들려 있다 | [공정거래위원회 지침 개정 (2025-10-24 시행)](https://www.korea.kr/news/policyNewsView.do?newsId=156721985#:~:text=%EC%A7%80%EB%B6%88%EC%9D%84%20%EA%B1%B0%EB%B6%80%ED%95%A0%20%EC%88%98%20%EC%97%86%EB%8A%94%20%EB%AA%A8%EB%93%A0%20%EB%B9%84%EC%9A%A9%EC%9D%98%20%ED%95%A9%EA%B3%84) |
| 미국은 가장 눈에 띄는 가격이 필수 수수료를 모두 넣은 총액이어야 한다고 한다 | [FTC 발표](https://www.ftc.gov/news-events/news/press-releases/2024/12/federal-trade-commission-announces-bipartisan-rule-banning-junk-ticket-hotel-fees#:~:text=the%20most%20prominent%20price%20in%20an%20ad%20needs%20to%20be%20the%20all%2Din%20total%20price) |
| 연동 규격도 숙박 기간 총액을 기준으로 삼고 기본가·세금·수수료는 구성 항목으로 따로 둔다 | [Google 호텔 가격 구조화 데이터](https://developers.google.com/hotels/hotel-prices/structured-data/hotel-price-structured-data#:~:text=The%20total%20price%20for%20the%20length%20of%20stay%20should%20be%20specified) |
| 1박 가격의 정의는 플랫폼마다 다르다. 세금 포함 총액을 박수로 나눈 곳과 세금 제외 1박으로 보이는 곳이 있다 | 조사 기록의 "플랫폼 화면" 절 |
| 세금 포함 총액이어도 현장에서 더 내는 세금이 있을 수 있다 | 같은 절 |

## Options

- **(가) 세금 포함 총액 하나만 담는다** ← 채택 — 두 공급사가 같은 모양이 된다. 대신 A 가 준 날짜별 금액을 버린다
- **(나) 총액에 날짜별 내역을 곁들인다(있는 공급사만)** — A 의 정보를 버리지 않는다. 대신 공급사에 따라 있고 없는 필드가 생겨, 표준 모델이 공급사 차이를 그대로 드러낸다
- **(다) 총액에 기본가와 세금을 나눠 담는다** — 구성 항목이 보인다. 대신 B 는 포함 여부만 주고 세금액을 주지 않아 같은 문제가 세금 쪽에서 생긴다

## Decision

- 표준 모델의 요금은 **세금 포함 기간 전체 총액 하나**다
- **금액과 통화를 한 값 객체로 묶는다.** 통화 없는 금액이 돌아다니지 않게 한다. 검증은 그 생성자가 한다([ADR-0041](0041-validate-in-constructors.md))
- **통화는 응답에 온 값을 그대로 싣고 변환하지 않는다.** 서로 다른 통화를 함께 노출할 때의 처리는 요구사항의 선택 항목이라 하지 않는다
- **최소 단위는 정수**다. 두 공급사가 원 단위 정수로 주고, 소수점을 쓰는 통화가 오면 그때 다시 본다
- A 의 날짜별 금액은 총액을 만드는 데만 쓰고 표준 모델에 담지 않는다
- **1박 얼마로 보여줄지는 보여주는 쪽이 총액과 박수로 계산한다.** 서버는 그 반올림 규칙을 정하지 않는다

**이유**

- 계산이 한쪽으로만 된다. B 의 총액에서 1박을 되돌릴 수 없고, A 의 날짜별에서 총액은 만들 수 있다. 두 공급사가 같은 모양이 되는 기준은 총액뿐이다
- 규제와 연동 규격이 총액을 기준으로 삼는다. 고객이 처음 보는 화면의 값이 총액이어야 한다는 방향과 맞다
- 1박 가격의 정의가 플랫폼마다 다르다. 서버가 미리 나눠 담으면 그 반올림 규칙이 서버 결정이 되고, 화면이 다른 규칙을 쓰고 싶을 때 걸린다

## Consequences

**얻는 것**
- 두 공급사의 요금이 같은 모양으로 나온다. 쓰는 쪽이 공급사를 구분하지 않는다
- 요금 필드가 하나라 응답이 단순하고, 규제가 요구하는 값과 같다
- 통화 없는 금액이 존재할 수 없다

**잃는 것**
- **A 가 준 날짜별 금액을 버린다.** 날짜별 가격을 보여주는 기능이 필요해지면 표준 모델을 고쳐야 한다. 그때는 (나)로 간다
- **세금 범위가 두 공급사에서 같은지 확인하지 못했다.** A 의 세금액 합과 B 의 "포함" 이 같은 범위인지는 스펙에 없고, 현장에서 더 내는 세금이 있을 수 있다는 것만 조사로 확인했다. 총액 하나로 담으면 모델이 이 차이를 숨긴다
- 1박 가격을 보여주려면 보여주는 쪽이 계산한다. 서버 응답만 보고는 그 값을 알 수 없다

**넘기는 것**
- 요금에 붙는 판매 조건(조식 포함, 무료 취소)을 어느 자리에 둘지 (Q4). 두 공급사 모두 조식 포함 여부를 주고, 조사에서는 한 객실 타입에 조건이 다른 요금이 여러 개 붙는 것을 확인했다
- ~~금액이 0 이거나 음수로 오는 경우를 어떻게 볼지~~ → [ADR-0027](0027-spec-violation-handling-criteria.md) 의 "요금에 적용한 결과" 표에서 정했다 (2026-09-17)
- 서로 다른 통화를 함께 노출하는 설계 (요구사항의 선택 항목)

## Discussion

- **AI 주장과 근거** — (가)를 권하면서 근거로 계산의 비가역성과 규제·연동 규격의 방향을 들었다
- **사용자 판단** — "총액으로 주는 게 맞다. 보여지는 것에 대한 간단한 계산은 프론트에서 하는 게 맞다" 로 같은 결론이었고, 표시 계산의 자리를 분명히 했다
- **AI 가 든 약점** — A 의 정보를 버리는 선택이고, 세금 범위가 같은지 확인하지 못했다는 두 가지다. 둘 다 잃는 것에 적었다

## Verification

통화 없는 금액을 만들 수 없는지
  → `MoneyTest.통화가 비어 있으면 만들 수 없다`

다른 통화를 섞어 더할 수 없는지 (A 의 날짜별 금액을 더할 때 통화가 갈리면 멈춘다)
  → `MoneyTest.통화가 다르면 더할 수 없다`

0원이 막히지 않고 음수만 막히는지 (ADR-0027 의 요금 표)
  → `MoneyTest.0원은 만들어진다` / `MoneyTest.음수 금액은 만들 수 없다`

두 공급사의 요금이 같은 모양으로 나오는지. A 의 날짜별 금액 합(세금 포함)이 총액이 되는지.
어댑터를 구현할 때 확인하고 그 테스트 이름을 여기에 적는다.
