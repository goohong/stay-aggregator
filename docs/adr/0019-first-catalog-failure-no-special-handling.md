# 0019. 공급사 첫 숙소 목록 실패에 별도 장치를 두지 않기로 결정

## Context

매핑은 PostgreSQL 에 저장해 앱을 다시 띄워도 남는다([ADR-0017](0017-mapping-in-server-rdb.md),
[ADR-0018](0018-postgresql-for-mapping.md)). 숙소 목록은 앱 기동 시와 기본 하루 한 번 받아오고, 주기는 설정으로 바꿀 수 있다
([ADR-0013](0013-catalog-sync-on-startup-and-interval.md), [ADR-0016](0016-catalog-sync-interval-default-daily.md)).
그래서 목록을 받아오지 못해 검색할 수 없는 경우는 서비스를 처음 띄울 때와 새 공급사의 첫 목록을 받을 때로 좁혀진다.
요구사항은 매핑을 만드는 단계가 실패하면 어떻게 할지 생각해 볼 지점으로만 언급한다.

## Options

- **(가) 앱 기동을 실패시킨다** — 매핑 없는 공급사를 안고 떠 있지 않는다. 대신 공급사 하나의 장애로 다른 공급사 검색까지 막힌다.
- **(나) 별도 장치 없이, 그 공급사는 다음 동기화까지 검색에서 빠진다** ← AI 추천 — 새 장치가 없다. 앱 재시작(기동 시 동기화)이나 주기 설정으로 회복한다.
  대신 회복 방법을 모르면 그 공급사가 주기 동안 빠져 있다.
- **(다) 매핑이 한 번도 없는 공급사만 짧은 간격으로 재시도한다** — 기동 순서가 달라도 금방 회복한다. 대신 재시도 간격·횟수·포기 조건을 정해야 하고 재시도 정책과 겹친다.

## Decision

**(나)** 를 택한다. 첫 목록을 받지 못한 공급사는 다음 동기화까지 검색에서 빠지고, 회복은 앱 재시작이나 동기화 주기 설정으로 한다.

**이유** — 운영에서는 매우 드문 상황이고, 이미 정한 기동 시 동기화와 설정 가능한 주기로 회복할 수 있다. 드문 상황 때문에
동기화 경로를 복잡하게 만들지 않는다.

## Consequences

**얻는 것**
- 동기화 경로에 새 장치가 생기지 않는다

**잃는 것**
- 회복 방법을 모르는 사람에게는 그 공급사가 주기 동안 검색에서 빠진 채로 보인다

**남겨 둘 것**
- README 의 실행 방법에 Mock 공급사를 앱보다 먼저 띄운다는 순서를 적는다
- 빠진 공급사를 알아채는 방법은 모니터링 설계(Q18)에서 다룬다
- 우선순위가 낮아 판단만 남긴다. 다른 결정이 끝난 뒤 다시 볼 수 있다

## Discussion

- **AI 주장과 근거** — 처음 실패한 공급사만 정기 주기보다 짧게 재시도하는 (다) 를 권했다. 공급사 서버가 앱보다 늦게 뜨기만 해도
  하루 동안 빠질 수 있다는 이유였다
- **반박** — 정말 드문 상황인데 이걸 고려해야 하는지부터 의문이다
- **검증 결과** — 운영에서는 처음 띄울 때와 새 공급사 연결 때뿐이고, 새 공급사 연결은 사람이 지켜보는 작업이다. 요구사항도
  구현이 아니라 생각해 볼 지점으로만 언급한다. 회복 수단은 이미 정한 결정(기동 시 동기화, 설정 가능한 주기)에 있다
- **그래서 어떻게 바뀌었나** — 추천을 (나) 로 바꾸고, 판단과 회복 방법만 남기기로 했다

## Verification

별도 구현이 없는 결정이다. README 를 쓸 때 실행 순서에 Mock 공급사를 먼저 띄우는지 확인한다.
