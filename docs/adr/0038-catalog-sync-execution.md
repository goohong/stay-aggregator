# 0038. 목록 동기화의 기동 방식·공급사 설정·트랜잭션 경계 결정

## Context

[ADR-0013](0013-catalog-sync-on-startup-and-interval.md)·[ADR-0016](0016-catalog-sync-interval-default-daily.md) 은 목록 동기화를 **언제** 하는지만 정했다.
앱 기동 시와 설정된 주기(기본 하루 한 번)다. 어떻게 도는지는 비어 있었다. 구현에 들어가기 전 세 가지를 정한다.
기동할 때 동기화가 끝날 때까지 기다릴지, 공급사 주소와 인증 키를 어디에 둘지, 한 번의 동기화를 어느 범위의 트랜잭션으로 묶을지다.

관련된 결정
- 공급사 하나의 목록 조회가 실패해도 그 공급사만 다음 주기까지 빠지고 앱은 뜬다([ADR-0019](0019-first-catalog-failure-no-special-handling.md))
- 어댑터는 공급사마다 한 클래스이고 인터페이스 타입으로 선언한 목록으로 주입된다([ADR-0031](0031-supplier-adapter-boundaries.md))
- 앱에는 Mock 의 존재를 아는 분기가 없고, 운영으로 옮길 때 바뀌는 것은 base-url 설정값뿐이다([ADR-0005](0005-separate-mock-module.md))
- 사라진 행 표시는 한 공급사 단위로 원자적이어야 한다([ADR-0037](0037-missing-catalog-entries-kept-and-marked.md))

## Options

기동 시 동기화
- **(가) 기동을 막지 않고 뒤에서 돌린다** ← AI 추천 — 앱이 바로 뜬다. 대신 동기화가 끝나기 전 검색은 매핑이 덜 채워진 상태로 응답한다.
- **(나) 동기화가 끝나야 기동이 끝난다** — 뜨는 순간부터 매핑이 채워져 있다. 대신 공급사가 느리거나 응답하지 않으면 그만큼 기동이 멈춘다.

공급사 주소·인증 키
- **(가) 설정 파일에 공급사마다 한 묶음** ← AI 추천 — 새 공급사는 어댑터 클래스 하나와 설정 묶음 하나로 붙는다. 대신 공급사 이름이 설정 키와 코드 양쪽에 있어 어긋나면 실행할 때 드러난다.
- **(나) 공급사마다 전용 설정 클래스** — 같은 모양의 클래스가 공급사 수만큼 반복된다.
- **(다) 코드 상수나 환경 변수만 사용** — 주소를 바꾸려면 빌드가 필요하고 Mock 과 실제 공급사를 오가기 번거롭다.

트랜잭션 경계
- **(가) 공급사 하나의 동기화 전체를 한 트랜잭션** ← AI 추천 — 실패 단위와 트랜잭션 단위가 같다. 대신 숙소가 아주 많아지면 트랜잭션이 길어진다.
- **(나) 모든 공급사를 한 트랜잭션** — 공급사 하나가 실패하면 성공한 공급사의 결과까지 되돌아간다. ADR-0019 와 어긋난다.
- **(다) 수백 건 배치마다 끊는다** — 트랜잭션이 짧다. 대신 중간에 멈추면 반만 반영된 상태가 남고, 사라진 행 표시가 일부만 되면 실제로는 목록에 있는 숙소가 검색에서 빠진 채 남을 수 있다.

## Decision

- 기동 시 동기화는 **앱 기동을 막지 않는다.** 앱이 뜬 뒤 뒤에서 돈다
- 공급사 주소와 인증 키는 **설정 파일에 공급사마다 한 묶음**으로 둔다. 저장소에는 Mock 을 가리키는 값만 두고, 실제 값은 환경 변수로 덮어쓴다
- 트랜잭션은 **공급사 하나의 동기화 전체**를 묶는다. 새 행 추가, 이름·최대 수용 인원 갱신, 사라진 행 표시가 함께 반영되거나 함께 취소된다

**이유** — ADR-0019 에서 공급사 하나의 실패가 앱 전체를 막지 않게 하기로 했는데, 기동을 기다리면 실패가 아니라 느림만으로도 기동이 멈춘다.
설정을 공급사별 묶음으로 두면 ADR-0005 가 말한 "운영으로 옮길 때 바뀌는 것은 설정값뿐"과 ADR-0031 이 말한 "새 공급사는 클래스 하나와 설정"이 그대로 성립한다.
트랜잭션을 공급사 단위로 두면 실패 단위와 같아져, 한 공급사의 실패가 다른 공급사의 결과를 되돌리지 않으면서 ADR-0037 이 요구한 표시의 원자성도 지켜진다.

## Consequences

**얻는 것**
- 공급사가 느리거나 응답하지 않아도 앱은 뜬다. Mock 의 무응답 모드로 그 상황을 확인할 수 있다
- 새 공급사를 붙일 때 고칠 곳이 어댑터 클래스 하나와 설정 묶음 하나로 유지된다
- 한 공급사의 동기화가 중간에 멈춰도 반만 반영된 상태가 남지 않는다

**잃는 것**
- 기동 직후 첫 동기화가 끝나기 전의 검색은 결과가 적거나 비어 보인다. 오류로 보이지는 않는다
- 공급사 이름이 설정 키와 코드 양쪽에 존재한다. 어긋나면 실행할 때 드러난다
- 한 공급사의 숙소가 아주 많아지면 트랜잭션이 길어지고 그동안 매핑 테이블에 쓰기 잠금이 걸린다. 하루 한 번 배경 작업이라 지금 규모에서는 문제로 보지 않았고, 길어지면 쪼개는 방법을 다시 본다

**넘기는 것**
- 목록 조회의 타임아웃 값. Mock 의 응답 지연 모드로 측정한 뒤 정한다([ADR-0028](0028-implement-decided-units-first.md))
- 기동 직후 매핑이 비어 있는 구간을 밖에서 알 수 있게 할지 (Q18)

## Verification

한 공급사의 동기화 도중 실패했을 때 그 공급사의 매핑이 이전 상태로 남는지
  → `CatalogSyncIntegrationTest.저장 도중 실패하면 그 공급사 매핑이 이전 상태로 남는다`

다른 공급사는 그대로 반영되는지
  → `CatalogSyncIntegrationTest.공급사 하나가 실패해도 다른 공급사는 반영된다`

설정 파일에 공급사별 묶음이 있고 코드에 주소가 없는지
  → `app/src/main/resources/application.yml` 의 `stay.suppliers`, `app/src/main/kotlin/com/stayaggregator/supplier/StayProperties.kt`

응답하지 않는 공급사가 있어도 기동이 끝나는지 — Mock 의 공급사 A 를 무응답 모드로 두고 `./gradlew :app:bootRun` 했을 때
관찰한 것(2026-09-17): 기동이 2.7초에 끝나고(`Started StayAggregatorApplicationKt in 2.692 seconds`),
30초 뒤 그 공급사만 타임아웃으로 실패했으며(`목록 동기화 실패 supplier=a`), 같은 주기에 공급사 B 는 반영됐다
(`목록 동기화 완료 supplier=b 숙소=1 객실타입=1 목록에없는숙소=0 제외=0`).

## Discussion

- **AI 주장과 근거** — 기동 방식을 선택지로 제시하면서 기동을 막는 안도 함께 놓았다
- **반박** — 내부 데이터를 정리하는 중이라고 앱을 멈추는 건 말이 안 된다
- **검증 결과** — 그렇다. 다른 시스템에서는 "앱은 뜨되 준비됨 신호를 늦추는" 중간 형태를 쓰지만, 우리는 배포 환경을 정한 것이 없고 매핑이 비어도 오류가 아니라 결과가 적을 뿐이라 그 형태를 둘 이유가 없었다
- **그래서 어떻게 바뀌었나** — 기동을 막는 안을 접고, 그 중간 형태가 필요해질 조건만 기록했다
