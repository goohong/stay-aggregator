# 0026. 예약 불가 상품은 응답에서 빼지 않고 예약 가능 객실 수 0 으로 노출

## Context

검색 응답에는 객실 타입마다 요청 기간 전체의 예약 가능 객실 수를 담고, 0 이면 예약 불가다
([ADR-0023](0023-multi-night-availability-minimum.md)).
요구사항은 예약 불가 상품을 응답에서 빼든 0 으로 노출하든 자유로 두고, 고른 쪽과 이유를 README 에 남기라고 한다.
정렬·페이징은 범위 밖이다.

## Options

- **(가) 응답에서 뺀다** — 예약할 수 있는 항목만 담긴다. 대신 "취급하지만 이 날짜엔 방이 없다"는 정보가 사라져, 응답을 받는 화면이 매진을 보여 줄 방법이 없다.
- **(나) 0 으로 노출한다** ← AI 추천 — 응답을 받는 쪽이 매진 표시와 숨기기 중 고를 수 있다. 대신 예약할 수 없는 항목만큼 응답이 커진다.

## Decision

**(나)** 를 택한다. 예약 가능 객실 수가 0 인 객실 타입도 응답에 담고, 서버에서 거르지 않는다.

**이유** — 매진을 보여 줄지는 응답을 받는 화면이 정할 일이다. 서버가 0 으로 넘기면 화면은 매진 표시든 숨기기든 고를 수 있지만,
서버가 빼면 그 선택지가 사라진다. 거르는 단계가 없어 판정 결과를 그대로 넘기는 만큼 로직도 단순하다.

## Consequences

**얻는 것**
- 응답을 받는 쪽이 매진 상품의 표시 여부를 정할 수 있다
- 판정 뒤에 거르는 단계가 없다

**잃는 것**
- 예약할 수 없는 항목만큼 응답이 커진다. 페이징이 범위 밖이라 줄일 수단이 없고, 실제 크기는 측정하지 않았다

**남겨 둘 것**
- 예약 가능 여부를 boolean 필드로 따로 둘지는 응답 필드를 설계할 때 정한다
- README 에 이 결정 한 줄과 이유를 적는다

## Discussion

- **AI 주장과 근거** — (가)를 권했다. 검색 결과는 예약하려고 보는 것이라 예약할 수 없는 항목은 쓸모가 없고,
  페이징이 없으니 보유 숙소가 늘면 매진 항목까지 담은 응답이 커진다는 이유였다
- **반박** — 써 본 숙박 앱들은 매진으로 보여 준다. 굳이 빼기보다 처리하지 않고 넘기는 게 로직도 단순하다
- **검증 결과** — 매진을 보여 줄지는 화면의 결정이라, 서버가 빼면 그 선택지를 서버가 대신 없앤다. 응답 크기 우려는 수치로 확인하지 않은 것이었다.
  "대부분의 숙박 앱이 그렇다"는 일반화는 확인하지 않았고, 로직 단순함은 필터 한 단계 차이라 보조 근거에 그친다
- **그래서 어떻게 바뀌었나** — 추천을 (나)로 바꾸고, 주된 이유를 "정보를 버리지 않아 응답을 받는 쪽이 고를 수 있다"로 적었다

## Verification

검색 통합 테스트에서 날짜 하나의 재고가 0 인 객실 타입이 응답에 예약 가능 객실 수 0 으로 포함되는지. 테스트를 만들면 그 이름을 여기에 적는다.
