# 0005. 앱과 Mock 공급사를 별도 Gradle 모듈로 분리

## Context

외부 공급사를 실제로 호출할 수 없으므로 공급사를 모사하는 Mock 서버가 필요하다.
Mock 은 앱과 **다른 포트**에서 별도 프로세스로 떠야 한다. 같은 프로세스에 두면 앱이 자기 자신을
HTTP 로 호출하게 되고, 무응답 상황에서 앱 자신의 스레드 풀이 고갈되어 연동 실패처럼 보인다.

Mock 은 버리는 코드다. 오래 관리할 것도, 품질을 다듬을 것도 아니다.
그래서 구조를 크게 만들지 않는 쪽이 낫다.

## Options

- **(가) 단일 모듈, Mock 을 `src/test/kotlin/mocksupplier/` 에** — 모듈을 안 늘린다.
  앱 패키지 밖이라 컴포넌트 스캔에 안 걸리고 제품 jar 에도 안 들어간다.
  대신 Mock 프로세스가 앱의 클래스패스와 설정을 그대로 물려받는다.
- **(나) 별도 Gradle 모듈 `mock-supplier`** ← AI 추천 — 앱과 코드도 의존성도 설정도 공유하지 않는다.
  대신 모듈이 하나 늘어난다.

## Decision

**(나)** 를 택한다. `app` 과 `mock-supplier` 두 모듈로 나눈다.

두 모듈은 **서로를 의존하지 않는다.** HTTP 로만 만나고, 그 주소는 앱 설정의 공급사 base-url 값이다.
앱에는 Mock 의 존재를 아는 분기가 없다. 운영 환경으로 옮길 때 바뀌는 것은 그 설정값뿐이다.

루트 빌드 파일에는 **플러그인 버전만 선언하고 적용은 각 모듈에서** 한다.
공통 블록으로 설정을 상속시키면 모듈마다 원치 않는 의존성이 딸려 들어간다.

**이유** — 이전 프로젝트에서 도메인별로 쪼갠 멀티모듈을 쓰다 설정이 꼬여 빌드가 깨진 경험이 있어
모듈을 늘리는 데 거부감이 있었다. 다만 그때는 모듈들이 서로 의존했고 이번에는 의존하지 않는다.
꼬임의 원인이 이번에는 없다.

## Consequences

**얻는 것**
- Mock 이 앱의 설정과 의존성을 물려받지 않는다. 자동 구성이 딸려 오지 않는다
- `./gradlew :mock-supplier:bootRun` 으로 뜨고, 앱과 완전히 독립적으로 죽이고 살릴 수 있다

**잃는 것**
- 모듈이 하나 늘어난다. 루트 빌드 파일의 공통 설정을 최소로 유지해야 이 비용이 커지지 않는다

## Discussion

- **AI 주장과 근거** — 처음에는 단일 모듈에 Mock 을 `src/test` 에 두자고 했다.
  근거는 "모듈을 안 늘리면서 스캔 회피와 제품 jar 제외를 둘 다 얻는다"
- **반박** — 별도 검토에서 함정이 드러났다. `src/test` 의 런타임 클래스패스로 Mock 을 띄우면
  **앱의 main 리소스와 의존성을 전부 들고 뜬다.** 앱의 `application.yml` 을 읽어 포트가 충돌하고,
  데이터소스 설정이 있으면 Mock 이 JPA 와 H2 를 자동 구성한다.
  **H2 를 파일 모드로 쓰기로 했으므로 앱과 Mock 이 같은 DB 파일을 열려다 락 충돌로 하나가 죽는다**
- **검증 결과** — 피하려면 Mock 전용 설정 이름, 자동 구성 제외 목록, 실행 태스크를 따로 만들어야 하고
  그 비용이 모듈 하나보다 크다
- **그래서 어떻게 바뀌었나** — 모듈을 늘리지 않으려던 선택이 오히려 더 많은 설정을 요구해서 뒤집었다

## Verification

두 모듈이 있고 서로를 가리키는 의존이 없는지
  → `settings.gradle.kts` 의 `include("app")`·`include("mock-supplier")`,
    그리고 `grep -n 'project(":' app/build.gradle.kts mock-supplier/build.gradle.kts` 가 비어 있음

앱과 Mock 이 HTTP 로만 만나는지
  → `app/src/main/resources/application.yml` 의 `stay.suppliers.*.base-url` 이 Mock 의 주소를 가리킨다
