# 0029. ADR Verification 은 커밋마다 맞추지 않고 모아서 점검하기로 결정

이 ADR 은 [ADR-0028](0028-implement-decided-units-first.md) 의 결정 중 "Verification 이 이미 있는 파일을 가리키면 그 ADR 커밋이나 바로 다음 커밋에서 그 파일을 맞춘다"를 대체한다.
ADR-0028 의 나머지(구현 단위 적용, 설계 순서, 테스트 이름 기록, 구현 단위 AI 기록)는 그대로다.

## Context

ADR-0028 은 Verification 과 실제 파일의 어긋남을 막으려고 짝 규칙을 두었다. 첫 구현 단위를 고르면서 이 규칙이
[ADR-0006](0006-add-dependencies-when-needed.md) 과 부딪쳤다. ADR-0020 의 Verification 은 WebClient 스타터를, ADR-0021 은
가상 스레드 설정을 가리키는데, 둘 다 쓰는 코드는 아직 없다. 짝 규칙을 따르면 쓰지 않는 의존성과 설정을 미리 넣어야 하고,
ADR-0006 은 그것을 금한다.

## Options

- **(가) 짝 규칙을 "이미 구현한 기능에 해당할 때"로 좁힌다** ← AI 추천 — ADR-0006 과 함께 지킬 수 있다. 대신 규칙 문장이 조건부가 되어 적용 여부를 매번 판단해야 한다.
- **(나) 짝 규칙을 없애고, Verification 은 모아서 한 번에 점검한다** — 커밋마다 문서와 파일을 서둘러 맞추지 않는다. 대신 점검 전까지는 어긋난 Verification 이 남아 있다.
- **(다) 짝 규칙을 그대로 두고 스타터와 설정을 미리 넣는다** — Verification 이 바로 맞는다. 대신 ADR-0006 을 어긴다.

## Decision

**(나)** 를 택한다. ADR 커밋마다 Verification 이 가리키는 파일을 맞추는 규칙을 두지 않는다. 의존성과 설정은 ADR-0006 대로 그것을 쓰는 기능 단위에서 넣고,
Verification 과 실제 파일이 맞는지는 모아서 한 번에 점검한다. 점검 시점은 따로 정하지 않았다.

**이유** — Verification 은 결정이 지켜지는지 확인하는 곳이지, 결정이 곧바로 파일에 반영돼야 한다는 약속이 아니다. 구현 순서에 따라 아직 반영되지 않은 결정이 있는 것은 자연스럽고,
그걸 커밋마다 서둘러 맞추려는 규칙이 오히려 ADR-0006 같은 다른 결정을 어기게 만든다.

## Consequences

**얻는 것**
- 의존성과 설정이 그것을 쓰는 기능 커밋과 짝을 이룬다(ADR-0006)
- 커밋마다 Verification 을 맞추는 부담이 없다

**잃는 것**
- 점검 전까지는 문서의 Verification 과 실제 파일이 어긋난 채 남는다. 지금 ADR-0005·0020·0021 이 그렇다
- 점검을 잊으면 어긋남이 쌓인다. 남은 부채는 `git grep "이 절에 이름을 적는다"` 와 Verification 절을 훑어 확인한다

## Discussion

- **AI 주장과 근거** — 짝 규칙을 "이미 구현한 기능에 해당할 때"로 좁혀 ADR-0006 과 함께 지키자고 권했다
- **반박** — 급하게 맞춘다는 규칙 자체가 이상하다. 나중에 한 번 전부 Verification 을 점검하면 된다
- **검증 결과** — 짝 규칙을 만든 이유는 문서만 보고 파일을 연 사람이 틀린 내용을 보는 것이었다. 모아서 점검해도 그 목적은 점검 시점에 달성되고, 그 전까지 어긋남이 남는 것은 비용으로 받아들일 수 있었다
- **그래서 어떻게 바뀌었나** — 규칙을 좁히는 대신 없애고 모아서 점검하기로 했다

## Verification

CLAUDE.md 커밋 규칙에 Verification 짝 규칙 문장이 없는지.
