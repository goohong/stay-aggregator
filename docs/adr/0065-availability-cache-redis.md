# 0065. 재고·요금을 숙소 단위로 판정한 뒤 Redis 에 캐시하기로 결정

## Context

요구사항의 선택 항목에 "요금/재고 캐시: TTL, 캐시 스탬피드 방지, 캐시와 원본 정합성 오차 허용 범위"가 있다. 사용자는 **대규모 조회를 전제로** 하기로 했다 (Q32).
공급사 규약은 숙소 목록은 자주 바뀌지 않지만 재고·요금은 매번 바뀐다고 적는다.

지금 검색은 공급사마다 매핑의 숙소 코드를 50개씩 **호출 묶음**으로 나눠 부르고, 묶음마다 재시도 → 서킷 → 판정을 거쳐 합친다
(`SearchService`, [ADR-0045](0045-search-concurrency-and-budget.md)·[0051](0051-retry-transient-supplier-failures.md)·[0056](0056-circuit-breaker-per-supplier-outside-retry.md)).
묶음은 매핑 순서대로 만들어져, 숙소 하나가 늘거나 빠지면 뒤의 묶음 구성이 모두 밀린다.

확인한 사실

| 사실 | 원문 |
|---|---|
| 캐시 스탬피드를 막는 방식은 잠금, 외부 재계산, 확률적 조기 만료가 있다. 조기 만료는 만료가 가까울수록 각 요청이 독립적으로 미리 다시 계산할 확률이 커진다 | [Wikipedia, Cache stampede](https://en.wikipedia.org/wiki/Cache_stampede): "each process may recompute the cache value before its expiration by making an independent probabilistic decision, where the probability of performing the early recomputation increases as we get closer to the expiration of the value." (근거로 Vattani·Chierichetti·Lowenstein, VLDB 2015 를 든다. 논문 원본은 확인 못 함) |
| Redis 의 `SET NX EX` 잠금 방식은 더 권하지 않는다 | [Redis SET](https://redis.io/docs/latest/commands/set/) 절 "Patterns": "The following pattern is discouraged in favor of the Redlock algorithm" |
| Google 은 검색 결과에 가격 캐시를 쓰고, 예약 화면의 총액은 표시한 총액과 같아야 한다고 요구한다 | [Pricing overview](https://developers.google.com/hotels/hotel-prices/dev-guide/updating-prices): "Google typically uses prices from its price cache when displaying search results." / [Price Accuracy Policy](https://support.google.com/hotelprices/answer/6064419?hl=en) "Price requirements" |
| Hotelbeds 는 검색 결과의 요금마다 예약 전에 다시 확인해야 하는지 표시한다 | [Booking API Workflow](https://developer.hotelbeds.com/documentation/hotels/booking-api/workflow/) "Parsing the results": "If the type is RECHECK you will need to perform an extra operation called CheckRate …" |

위 인용은 독립 검토(Fable)가 원문을 열어 옮긴 것이고, 이 ADR 을 쓰며 다시 대조하지 않았다.

## Options

저장소
- **(가) Redis** ← 채택 — 여러 인스턴스가 공유해 공급사 호출이 실제로 준다. 대신 인프라가 늘고 인스턴스 사이 스탬피드를 따로 다뤄야 한다
- **(나) 앱 메모리** — 인프라가 늘지 않는다. 대신 인스턴스마다 따로라 대수가 늘수록 적중률이 떨어진다
- **(다) 메모리 앞에 Redis** — 대신 두 층의 만료가 어긋나 같은 검색이 인스턴스마다 다른 재고를 보일 수 있다

단위
- **(ㄱ) 숙소 하나** ← 채택 — 묶음 구성이 바뀌어도 적중한다. 캐시에 없는 숙소만 모아 묶음으로 부른다
- **(ㄴ) 호출 묶음 하나** — 단순하다. 대신 숙소 하나만 늘어도 뒤의 묶음이 모두 빗나간다
- **(ㄷ) 검색 결과 전체** — 대신 공급사 실패 결과까지 들어가고 조건이 조금만 달라도 빗나간다

값
- **(A) 판정을 마친 결과** ← 채택 — 판정과 격리 기록이 공급사 응답 한 번에 한 번만 일어난다
- **(B) 판정 전 받은 값** — 판정 규칙·매핑 변경이 바로 반영된다. 대신 적중할 때마다 판정과 격리 기록이 다시 돌아, 격리 횟수가 "공급사가 준 횟수"가 아니라 "캐시 적중 횟수"가 된다

스탬피드
- **(1) 만료 전 확률적 조기 갱신 + 인스턴스 안 같은 요청 합치기** ← 채택 — 갱신이 실패해도 기존 값이 남는다. 대신 처음 뜨는 키와 인스턴스 사이 중복은 막지 못한다
- **(2) Redis 잠금 + 대기** — 인스턴스 사이 중복이 없다. 대신 고객 요청이 잠금을 기다리고, 채우던 요청이 실패하면 기다린 쪽에 줄 값이 없다. Redis 문서도 단순 잠금을 권하지 않는다
- **(3) 막지 않는다** — 대신 인기 키가 만료될 때마다 공급사에 호출이 몰린다

## Decision

**키와 값**
- 키: 공급사, 숙소 코드, 체크인, 체크아웃, 성인, 아동. **인원은 뺄 수 없다.** 규약은 공급사가 인원으로 객실을 거른다고만 하고 요금이 인원과 무관하다고 하지 않는다
- 값: 그 숙소의 **판정을 마친 결과**(내보낼 객실 타입 목록, 스펙과 달라 뺀 건수, **우리가 공급사에서 받은 시각**)
- **응답에 항목이 하나도 없던 숙소도 빈 결과로 캐시한다.** 인원 조건에 맞는 객실이 없는 것은 정상 응답이다. 캐시하지 않으면 그런 숙소를 매번 다시 부른다
- **매진(예약 가능 0)도 캐시한다.** 정상 응답이다
- **공급사 실패는 캐시하지 않는다.** 실패한 묶음의 숙소는 아무 값도 쓰지 않는다. 회복한 공급사가 캐시 때문에 계속 실패로 보이지 않게 한다

**흐름**
- 캐시 조회는 **묶음을 만들기 전**이다. 공급사마다 캐시에서 한 번에 읽고(MGET), 빗나간 숙소만 50개씩 묶어 부른다. 그래서 재시도·서킷보다 앞이고 공급사별 검색 시간 한계 안이다
- 캐시 쓰기는 **응답을 먼저 보내고 뒤에서** 한다. 실패해도 로그만 남긴다 ([ADR-0055](0055-quarantine-grouped-in-db.md) 와 같은 방식)
- **만료된 값은 공급사가 실패해도 내보내지 않는다.** 얼마나 오래된 값까지 괜찮은지를 또 정하지 않는다

**스탬피드**
- 값에 받은 시각을 함께 두고, 만료가 가까운 적중은 확률적으로 그 숙소를 이번 묶음에 넣어 새로 받는다 (조기 갱신)
- 같은 인스턴스 안에서 같은 요청이 동시에 나가면 하나를 함께 쓴다

**Redis 장애**
- Redis 조회에 짧은 한계를 두고, 넘거나 실패하면 **캐시 없이 공급사를 직접 부른다.** 캐시는 빠르게 하는 장치이지 필수가 아니다
- 이 실패는 공급사 서킷에 세지 않는다. 우리 쪽 문제로 멀쩡한 공급사를 끊지 않는다 (ADR-0056)

**응답**
- **모든 항목에** 우리가 공급사에서 받은 시각을 싣는다. 새로 받은 것도 캐시에서 온 것도 같은 필드다. 캐시라는 구현이 계약에 드러나지 않는다
- 예약 전에 다시 확인할지는 받는 쪽이 이 시각으로 판단한다. 우리는 예약이 범위 밖이라 재확인 단계를 둘 수 없다

**클라이언트**
- Reactive Redis(Lettuce)로 Reactor 흐름 안에서 부른다. 타임아웃·동시성을 공급사 호출과 같은 방식으로 다룬다

**값(TTL, 조기 갱신 강도, Redis 조회 한계)은 선택 항목을 마친 뒤 다른 값들과 함께 정한다**

**이유**

- 대규모 전제에서 인스턴스마다 따로인 캐시는 대수가 늘수록 효과가 줄어든다
- 숙소 단위여야 매핑이 조금만 바뀌어도 캐시 전체가 빗나가는 일이 없다
- 판정 후 값이어야 격리 기록의 횟수가 공급사 응답 기준으로 남는다. 매핑 변경이 TTL 뒤에 반영되는 것은, 매핑이 하루 단위로 바뀌고 TTL 은 그보다 훨씬 짧을 것이라 실익이 작다
- 캐시 값은 추정이 아니라 과거 관찰이다. 문제는 그것을 지금 값처럼 내보내는 것이라, 받은 시각을 사실로 싣는다 (README 의 "추정한 값을 사실처럼 내보내지 않는다")

## Consequences

**얻는 것**
- 같은 조건의 검색이 반복되면 공급사 호출이 준다
- 공급사가 조금 늦어도 캐시에 있는 숙소는 바로 나간다
- 받는 쪽이 값의 나이를 안다

**잃는 것**
- **TTL 동안 실제와 다른 재고·요금이 나갈 수 있다.** 매진된 방이 예약 가능으로 보일 수 있다. 받은 시각으로 드러내지만 막지는 못한다
- Redis 가 인프라로 는다. compose·테스트에 Redis 가 필요하다
- 인원 조합이 키에 들어가 적중률이 떨어진다. 얼마나 떨어질지는 트래픽을 알아야 한다
- 매핑 변경이 TTL 이 지나야 캐시에 반영된다
- 처음 뜨는 키와 인스턴스 사이 스탬피드는 남는다
- Redis 가 죽으면 공급사 호출이 갑자기 는다
- 응답 항목마다 시각 필드가 는다

**다시 볼 것**
- TTL·조기 갱신 강도·Redis 조회 한계의 값
- 인원 조합별 적중률 측정

## Discussion

- **AI 주장과 근거** — 저장소는 Redis·메모리·둘 다를 내놓았다
- **사용자 판단** — "둘 다가 많이 어려워? 그럼 그냥 레디스로 우선 구현하자." AI 는 두 층의 만료가 어긋나 인스턴스마다 다른 재고를 보일 수 있는 것이 어렵다고 답했다
- **단위와 응답 표시** — 사용자가 "Fable 하고 논의해보자"고 해 독립 검토를 받았다. 검토는 숙소 단위를 권하면서 값을 **판정 후**로 두라고 했다(판정 전이면 격리 횟수가 캐시 적중 횟수로 오염). 빈 결과도 캐시해야 한다는 것, 인원을 키에서 뺄 수 없다는 것을 짚었다.
  또 캐시와 무관한 **기존 결함 둘**(요청하지 않은 숙소 코드, 항목 중복)을 찾아 먼저 고쳤다 ([ADR-0027](0027-spec-violation-handling-criteria.md) 표에 추가)
- **사용자 판단** — 판정 후 값, 조기 갱신 + 인스턴스 안 합치기, Redis 장애 시 직접 호출, 실패는 캐시 안 함·매진은 캐시, 만료된 값은 내보내지 않음, 응답 뒤 쓰기, 모든 항목에 받은 시각, Reactive 클라이언트를 모두 추천안으로 정했다
