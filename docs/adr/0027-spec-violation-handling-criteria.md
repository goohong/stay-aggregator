# 0027. 규약과 다른 공급사 응답을 세 가지 질문으로 판정하기로 결정

이 ADR 은 [ADR-0024](0024-missing-night-as-zero-and-record.md) 와 [ADR-0025](0025-out-of-spec-inventory-dates.md) 를 대체한다.

## Context

연박 예약 가능 객실 수는 숙박일별 잔여 수의 최솟값으로 판정한다([ADR-0023](0023-multi-night-availability-minimum.md)).
공급사 스펙은 날짜별 재고가 체크인일부터 체크아웃 전날까지 온다고 정하고, `remainingRooms` 를 정수이자 "그날 예약 가능한 해당 타입 객실 수"로 정의한다.
0 이상이라고 명시하지는 않는다. 날짜가 빠지거나, 범위 밖 날짜·중복·음수가 오는 경우는 스펙이 다루지 않는다.

ADR-0024·0025 는 이런 경우를 값을 보정해(빠진 날·음수는 0, 중복은 작은 값, 범위 밖은 무시) 판정하고 사실을 남기기로 했다.
그 뒤 예약 불가 상품을 0 으로 노출하기로 하면서([ADR-0026](0026-expose-unbookable-as-zero.md)), 규약 위반이 고객에게 "매진"이라는 사실로 보이게 됐다.
또 매핑에 없는 객실 타입은 응답에서 빼기로 한 [ADR-0015](0015-exclude-unmapped-room-types.md) 와 처리 단위가 달랐고, 경우마다 심각도를 판단해 규칙을 정한 탓에 새 위반이 나오면 다시 판단해야 했다.

참고한 외부 문서

| 사실 | 원문 |
|---|---|
| 규정되지 않은 상황에서 복구 대신 오류를 내면 결함이 주목받는다. 상호운용 문제는 고칠 수 있는 쪽에 알려져야 하고, 시스템에 따라 덜 직접적인 수단을 써야 할 수 있다 | [RFC 9413 §5.1](https://www.rfc-editor.org/rfc/rfc9413.html#section-5.1): "Choosing to generate fatal errors for unspecified conditions instead of attempting error recovery can ensure that faults receive attention." / "Other systems might need to use less direct means of making errors known." |
| Booking.com 은 여러 업데이트 중 무효한 것이 있어도 요청 전체를 버리지 않고 오류를 알린다. 범위를 넘는 값은 보정하고 경고를 남긴다 | [B.XML availability](https://developers.booking.com/connectivity/docs/b_xml-availability#:~:text=at%20least%20one%20invalid%20update): "When processing a request containing multiple updates with at least one invalid update, the API returns a HTTP status 200 with error response." · [Values greater than 255](https://developers.booking.com/connectivity/docs/b_xml-availability#:~:text=Values%20greater%20than%20255%20are%20automatically%20reset%20to%20254) |
| Google Hotel Prices 는 무효한 RoomBundle 을 거부하고 그 요금만 판매 불가로 둔다 | [Feed Status 1073](https://developers.google.com/hotels/hotel-prices/dev-guide/feed-status-errors#:~:text=All%20%3CRoomBundle%3E%20values%20for%20this%20itinerary%20are%20invalid): "All <RoomBundle> values for this itinerary are invalid and have been rejected." |

두 곳은 데이터를 받아 보낸 쪽에 오류를 돌려줄 수 있는 위치이고, 우리는 공급사 응답을 받아 쓸 뿐 돌려줄 수단이 없다. 그래서 처리 단위만 참고한다.

## Options

- **(가) ADR-0024·0025 유지: 값을 보정하고 사실을 남긴다** — 판정 규칙이 가장 적다. 대신 0 노출과 겹쳐 규약 위반이 매진으로 보이고, 위반마다 심각도를 판단해야 한다.
- **(나) 규약과 다른 응답은 공급사 응답 전체를 실패로 본다** — 가장 엄격하다. 대신 정상 항목까지 버리고, 공급사가 늘 같은 위반을 보내면 모든 검색이 부분 실패가 된다. 다시 호출해도 결과가 같다.
- **(다) 세 가지 질문을 순서대로 물어 처리 단위를 정한다** ← AI 추천 — 새 위반도 같은 질문으로 분류되고 질문마다 테스트할 수 있다. 대신 항목을 격리해 남기는 경로가 새로 생긴다.

## Decision

**(다)** 를 택한다. 규약과 다른 응답을 받으면 아래 질문을 순서대로 묻고, 처음 "아니요"가 나오는 곳에서 처리한다.

| 순서 | 질문 | 아니요면 |
|---|---|---|
| 1 | 응답 전체를 규약대로 읽을 수 있는가 (HTTP 상태·resultCode 가 성공이고 본문 구조를 파싱할 수 있는가) | 공급사 실패. 부분 실패로 표시한다 |
| 2 | 위반된 데이터가 이번 요청의 출력값 계산에 쓰이는가 | 무시한다. 판정을 바꾸지 않고 기록만 한다 |
| 3 | 그 항목의 출력값을 규약에 맞는 데이터만으로 하나로 정할 수 있는가 | 그 항목만 응답에서 빼고 원본을 격리해 남긴다 |
| — | 모두 예 | 정상 처리한다. 규약과 달랐던 점이 있으면 기록한다 |

날짜별 재고에 적용한 결과

| 경우 | 결과 | 걸린 질문 |
|---|---|---|
| 요청하지 않은 날짜가 섞임 | 무시하고 기록 | 2 |
| 요청 숙박일 하나가 빠짐 | 그 객실 타입 제외, 원본 격리 | 3 (그날 값이 없다) |
| 같은 날짜가 다른 값으로 두 번 옴 | 그 객실 타입 제외, 원본 격리 | 3 (어느 값인지 모른다) |
| 같은 날짜가 같은 값으로 두 번 옴 | 그 값을 쓰고 기록 | 모두 예 |
| 잔여 수가 음수 | 그 객실 타입 제외, 원본 격리 | 3 |

음수를 규약에 맞지 않는 값으로 보는 것은 명시 규칙이 아니라, 필드가 객실 **수**로 정의돼 있다는 데서 끌어낸 판단이다.

**이유** — 오류인지는 같아도 처리 단위는 "그 위반 때문에 내보낼 값을 하나로 정할 수 없게 되는가"로 가를 수 있다.
그렇게 가르면 규약 위반을 매진 같은 사업 사실로 바꾸지 않고, 믿을 수 있는 이웃 항목은 버리지 않는다.
매핑에 없는 객실 타입을 뺀 ADR-0015 도 내부 식별자라는 출력값을 정할 수 없어서 뺀 것이라 같은 기준으로 설명된다.

## Consequences

**얻는 것**
- 규약 위반이 고객 응답에서 매진으로 보이지 않는다
- 새 종류의 위반도 세 질문으로 처리가 정해지고, 질문마다 테스트로 확인할 수 있다
- 요금 필드 등 다른 출력값의 위반에도 같은 질문을 쓸 수 있다
- 공급사 실패는 응답 전체를 읽을 수 없는 경우로 한정되어, 데이터 이상이 공급사 실패율에 섞이지 않는다

**잃는 것**
- 정규화 결과가 "사용"과 "격리" 두 갈래가 되고, 격리한 원본을 남기는 경로가 새로 필요하다
- 제외된 항목은 고객 응답에 보이지 않고 부분 실패로도 표시되지 않는다. 공급사가 모든 항목에 같은 위반을 보내면 그 공급사 결과가 사라지는데도 응답은 정상으로 보인다
- 질문 1 의 "본문 구조"와 질문 3 의 "항목"을 어디서 끊을지는 공급사 응답 DTO 설계에 달려 있다
- 음수 판단은 필드 정의에서 끌어낸 해석이다

**넘기는 것**
- 격리한 원본과 기록을 어떤 형태로 어디에 남기고 누가 알아챌지 (Q17·Q18)
- 공급사 상태를 성공·실패 두 값으로 둘지, 데이터 이상으로 결과가 줄어든 상태를 따로 표시할지 (Q25)
- 필수 필드가 빠진 항목을 파싱 단계에서 응답 전체 실패로 볼지 항목 실패로 볼지 (Q6)

## Discussion

- **AI 주장과 근거** — 빠진 날은 사용자 판단대로 0 으로 보고 사실을 남기기로 했고(ADR-0024), 나머지 세 경우도 같은 원칙으로 보정하자고 권했다(ADR-0025)
- **반박** — 엄격하게 보면 규격 외 응답은 에러 처리일 수도 있다. 다른 AI 의 독립 검토를 받은 뒤, 그 안도 결국 심각도를 주관적으로 나눈 것이니 더 객관적으로 서술할 수 있느냐는 지적이 이어졌다
- **검증 결과**
  - 독립 검토는 공급사 응답 전체 실패가 정상 항목까지 버리고 재시도로도 달라지지 않는다는 점을 들어, 객실 타입 단위 격리를 권했다
  - 같은 검토가 기존 ADR 의 오류를 짚었다. ADR-0025 가 스펙이 "0 이상의 정수"를 정한다고 쓴 것은 틀렸다. 스펙은 정수라고만 한다. 객실 타입 단위 선택지가 빠졌고, ADR-0024 가 ADR-0015 와 같은 방식이라고 쓴 것은 기록 형태를 넘긴 점만 같았다. 중복을 작은 값으로 보는 규칙에는 외부 선례가 없었다
  - 검토가 든 Google 의 중복 요소 규칙(Feed Status 1081)은 인원 요소에 대한 것이라 날짜 중복의 선례로 쓰지 않았다
  - 심각도 대신 "내보낼 값을 하나로 정할 수 있는가"라는 질문으로 바꾸자 경우마다 판단하지 않고 분류할 수 있었다
- **그래서 어떻게 바뀌었나** — ADR-0024·0025 를 이 ADR 로 대체했다

## Verification

재고 정규화 테스트에서 위 표의 다섯 경우가 각각 표의 결과로 처리되고, 공급사 실패로 집계되지 않는지. 테스트를 만들면 그 이름을 여기에 적는다.
