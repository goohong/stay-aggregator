# 0027. 스펙과 다른 공급사 응답을 세 가지 질문으로 판정하기로 결정

이 ADR 은 [ADR-0024](0024-missing-night-as-zero-and-record.md) 와 [ADR-0025](0025-out-of-spec-inventory-dates.md) 를 대체한다.

## Context

연박 예약 가능 객실 수는 숙박일별 잔여 수의 최솟값으로 판정한다([ADR-0023](0023-multi-night-availability-minimum.md)).
공급사 스펙은 날짜별 재고가 체크인일부터 체크아웃 전날까지 온다고 정하고, `remainingRooms` 를 정수이자 "그날 예약 가능한 해당 타입 객실 수"로 정의한다.
0 이상이라고 명시하지는 않는다. 날짜가 빠지거나, 범위 밖 날짜·중복·음수가 오는 경우는 스펙이 다루지 않는다.

ADR-0024·0025 는 이런 경우를 값을 보정해(빠진 날·음수는 0, 중복은 작은 값, 범위 밖은 무시) 판정하고 사실을 남기기로 했다.
그 뒤 예약 불가 상품을 0 으로 노출하기로 하면서([ADR-0026](0026-expose-unbookable-as-zero.md)), 스펙과 다른 응답이 고객에게 "매진"이라는 사실로 보이게 됐다.
또 매핑에 없는 객실 타입은 응답에서 빼기로 한 [ADR-0015](0015-exclude-unmapped-room-types.md) 와 처리 단위가 달랐고, 경우마다 심각도를 판단해 규칙을 정한 탓에 새로운 경우가 나오면 다시 판단해야 했다.

참고한 외부 문서

| 사실 | 원문 |
|---|---|
| 규정되지 않은 상황에서 복구 대신 오류를 내면 결함이 주목받는다. 상호운용 문제는 고칠 수 있는 쪽에 알려져야 하고, 시스템에 따라 덜 직접적인 수단을 써야 할 수 있다 | [RFC 9413 §5.1](https://www.rfc-editor.org/rfc/rfc9413.html#section-5.1): "Choosing to generate fatal errors for unspecified conditions instead of attempting error recovery can ensure that faults receive attention." / "Other systems might need to use less direct means of making errors known." |
| Booking.com 은 여러 업데이트 중 무효한 것이 있어도 요청 전체를 버리지 않고 오류를 알린다. 범위를 넘는 값은 보정하고 경고를 남긴다 | [B.XML availability](https://developers.booking.com/connectivity/docs/b_xml-availability#:~:text=at%20least%20one%20invalid%20update): "When processing a request containing multiple updates with at least one invalid update, the API returns a HTTP status 200 with error response." · [Values greater than 255](https://developers.booking.com/connectivity/docs/b_xml-availability#:~:text=Values%20greater%20than%20255%20are%20automatically%20reset%20to%20254) |
| Google Hotel Prices 는 무효한 RoomBundle 을 거부하고 그 요금만 판매 불가로 둔다 | [Feed Status 1073](https://developers.google.com/hotels/hotel-prices/dev-guide/feed-status-errors#:~:text=All%20%3CRoomBundle%3E%20values%20for%20this%20itinerary%20are%20invalid): "All <RoomBundle> values for this itinerary are invalid and have been rejected." |

두 곳은 데이터를 받아 보낸 쪽에 오류를 돌려줄 수 있는 위치이고, 우리는 공급사 응답을 받아 쓸 뿐 돌려줄 수단이 없다. 그래서 처리 단위만 참고한다.

## Options

- **(가) ADR-0024·0025 유지: 값을 보정하고 사실을 남긴다** — 판정 규칙이 가장 적다. 대신 0 노출과 겹쳐 스펙과 다른 응답이 매진으로 보이고, 경우마다 심각도를 판단해야 한다.
- **(나) 스펙과 다른 응답은 공급사 응답 전체를 실패로 본다** — 가장 엄격하다. 대신 정상 항목까지 버리고, 공급사가 늘 같은 방식으로 다르게 보내면 모든 검색이 부분 실패가 된다. 다시 호출해도 결과가 같다.
- **(다) 세 가지 질문을 순서대로 물어 처리 단위를 정한다** ← AI 추천 — 새로운 경우도 같은 질문으로 분류되고 질문마다 테스트할 수 있다. 대신 뺀 항목을 남기는 경로가 새로 생긴다.

## Decision

**(다)** 를 택한다. 스펙과 다른 응답을 받으면 아래 질문을 순서대로 묻고, 처음 "아니요"가 나오는 곳에서 처리한다.

| 순서 | 질문 | 아니요면 |
|---|---|---|
| 1 | 응답 전체를 스펙대로 읽을 수 있는가 (HTTP 상태·resultCode 가 성공이고 본문 구조를 파싱할 수 있는가) | **그 공급사의 응답 전체를 버리고, 검색 응답에 그 공급사를 실패로 표시한다.** 다른 공급사의 결과는 그대로 내보낸다 |
| 2 | 스펙과 다른 그 데이터가 이번 요청의 출력값 계산에 쓰이는가 | **그 데이터만 버리고 나머지로 계산한다.** 출력값은 그대로 두고, 무엇을 버렸는지 기록한다 |
| 3 | 그 항목의 출력값을 스펙에 맞는 데이터만으로 하나로 정할 수 있는가 | **그 항목을 검색 응답에서 빼고 무엇을 왜 뺐는지 기록한다.** 같은 응답의 다른 항목은 그대로 쓴다 |
| — | 모두 예 | **받은 값으로 정상 계산한다.** 스펙과 달랐던 점이 있으면 기록한다 |

여기서 "기록한다"는 지금 로그 한 줄까지를 뜻한다. 뺀 응답의 원본을 따로 보관하는 것은 아직 하지 않는다 ([ADR-0039](0039-catalog-sync-remaining.md) 의 "뺀 것을 지금 어디까지 남길지", 형태는 Q17·Q18).

**첫 질문에는 응답이 아예 오지 않은 경우도 넣는다.** 정한 시간 안에 오지 않은 것과 연결하지 못한 것이다.
"스펙대로 읽을 수 있는가"를 못 받은 경우까지 넓히는 것이고, 그래야 실패를 HTTP 로 알리는 공급사와 본문으로 알리는 공급사와
아무 말도 하지 않은 공급사가 consumer 에게 같은 신호로 보인다([ADR-0031](0031-supplier-adapter-boundaries.md)).
종류를 나누지는 않는다. 대신 **원인 예외를 `cause` 로 보존하고 그 클래스 이름을 로그 문장에 넣어**, 뒤에 지표를 만들 때 종류로 셀 수 있게 둔다(Q18).

날짜별 재고에 적용한 결과

| 경우 | 결과 | 걸린 질문 |
|---|---|---|
| 요청하지 않은 날짜가 섞임 | 그 날짜만 버리고 나머지 날짜로 계산한다. 버린 날짜를 기록한다 | 2 |
| 요청 숙박일 하나가 빠짐 | 그 객실 타입을 응답에서 빼고 빠진 날짜를 기록한다 | 3 (그날 값이 없다) |
| 같은 날짜가 다른 값으로 두 번 옴 | 그 객실 타입을 응답에서 빼고 두 값을 기록한다 | 3 (어느 값인지 모른다) |
| 같은 날짜가 같은 값으로 두 번 옴 | 그 값으로 계산하고 두 번 온 사실을 기록한다 | 모두 예 |
| 잔여 수가 음수 | 그 객실 타입을 응답에서 빼고 받은 값을 기록한다 | 3 |

음수를 스펙에 맞지 않는 값으로 보는 것은 명시 규칙이 아니라, 필드가 객실 **수**로 정의돼 있다는 데서 끌어낸 판단이다.

**이유** — 오류인지는 같아도 처리 단위는 "그 차이 때문에 내보낼 값을 하나로 정할 수 없게 되는가"로 가를 수 있다.
그렇게 가르면 스펙과 다른 응답을 매진 같은 사업 사실로 바꾸지 않고, 믿을 수 있는 이웃 항목은 버리지 않는다.
매핑에 없는 객실 타입을 뺀 ADR-0015 도 내부 식별자라는 출력값을 정할 수 없어서 뺀 것이라 같은 기준으로 설명된다.

## Consequences

**얻는 것**
- 스펙과 다른 응답이 고객 응답에서 매진으로 보이지 않는다
- 새로운 경우도 세 질문으로 처리가 정해지고, 질문마다 테스트로 확인할 수 있다
- 요금 필드처럼 다른 출력값에도 같은 질문을 쓸 수 있다
- 공급사 실패는 응답 전체를 읽을 수 없는 경우로 한정되어, 데이터 이상이 공급사 실패율에 섞이지 않는다

**잃는 것**
- 정규화 결과가 "쓸 것"과 "뺀 것" 두 갈래가 되고, 뺀 것을 남기는 경로가 새로 필요하다
- 제외된 항목은 고객 응답에 보이지 않고 부분 실패로도 표시되지 않는다. 공급사가 모든 항목을 같은 방식으로 다르게 보내면 그 공급사 결과가 사라지는데도 응답은 정상으로 보인다
- 질문 1 의 "본문 구조"와 질문 3 의 "항목"을 어디서 끊을지는 공급사 응답 DTO 설계에 달려 있다
- 음수 판단은 필드 정의에서 끌어낸 해석이다

**넘기는 것**
- 뺀 항목의 원본과 기록을 어떤 형태로 어디에 남기고 누가 알아챌지 (Q17·Q18). 요구사항이 선택 항목으로 둔 "격리"가 이 자리다
- 공급사 상태를 성공·실패 두 값으로 둘지, 데이터 이상으로 결과가 줄어든 상태를 따로 표시할지 (Q25)
- 필수 필드가 빠진 항목을 파싱 단계에서 응답 전체 실패로 볼지 항목 실패로 볼지 (Q6)

## Discussion

- **AI 주장과 근거** — 빠진 날은 사용자 판단대로 0 으로 보고 사실을 남기기로 했고(ADR-0024), 나머지 세 경우도 같은 원칙으로 보정하자고 권했다(ADR-0025)
- **반박** — 엄격하게 보면 규격 외 응답은 에러 처리일 수도 있다. 다른 AI 의 독립 검토를 받은 뒤, 그 안도 결국 심각도를 주관적으로 나눈 것이니 더 객관적으로 서술할 수 있느냐는 지적이 이어졌다
- **검증 결과**
  - 독립 검토는 공급사 응답 전체 실패가 정상 항목까지 버리고 재시도로도 달라지지 않는다는 점을 들어, 객실 타입 단위로 빼는 쪽을 권했다
  - 같은 검토가 기존 ADR 의 오류를 짚었다. ADR-0025 가 스펙이 "0 이상의 정수"를 정한다고 쓴 것은 틀렸다. 스펙은 정수라고만 한다. 객실 타입 단위 선택지가 빠졌고, ADR-0024 가 ADR-0015 와 같은 방식이라고 쓴 것은 기록 형태를 넘긴 점만 같았다. 중복을 작은 값으로 보는 규칙에는 외부 선례가 없었다
  - 검토가 든 Google 의 중복 요소 규칙(Feed Status 1081)은 인원 요소에 대한 것이라 날짜 중복의 선례로 쓰지 않았다
  - 심각도 대신 "내보낼 값을 하나로 정할 수 있는가"라는 질문으로 바꾸자 경우마다 판단하지 않고 분류할 수 있었다
- **그래서 어떻게 바뀌었나** — ADR-0024·0025 를 이 ADR 로 대체했다

## Verification

숙소 목록 쪽은 확인됐다.

첫 번째 질문(응답 전체를 스펙대로 읽을 수 있는가)에서 공급사마다 다른 실패 표현이 한 신호가 되는지
  → `SupplierCatalogAdapterTest.공급사 A 가 HTTP 실패를 주면 오류가 된다`,
    `SupplierCatalogAdapterTest.공급사 B 가 본문 결과 코드로 알린 실패도 같은 오류가 된다`,
    `SupplierCatalogAdapterTest.본문을 읽을 수 없으면 오류가 된다`

한 신호로 모으는 범위가 공급사와 만나는 구간까지이고, 응답을 우리 형태로 바꾸는 코드의 오류는 들어오지 않는지
  → `SupplierFailureTest.감싸기 위에서 난 오류는 공급사 실패가 된다`,
    `SupplierFailureTest.감싸기 아래에서 난 오류는 그대로 간다`,
    `SupplierFailureTest.원인 예외는 보존된다`

첫 질문 중 목록을 담는 필드가 있는지는 공급사마다 다르지 않아 정규화가 본다 (ADR-0041)
  → `CatalogNormalizerTest.숙소 목록을 담는 필드가 없으면 공급사 실패가 된다`

응답이 오지 않은 경우도 첫 질문의 "아니요"가 되는지, 그러면서 원인 종류가 로그에 남는지
  → `SupplierCatalogAdapterTest.공급사가 응답하지 않으면 정한 시간에 끊는다`,
    `SupplierCatalogAdapterTest.연결하지 못하면 오류가 된다`,
    `SupplierCatalogAdapterTest.본문을 읽을 수 없으면 오류가 된다`
    (세 건 모두 `assertKeepsCauseKind` 로 원인이 보존되고 그 클래스 이름이 메시지에 들어가는지 본다)

두 번째·세 번째 질문(항목 하나하나의 값을 쓸 수 있는가)
  → `CatalogNormalizerTest` 의 나머지 건과 `NormalizedHotelTest` (값 판정은 그 값을 담는 객체가 한다, ADR-0041)

재고 쪽은 검색을 구현할 때 확인한다. 위 표의 다섯 경우가 각각 표의 결과로 처리되고 공급사 실패로 집계되지 않는지 보고, 그 테스트 이름을 여기에 적는다.
