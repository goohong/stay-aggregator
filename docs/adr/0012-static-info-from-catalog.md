# 0012. 응답의 숙소·객실 타입 정적 정보는 숙소 목록 기준으로 저장해 사용

## Context

검색 응답에는 숙소명, 객실 타입명, 최대 수용 인원이 들어가야 한다. 이 세 값은 공급사의
숙소 목록 API 응답과 재고·요금 API 응답 양쪽에 모두 있다.

재고·요금 API 는 숙소 코드 목록으로 조회하고, 그 숙소의 객실 타입은 응답으로 받는다.
공급사는 요청 인원을 수용할 수 있는 객실 타입만 돌려준다. 숙소 목록은 드물게 바뀌고
재고·요금은 조회할 때마다 바뀐다. 이 성격 차이를 설계에 어떻게 반영했는지가 매핑에서
가장 중요한 판단이다.

공급사 상품마다 내부 식별자를 발급해 매핑에 저장하고, 목록을 다시 받아와도 유지한다
([ADR-0010](0010-keep-internal-id-on-merge.md), [ADR-0011](0011-internal-id-random-uuid.md)).
이번 결정은 응답의 세 값을 저장해 둔 목록 값에서 줄지, 매 조회 응답에서 줄지다.

## Options

- **(가) 숙소 목록 API 에서 받아 저장한 값을 쓴다** ← AI 추천 — 드물게 바뀌는 정보는 목록에서,
  매번 바뀌는 요금·재고만 조회에서 가져온다는 구분이 그대로 드러난다. 목록 API 와 조회 API 의
  표기가 달라도 응답이 일관되고, 조회 응답에 이름을 주지 않는 공급사도 붙일 수 있다. 병합할 때
  검색 없이 이름을 비교할 수 있고, 캐시를 둘 때 정적 정보와 요금·재고를 따로 다루기 쉽다.
  대신 목록을 다시 받아오기 전에 공급사가 값을 바꾸면 응답에 잠시 옛 값이 나간다.
- **(나) 매 조회 응답의 값을 쓴다** — 항상 공급사의 가장 최근 값이다. 대신 조회 응답에 이름이 없는
  공급사를 붙이면 응답을 채울 수 없고, 요청 언어에 따라 이름이 달라지는 공급사면 응답이 흔들린다.
- **(다) 저장값을 쓰되 조회 응답 값이 다르면 조회 값을 쓴다** — 안정성과 최신성을 둘 다 노린다.
  대신 둘이 다를 때의 규칙이 필요하고, 저장값을 그 자리에서 고치면 검색할 때마다 쓰기가 생긴다.

(가) 에 덧붙일 후보도 검토했다.

- **최대 수용 인원만 조회 값을 쓴다** — 공급사가 인원으로 객실 타입을 거른 기준과 응답의 값이 항상
  일치한다. 대신 "정적 정보는 목록 기준" 원칙에 필드 하나만 예외가 생긴다.
- **모르는 객실 타입이 조회에 나오면 그 자리에서 매핑을 만든다** — 새 객실 타입을 목록 갱신 전에도
  바로 응답에 넣는다. 대신 검색 중에 쓰기가 생기고, 동시 검색이 같은 객실 타입을 만나면 중복 발급을
  막아야 하며, 매핑의 출처가 숙소 목록이라는 원칙이 흐려진다.
- **조회 응답이 저장값과 어긋나면 목록 갱신을 앞당기는 신호를 남긴다** — 검색 중에는 쓰지 않고
  어긋남을 오래 방치하지 않는다. 목록을 언제 받아올지와 한 몸이라 그 결정에서 함께 정한다.

## Decision

**(가)** 를 택한다. 응답의 숙소명, 객실 타입명, 최대 수용 인원은 모두 숙소 목록 API 에서 받아
저장한 값을 쓴다. 덧붙일 후보는 채택하지 않는다.

**이유** — 매핑이 이 기능의 핵심인데, 최대 수용 인원 하나만 조회 값을 쓰면 원칙에 예외를 두는 것이 된다.
최대 수용 인원은 이름이나 요금보다 드물게 바뀐다.

## Consequences

**얻는 것**
- 응답의 정적 정보는 전부 숙소 목록 기준이라고 한 줄로 설명된다
- 조회 API 가 무엇을 주는지에 덜 묶여, 공급사가 늘어도 응답을 채우는 방식이 같다

**잃는 것 (알려진 한계)**
- 공급사가 숙소명이나 객실 타입명을 바꾸면 다음 목록 갱신까지 옛 이름이 나간다
- 공급사가 최대 수용 인원을 늘리면, 다음 목록 갱신까지 "최대 2명"으로 표시된 객실 타입이 성인 3명 검색
  결과에 나오는 모순이 생길 수 있다. 줄인 경우는 공급사가 그 객실 타입을 돌려주지 않아 드러나지 않는다
- 이미 매핑된 숙소에 공급사가 새 객실 타입을 추가하면, 목록 갱신 전까지 조회 응답에는 나오지만 내부
  식별자가 없어 검색 응답에 넣지 못한다. 이 경우를 조용히 뺄지 기록으로 남길지는 아직 정하지 않았다

**범위 밖으로 남기는 확장**
- 공급사가 콘텐츠 변경을 알려 오면 해당 숙소만 다시 가져와 저장값을 갱신하는 방식. 이번 공급사 스펙에는
  공급사가 알림을 보내는 API 가 없어 구현하지 않는다. 알림이 생겨도 누락될 수 있어, 주기적으로 불러오는
  방식이 완전히 없어지지는 않는다

## Discussion

- **AI 주장과 근거** — (가) 에 최대 수용 인원만 조회 값을 쓰는 예외를 덧붙이자고 권했다. 공급사가 인원으로
  거른 기준과 보여주는 값이 달라지는 모순을 막기 위해서였다
- **반박** — 매핑을 핵심으로 본다면서 필드 하나에 예외를 두는 것 같다. 최대 수용 인원은 자주 바뀌지 않는다.
  새로 바뀐 정보는 공급사가 원할 때 우리에게 갱신을 요청하는 방식을 나중에 구현하면 된다
- **검증 결과** — 그 모순은 최대 인원이 늘어날 때만, 다음 목록 갱신까지만 생긴다. 원칙을 하나로 두는 편이
  설명과 유지가 쉽다. 공급사가 먼저 알려 오는 방식은 실무에 있지만 이번 스펙의 공급사 API 에는 없다
- **그래서 어떻게 바뀌었나** — 예외 없이 (가) 로 정하고, 모순은 알려진 한계로, 공급사 알림 방식은 범위 밖
  확장으로 기록했다

## Verification

아직 구현 전이다. 검색을 구현할 때 "공급사 조회 응답의 이름·최대 수용 인원이 저장값과 달라도 응답은
저장값을 쓰는지" 확인하는 테스트를 추가하고 이 절에 이름을 적는다.
