# 0049. 공급사 식별자는 어댑터만 갖고 응답 공통 형태에는 싣지 않기로 결정

## Context

[ADR-0031](0031-supplier-adapter-boundaries.md) 이 "공급사 식별자를 공통 형태에도 실을지"를 재고·요금 공통 형태를 만드는 검색 단위로 넘겼다. 그 단위다.

지금 공급사 식별자 `"a"` 는 어댑터의 상수 하나에서 나와 **두 통로**로 흐른다.

| 통로 | 어디 | 누가 읽나 |
|---|---|---|
| ① 어댑터 속성 `CatalogAdapter.supplierId` | `sync(adapter)` 안 | 성공·실패 로그와 예외 메시지 3곳 |
| ② 응답 안 `FetchedCatalog.supplierId` | 어댑터 → 정규화 → `NormalizedCatalog` → 저장소 | DB `supplier` 컬럼, `missing_since` 표시 범위, 예외 메시지 |

실제 일을 하는 값은 ② 다. 저장소는 `(supplier, supplier_hotel_code)` 로 행을 찾고 `where supplier = :supplier` 로 그 공급사 행만 `missing_since` 를 표시한다.
내부 식별자는 그 행을 찾은 **결과**로 나오므로 공급사 식별자를 대신할 수 없다.

① 이 따로 있는 이유는 **응답이 오지 않았을 때**다. 타임아웃·장애면 응답 객체가 없어 어느 공급사가 실패했는지를 어댑터만 안다.
검색에서는 이것이 로그가 아니라 응답 데이터가 된다 ([ADR-0046](0046-supplier-status-in-search-response.md) 의 공급사별 상태).

정규화(`CatalogNormalizer`)는 ② 를 입력에서 출력으로 **옮기기만** 한다. 정규화 규칙은 공급사 공통이라 공급사가 누군지 알 필요가 없는데, 값을 실어 나르느라 알고 있다.

## Options

- **(가) 응답 공통 형태에서 뺀다. 어댑터가 갖고 consumer 가 어댑터 값을 넘긴다** ← 채택 —
  통로가 하나가 되고 정규화가 공급사를 모르게 된다. 대신 응답 객체만 들고 있으면 출처를 모른다
- **(나) 지금대로 둘 다 두고 재고 응답에도 싣는다** — 응답 객체가 어디로 가든 출처를 안다.
  대신 같은 상수가 두 통로로 분리되어 나가고, 한 함수 안에서 저장할 때는 ②, 로그 찍을 때는 ① 을 쓴다
- **(다) 어댑터 속성을 빼고 응답에만 싣는다** — 응답이 오지 않으면 어느 공급사인지 알 수 없어 실패 로그와 검색의 공급사별 상태를 만들 수 없다

## Decision

- **공급사 식별자는 어댑터가 갖는다.** `CatalogAdapter.supplierId` 와 앞으로 만들 재고·요금 인터페이스의 같은 속성이다
- **응답 공통 형태(`Fetched…`)에는 싣지 않는다.** `FetchedCatalog.supplierId` 를 지우고, 재고·요금 응답 형태도 공급사를 모르게 만든다
- **정규화의 입력과 출력에서도 뺀다.** `NormalizedCatalog.supplierId` 를 지운다
- consumer 가 어댑터 값을 저장소에 넘긴다. `repository.applyCatalog(adapter.supplierId, …)`
- 정규화 안의 예외 메시지에 공급사 이름이 필요하면 consumer 가 잡아서 붙인다. 정규화는 공급사를 모른다

**이유**

- 같은 값이 두 통로로 흐를 이유가 없다. 응답이 어댑터 손을 떠나 혼자 돌아다니는 곳이 지금 코드에 없다. 항상 `sync(adapter)` 안에서 어댑터와 함께 있다
- 정규화가 공급사를 모른다는 것이 타입으로 보인다. ADR-0031 이 말한 "공통 규칙은 공급사를 구분하지 않는다"와 일관된다
- 가짜 어댑터를 만들 때 식별자와 응답을 맞출 일이 없어진다. 지금 통합 테스트는 응답에서 식별자를 꺼내 어댑터에 다시 넣는 헬퍼로 이것을 피하고 있다

## Consequences

**얻는 것**
- 공급사 식별자의 통로가 하나다
- `Fetched…`·`Normalized…` 가 공급사를 모르는 순수 데이터가 된다
- 재고·요금 인터페이스를 같은 구조로 만들 기준이 생긴다

**잃는 것**
- 응답 객체를 여러 공급사 것을 한 목록에 모으는 곳이 생기면 (어댑터, 응답) 쌍으로 들고 다녀야 한다. 검색에서 그런 곳이 생긴다
- 목록 동기화의 파일 다섯(공통 형태, 두 어댑터, 정규화, 서비스)과 테스트를 고친다

**넘기는 것**
- 없음. ADR-0031 이 넘긴 항목은 이것으로 닫는다

## Discussion

- **AI 주장과 근거 (1차)** — (가)를 권하면서 근거로 "새 공급사가 식별자를 네 자리에 적는다"와 "가짜 어댑터를 손으로 맞춘다"를 들었다
- **반박 (1차)** — 사용자가 "어댑터에 한 번만 넣으면 흐름대로 알아서 전달되는 거 아닌가? 왜 손으로 맞춰야 한다는 거지" 라고 물었다
- **검증 결과 (1차)** — 사용자가 맞다. 운영 코드에서 값을 적는 곳은 상수 하나이고 나머지는 참조다. AI 가 "참조하는 줄 수"를 "적는 자리 수"로 말했다.
  손으로 맞추는 것은 테스트의 가짜 어댑터뿐이고 그마저 헬퍼로 해결돼 있었다. AI 가 (나)로 추천을 바꿨다
- **반박 (2차)** — 사용자가 "supplierId 가 있어야 이후 흐름이 진행되는 거지? 로깅만을 위한 코드는 필요성을 검토해 봐야 할 것 같다"고 했고,
  이어서 "수정이 대가인 건 말이 안 된다. 결정이 맞는지만 보면 된다. 어디서 어딜 호출하고 어떻게 전달되는지 한 흐름으로 정리해 달라"고 했다
- **검증 결과 (2차)** — 흐름을 한 줄로 그리자 두 가지가 드러났다. 같은 함수 안에서 저장은 ②, 로그는 ① 을 쓴다는 것, 그리고 정규화가 값을 옮기기만 한다는 것.
  AI 가 (나)의 유일한 근거로 든 "수정 범위"는 결정의 근거가 아니었다. 그것을 빼면 (가)가 더 나은 코드다
- **그래서 어떻게 바뀌었나** — (가)로 정했다. AI 의 추천이 (가) → (나) → (가) 로 두 번 바뀌었는데, 두 번 다 근거를 잘못 세운 것이 원인이다.
  처음은 "적는 자리 수"를 부풀렸고, 두 번째는 수정량을 근거에 넣었다
- **말** — 이 논의에서 AI 가 `missing_since` 를 "사라짐"이라고 불러 사용자가 헷갈렸다. [용어](../glossary.md) 가 컬럼 이름 그대로 부르라고 정해 둔 것을 어겼다

## Verification

응답 공통 형태와 정규화 결과에 공급사 식별자가 없는지
  → `FetchedCatalog`·`NormalizedCatalog` 에 `supplierId` 필드가 없다

consumer 가 어댑터 값을 저장소에 넘기는지
  → `CatalogSyncService.sync` 의 `repository.applyCatalog(adapter.supplierId, …)`

가짜 어댑터가 식별자와 응답을 따로 맞추지 않는지
  → `CatalogSyncIntegrationTest` 에서 `FakeCatalogAdapter` 를 만드는 곳

재고·요금 인터페이스가 같은 구조인지
  → `FetchedAvailability` 에 `supplierId` 필드가 없고 `AvailabilityAdapter.supplierId` 만 있다
