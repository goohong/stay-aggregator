# 0054. 제외한 항목은 문제가 된 값 하나로만 종류를 나누기로 결정

## Context

요구사항의 선택 항목인 "정규화 실패 데이터 격리"를 하기로 했다. 변환하지 못한 것을 버리지 않고 남겨 나중에 분석할 수 있게 하는 일이다.

남기는 방식을 조사해 보니 ([격리 방식 조사](../research/failed-data-quarantine.md)) 같은 문제를 매번 새 행으로 쌓지 않는다.
**같은 문제는 한 기록으로 묶고 횟수를 센다.**
Sentry 는 "Events with the same fingerprint are grouped together into an issue." 라고 적는다.
같은 잘못된 값이 검색마다 와도 기록이 계속 늘지 않게 하려는 것이다.

묶으려면 무엇이 같은 문제인지 정하는 기준이 있어야 한다. 지금 코드의 제외 사유는 문장이고, 그 안에 값이 섞여 있다.

```
"숙박일 2026-10-06 의 재고가 없다"
"숙박일 2026-10-07 의 재고가 없다"
```

문장으로 묶으면 같은 문제가 날짜 수만큼 따로 쌓인다. 그래서 사유를 종류로 나눠야 한다 (Q17 의 "어떤 종류로 나눌지").

지금 코드가 낼 수 있는 제외 사유를 전부 모으면 문제의 모양은 넷이다. 값이 없다, 범위 밖이다, 둘이 와서 하나로 못 정한다, 매핑에 없다.
문제가 된 값은 숙소 코드, 숙소명, 객실 타입 코드, 객실 타입명, 최대 수용 인원, 재고, 요금, 통화, 판매 조건, 매핑이다.

## Options

- **(가) 값과 모양을 섞어 한 축으로 촘촘하게 둔다** (`INVENTORY_MISSING`, `RATE_NEGATIVE` 등 17개 안팎) — 가장 구체적이다.
  대신 값이 하나 늘 때마다 종류가 여러 개씩 늘어난다
- **(나) 값과 모양을 두 축으로 따로 둔다** — 목록 15개로 50가지를 나타낸다. 같은 값에서 난 서로 다른 문제가 따로 묶인다.
  대신 모든 제외 지점에 모양을 매겨야 하고, 모양만으로 모아 볼 쓸 곳은 확인되지 않았다
- **(다) 문제가 된 값 하나로만 나눈다** ← 채택 — 가장 적게 정한다. 운영자가 할 일("그 공급사에 그 값을 확인해 달라")에 맞는다.
  대신 같은 값에서 서로 다른 문제가 번갈아 오면 한 기록으로 합쳐진다
- **(라) 모양 하나로만 나눈다** — 가장 단순하다. 대신 재고가 없는 건지 요금이 없는 건지를 종류로 알 수 없다

## Decision

- **제외한 항목의 종류는 문제가 된 값 하나다.** 모양(없다, 범위 밖, 하나로 못 정함)은 종류로 두지 않는다
- **같은 문제로 묶는 기준은 공급사, 숙소 코드, 객실 타입 코드, 문제가 된 값이다**
- 묶은 기록마다 **횟수, 처음 본 시각, 마지막 시각, 마지막 사유 문장, 마지막 원본**을 둔다.
  모양은 마지막 사유 문장에 들어 있어 열어 보면 보인다
- 값 하나에 걸리지 않는 구조 문제(예: 팔 수 있는 객실 타입이 없다)는 값 목록에 `구조` 를 하나 두어 담는다
- 매핑에 없어 뺀 것도 값 목록의 `매핑` 으로 담는다. 응답 건수에서 빼는 규칙은 그대로다 ([ADR-0046](0046-supplier-status-in-search-response.md))

**이유**

- **모양을 따로 둘 근거가 없었다.** 모양만으로 모아 보는 일("값이 없는 문제가 몇 건인가")을 보고 운영자가 할 일이 떠오르지 않는다.
  운영자는 결국 "공급사 A 의 재고 데이터가 깨졌다"를 보고 그 공급사에 연락한다
- 같은 값에서 난 다른 문제가 합쳐져도 **할 일이 같다.** 재고가 빠졌든 음수로 왔든 "재고 데이터를 확인해 달라"다
- 쓸 근거가 없는 칼럼을 만들지 않는다. 필요해지면 칼럼 하나를 더하면 되고, 이미 쌓인 기록은 사유 문장으로 모양을 가를 수 있다

## Consequences

**얻는 것**
- 정할 목록이 값 하나라 짧고, 제외 지점마다 매길 것이 하나다
- 같은 문제가 검색마다 와도 기록은 그 문제 하나로 늘지 않는다
- 기록의 행 수가 매핑 크기(숙소 × 객실 타입 × 값 종류)를 넘지 않는다

**잃는 것**
- **같은 값에서 서로 다른 문제가 번갈아 오면 한 기록으로 합쳐지고 마지막 문제만 보인다.** 횟수도 더해진다
- 모양별로 모아 보려면 사유 문장을 읽어야 한다

**다시 볼 것**
- 모양별 집계가 필요한 쓸 곳이 생기면 (예: 지표에서 "범위 밖" 만 따로 경보) 모양 칼럼을 더한다 (Q18)
- 이름 표기가 달라 생기는 어긋남(Q17 의 앞부분)은 이 결정이 다루지 않는다. 그것은 제외가 아니라 경고라 성격이 다르다

## Discussion

- **AI 주장과 근거** — 처음에는 (나)를 권했다. 근거로 "목록 15개로 50가지를 나타낸다"를 들었다
- **반박** — 사용자가 물었다. "값만 저장하는 건 안 좋은 설계인가? 모양을 두어서 그 칼럼만으로 모아 보기 위함이야?"
- **검증 결과** — 모양 칼럼이 하는 일을 따져 보니 둘뿐이었다. 모양만으로 모아 보기, 같은 값에서 난 다른 문제를 따로 묶기.
  앞의 것은 쓸 곳이 확인되지 않았다. 뒤의 것은 실제 차이지만 운영자가 할 일을 바꾸지 않고, 마지막 사유 문장으로 보인다.
  **AI 가 든 근거는 표현할 수 있는 경우의 수였지, 그만큼 나눌 필요가 있다는 근거가 아니었다**
- **그래서 어떻게 바뀌었나** — 추천을 (다)로 바꿨고 사용자가 (다)로 정했다

## Verification

같은 값의 문제가 한 기록으로 묶이고, 날짜가 다른 같은 문제도 묶이며, 마지막 사유와 원본이 바뀌는지
  → `QuarantineIntegrationTest.같은 문제가 여러 번 오면 한 행에 횟수가 늘고 마지막 사유와 원본이 바뀐다`

값이 다르면 다른 기록인지
  → `QuarantineIntegrationTest.문제가 된 값이 다르면 다른 행이다`

값은 어디서 붙나
  → 검색: `AvailabilityNormalizer` 가 판정 단계(`step`)마다 붙인다. 목록: `CatalogNormalizer` 가 값 객체가 거부하며 알린 필드에서 정한다 ([ADR-0067](0067-rejection-carries-field.md))
