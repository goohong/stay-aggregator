# 0053. 통화가 다른 상품을 한 응답에 함께 내보내되 환산하지 않기로 결정

## Context

요구사항의 선택 항목에 "서로 다른 통화의 상품을 함께 노출할 때의 설계"가 있다.

[ADR-0042](0042-rate-as-tax-included-total.md) 가 절반을 이미 정했다.

> **통화는 응답에 온 값을 그대로 싣고 변환하지 않는다.** 서로 다른 통화를 함께 노출할 때의 처리는 요구사항의 선택 항목이라 하지 않는다

그때 미룬 나머지를 여기서 본다.

확인한 사실

| 사실 | 어디서 |
|---|---|
| 통화는 ISO 4217 코드로 오고 `KRW`·`USD` 가 예시로 들려 있다 | 공급사 스펙의 필드 사전 |
| 금액은 "통화의 최소 단위 정수"다. 원은 원 단위이고 소수점이 없다 | 같은 곳 |
| 통화는 **항목 단위**로 온다. 공급사 A 는 날짜별 금액을 주지만 통화는 항목에 하나다 | 두 공급사의 재고·요금 응답 |
| 정렬과 페이징은 범위 밖이다. 최저가 정렬을 할 필요가 없다 | 요구사항의 비범위 |
| 우리 코드는 통화를 그대로 들고 다닌다. 값 객체가 통화 없는 금액을 막고, 통화가 다른 금액을 더하지 못하게 막는다 | `Money` (`app/src/main/kotlin/com/stayaggregator/domain/Money.kt`) |

**지금 구조에서 이미 통화가 섞여 나갈 수 있다.** 공급사 A 가 원으로, B 가 달러로 주면 한 응답의 항목마다 통화가 다르다.
막는 곳이 없고, 막을 이유도 아직 없었다.

## Options

- **(가) 섞여 나가게 두고 항목마다 통화를 싣는다. 환산하지 않는다** ← 채택 — 받은 값을 그대로 전한다.
  대신 받는 쪽이 통화를 항목마다 확인해야 하고, 값끼리 비교할 수 없다
- **(나) 서버가 하나의 통화로 환산해서 내보낸다** — 받는 쪽이 비교할 수 있다.
  대신 **환율을 우리가 정해야 한다.** 어느 출처의, 몇 시 값인지, 수수료를 얹을지가 모두 우리 결정이 되고,
  그 값이 응답에서는 공급사가 준 값과 구분되지 않는다
- **(다) 한 응답에는 한 통화만 나가게 거른다** — 응답이 단순하다.
  대신 통화가 다르다는 이유로 팔 수 있는 상품을 감춘다. 무엇을 남길지도 우리가 정해야 한다

## Decision

- **통화가 다른 상품을 한 응답에 함께 내보낸다.** 거르지 않는다
- **항목마다 통화를 싣는다.** 지금 `rate.currency` 가 그것이다
- **서버는 환산하지 않는다** (ADR-0042 를 이어받는다)
- **응답 수준에 "이 응답에 든 통화 목록" 같은 필드를 따로 두지 않는다.** 항목마다 있으므로 받는 쪽이 모으면 된다
- **금액은 통화가 같을 때만 더할 수 있다.** 값 객체가 막는다

**나중에 환산이 필요해지면** (정렬·최저가·예산 필터 같은 기능이 생기면) 이렇게 한다. 지금은 하지 않는다.

- 환산값을 **원래 값 대신 넣지 않는다.** 원래 통화와 금액을 그대로 두고 환산값을 따로 붙인다
- 환산값에는 **환율·기준 시각·출처**를 함께 싣는다. 그래야 받는 쪽이 그것이 추정값임을 안다
- 환율은 우리가 만들지 않고 **환율을 주는 곳에서 받는다**

**이유**

- 환율은 우리가 아는 값이 아니다. 출처·시각·수수료를 우리가 고르면 그 선택이 응답에서는 사실처럼 보인다.
  이것은 [README 에 적은 원칙](../../README.md)과 같다 — **추정한 값을 사실처럼 내보내지 않는다**
- 비교가 필요한 기능(정렬·최저가)이 지금 범위 밖이다. 비교할 일이 없는데 비교하려고 환산하는 것은 앞선 결정이다
- 통화가 다르다고 상품을 감추면 팔 수 있는 것을 못 팔게 된다. 어느 통화를 남길지도 근거 없는 선택이다
- 통화 목록을 응답 수준에 따로 두는 것은 항목에 있는 값을 한 번 더 적는 것이다. 한쪽이 바뀌면 다른 쪽이 틀린 말이 된다

## Consequences

**얻는 것**
- 받는 쪽이 공급사가 준 금액과 통화를 그대로 본다. 우리가 손댄 값이 섞이지 않는다
- 통화가 달라도 상품이 사라지지 않는다
- 통화가 다른 금액을 실수로 더하는 일이 값 객체에서 막힌다

**잃는 것**
- **받는 쪽이 값끼리 비교할 수 없다.** 원 100,000 과 달러 80 중 어느 쪽이 싼지 응답만으로는 모른다
- 화면이 통화를 섞어 보여주게 되고, 그것을 어떻게 보여줄지는 화면의 몫이다
- 한 응답에 통화가 몇 가지 들었는지 알려면 받는 쪽이 항목을 훑어야 한다

**다시 볼 것**
- 정렬·최저가·예산 필터 중 하나라도 필요해지면 환산이 필요하다. 그때 위에 적은 방식(원래 값을 두고 환산값을 따로, 환율·시각·출처와 함께)으로 한다
- 소수점을 쓰는 통화가 오면 금액의 최소 단위 정수 가정을 다시 본다 (ADR-0042 가 이미 넘긴 것)

## Discussion

- **AI 주장과 근거** — (가)를 권했다. 근거는 환율이 우리가 아는 값이 아니라는 것과, 비교가 필요한 기능이 범위 밖이라는 것이다
- **사용자 판단** — 선택 항목 중 이것을 하기로 골랐다
- **AI 가 확인한 것** — 지금 코드가 이미 통화를 섞어 내보낼 수 있고 막는 곳이 없다는 것.
  즉 이 결정은 동작을 바꾸는 것이 아니라 **이미 그런 이유를 적고, 나중에 어떻게 할지를 정해 두는 것**이다

## Verification

통화가 다른 금액을 더할 수 없는지
  → `MoneyTest.통화가 다르면 더할 수 없다`

통화 없는 금액을 만들 수 없는지
  → `MoneyTest.통화가 비어 있으면 만들 수 없다`

응답의 항목마다 통화가 실리는지
  → `SearchControllerTest.응답에 요구된 최소 정보와 공급사별 상태가 실린다` 의 `roomTypes[0].rate.currency`

환산하는 코드가 없는지
  → `grep -rn "currency" app/src/main/kotlin` 에 환율·환산과 관련된 줄이 없다. 받은 값을 그대로 옮기는 줄만 있다 (2026-09-17 확인)
