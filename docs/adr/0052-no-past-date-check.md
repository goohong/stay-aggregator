# 0052. 체크인일이 지난 날짜인지는 검사하지 않기로 결정

## Context

[ADR-0043](0043-stay-period-value-object.md) 이 숙박 구간 값 객체를 만들면서 이것을 넘겼다.

> 체크인일이 지난 날짜이거나 너무 먼 미래일 때 어떻게 볼지. 이 값 객체는 두 날짜의 앞뒤만 본다.

[ADR-0048](0048-guest-count-invariants.md) 에서 한국 밖 숙소도 다룰 수 있다는 것을 전제로 삼으면서 이 질문이 무거워졌다 (Q28).
서버가 자정을 넘긴 시점에 현지로는 아직 어제인 숙소가 생긴다. "지난 날짜"가 어디 기준인지가 정해져야 검사할 수 있다.

우리가 가진 것과 없는 것

| | |
|---|---|
| 매핑에 있는 것 | 공급사 코드, 내부 식별자, 이름, 최대 수용 인원 |
| **없는 것** | **숙소의 위치나 시간대.** 공급사 목록 API 가 주지 않는다 |
| 지난 날짜로 검색하면 | 공급사가 그 조건의 재고를 주지 않는다. 결과가 비어서 온다 |

## Options

- **(가) 검사하지 않는다** ← 채택 — 어느 기준을 쓸지 정하지 않아도 된다. 대신 명백히 잘못된 요청도 공급사까지 나간다
- **(나) 서버 시간대로 본다** — 단순하고 대부분의 잘못된 요청을 잡는다.
  대신 서버가 자정을 넘긴 시점에 현지로는 아직 어제인 숙소를 막는다. **합법인 요청을 우리가 막는 것**이다
- **(다) 가장 이른 시간대로 본다 (UTC-12)** — 지구 어디서도 아직 오지 않은 날짜만 막아 합법인 요청을 막지 않는다.
  대신 거의 아무것도 못 걸러 검사하는 의미가 옅다

## Decision

- **체크인일이 지난 날짜인지 검사하지 않는다.** 숙박 구간 값 객체는 두 날짜의 앞뒤만 본다 (ADR-0043)
- 숙박 일수의 상한도 두지 않는다. 공급사 스펙에 상한이 없다

**이유**

- **"오늘"의 기준을 정할 근거가 없다.** 숙소의 시간대를 우리가 모른다. 매핑에 없고 공급사가 주지 않는다.
  서버 기준으로 정하면 합법인 요청을 막게 되고, 가장 이른 시간대로 정하면 거의 아무것도 못 막는다
- 모르는 것에 규칙을 만들지 않는다 ([ADR-0048](0048-guest-count-invariants.md) 과 같은 원칙이다)
- 지난 날짜로 검색해도 공급사가 빈 결과를 준다. 잘못된 요청이 조용히 틀린 값을 만들지는 않는다

## Consequences

**얻는 것**
- 합법인 요청을 막지 않는다
- 검사 기준을 정하지 않아도 되고, 그 기준이 틀렸을 때 생길 문제가 없다

**잃는 것**
- **명백히 잘못된 요청도 공급사까지 나간다.** 1년 전 날짜로 검색해도 공급사를 부른다. 그만큼 공급사에 쓸모없는 호출이 간다
- 고객은 빈 결과를 받고 왜 비었는지 모른다. 응답이 "지난 날짜입니다"라고 말해 주지 않는다

**다시 볼 것**
- 숙소의 시간대나 위치를 알게 되면 (공급사가 주거나 우리가 저장하게 되면) 그때 현지 기준으로 검사할 수 있다
- 쓸모없는 호출이 실제로 문제가 되면 (공급사 호출 한도에 걸리는 등) 그때 가장 이른 시간대 기준이라도 두는 것을 본다

## Discussion

- **AI 주장과 근거** — 세 선택지를 내놓고 (가)를 권했다. 근거는 숙소 시간대를 모른다는 것이다
- **사용자 판단** — (가)로 정했다
- 반박은 없었다
