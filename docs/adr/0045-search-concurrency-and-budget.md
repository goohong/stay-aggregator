# 0045. 재고·요금 호출을 50개씩 나누고 동시 실행 수와 검색 시간 한계를 두기로 결정

## Context

검색 한 건이 들어오면 매핑에서 숙소 코드를 꺼내 공급사별로 묶어 재고·요금 API 를 부른다.
그 호출을 몇 개씩, 몇 개를 동시에, 얼마나 기다릴지가 정해지지 않았다.

확인한 사실

| 사실 | 근거 |
|---|---|
| 재고·요금 API 는 한 번에 숙소 코드 **50개**까지 받고, **초과하면 오류**다. 공급사 A 는 HTTP 400 `TOO_MANY_HOTEL_CODES`, B 는 HTTP 200 + `E400` 으로 거절한다 | 공급사 스펙의 본문과 오류 표 |
| 예시 데이터는 이 한계에 걸리지 않는다. 숙소가 수천 개로 늘 때 어떻게 할지를 설계 문서에 남기라고 한다 | 같은 곳 |
| 두 공급사 모두 **호출 한도 초과** 오류가 따로 있다 (A 는 429, B 는 `E429`). 한도 수치는 스펙에 없다 | 오류 표 |
| WebClient 의 기본 커넥션 풀은 **프로세서 수의 두 배, 최소 16** 이다. 풀이 차면 대기 큐에 들어가 기본 **45초**를 기다린다 | [Reactor Netty `ConnectionProvider`](https://projectreactor.io/docs/netty/release/api/reactor/netty/resources/ConnectionProvider.html) 의 `DEFAULT_POOL_MAX_CONNECTIONS` ("Fallback to 2 * available number of processors (but with a minimum value of 16)"), [HttpClient Timeout](https://github.com/reactor/reactor-netty/blob/main/docs/modules/ROOT/pages/http-client.adoc) ("Default: 45s") |
| DB 커넥션 풀은 HikariCP 기본 **10** 이다 | [ADR-0021](0021-block-on-virtual-threads.md) 에 기록 |
| 동시 호출 수는 `Flux.flatMap(mapper, concurrency)` 의 인자로 제한한다 | [ADR-0009](0009-reactor-over-coroutines.md) |

숙소가 3,000개면 공급사당 60회, 두 공급사면 120회다. 제한 없이 모두 띄우면 기본 풀(최소 16)을 넘어
100회 넘는 호출이 대기 큐에서 최대 45초를 기다린다. 검색 한 건이 그만큼 늘어진다.

## Options

동시 실행 수와 시간 한계
- **(가) 동시 실행 수와 검색 전체 시간 한계만 정하고 풀 크기는 기본값을 쓴다** ← 채택 — 지금 만질 근거가 있는 것만 정한다. 대신 실제 규모에서 기본 풀이 맞는지 확인하지 못한다
- **(나) 풀 크기까지 명시한다** — 대신 측정 없이 숫자를 정하게 된다. 타임아웃과 달리 외부 기본값 같은 근거조차 없다
- **(다) 검색 구현 뒤로 넘긴다** — 대신 `concurrency` 인자에 넣을 값이 당장 필요해, 넘기면 구현하며 임의로 정하게 된다

Mock 의 숙소 코드 수 검사
- **(ㄱ) Mock 이 숙소 코드를 받아 50개를 넘으면 공급사처럼 오류를 준다** ← 채택 — 나눠 부르는 것이 실제로 되는지 테스트가 확인한다. 대신 Mock 코드가 는다
- **(ㄴ) 그대로 둔다** — Mock 이 가볍다. 대신 나누기가 문서에만 남고, 잘못 구현해도 테스트가 통과한다

## Decision

- **대상 숙소 코드를 공급사별로 모아 50개 이하의 묶음으로 나눠 부른다.** 이것은 우리 판단이 아니라 공급사가 거절하는 제약이다
- **묶음 호출의 동시 실행 수를 제한한다.** `flatMap` 의 `concurrency` 인자로 준다.
  값은 **WebClient 기본 풀 크기를 넘지 않게** 잡는다. 시작값은 공급사당 4 로 둔다
- **검색 한 건 전체에 시간 한계를 둔다.** 그 안에 끝내지 못한 공급사는 부분 실패로 내보내고 나머지 결과로 응답한다.
  개별 호출 타임아웃과 별개다. 목록 동기화의 30초([ADR-0039](0039-catalog-sync-remaining.md))는 배경 작업 값이라 검색에 쓰지 않는다
- **커넥션 풀 크기는 기본값을 쓴다.** WebClient 도 DB 도 지금 만질 근거가 없다
- **Mock 이 숙소 코드 수를 검사해 50개를 넘으면 공급사처럼 오류를 준다.** A 는 HTTP 400 과 그 오류 이름으로, B 는 HTTP 200 과 본문 코드로 각자 모양대로 거절한다

**이유**

- 50개는 지키지 않으면 그 호출이 통째로 실패하고, 실패 모양이 공급사마다 달라 부분 실패 처리까지 번진다
- 제한 없이 띄우면 기본 풀을 넘어 대기 큐에서 기다린다. 그 기다림은 타임아웃 바깥이라 우리가 건 한계로 끊이지 않는다
- 개별 호출만 끊으면 호출이 수십 번일 때 검색 한 건이 그만큼 길어진다. 고객이 기다리는 요청이므로 전체에도 한계가 있어야 한다
- 풀 크기는 측정이 있어야 정할 수 있다. 지금 Mock 은 1~2ms 로 답하고 숙소가 셋이라 어떤 값을 넣어도 차이가 보이지 않는다

## Consequences

**얻는 것**
- 숙소가 늘어도 공급사가 거절하지 않는다
- 느린 공급사 하나가 검색 전체를 끌지 않는다
- 나눠 부르는 것이 테스트로 확인된다

**잃는 것**
- **동시 실행 수와 검색 시간 한계의 숫자에 측정 근거가 없다.** "기본 풀을 넘지 않는다"에서 끌어낸 값이고,
  타임아웃을 정할 때 있었던 중간 장비 기본값 같은 외부 근거조차 없다
- 프로세서 수에 따라 기본 풀이 달라져 환경마다 동시성이 다르다
- Mock 코드가 는다. 검증 수단을 늘리는 것이라 안내서가 말한 "Mock 자체는 채점하지 않는다"와 어긋나지 않지만,
  어디까지 흉내 낼지 선은 필요하다. **공급사 스펙에 오류로 적힌 것까지만 흉내 내고 그 밖은 하지 않는다**

**다시 볼 것**
- 동시 실행 수와 검색 시간 한계의 값. 관측한 지연 분포로 정한다. 그때 풀 크기도 함께 본다
- **호출 한도(429·`E429`)를 어떻게 다룰지.** 한도 수치가 스펙에 없어 지금은 정하지 않는다.
  동시 실행 수를 제한하는 것이 1차 방어이고, 한도에 걸렸을 때의 처리는 재시도·서킷과 같은 자리에서 본다
- 재고·요금 호출 하나의 타임아웃 값. 목록 조회와 다른 값이 맞는지

## Discussion

- **AI 주장과 근거** — (가)를 권하면서 근거로 기본 풀 크기와 대기 45초를 들었다. 약점으로 값에 측정 근거가 없다는 점을 들었다
- **사용자 판단** — (가)로 가되 값의 근거는 나중에 만들어 튜닝하기로 했다
- **반박** — Mock 에 검사를 더하는 것이 "Mock 에 시간을 쓰지 말라"와 부딪히지 않느냐는 AI 의 우려에 대해,
  그 제약은 완성도를 채점하지 않으니 다듬지 말라는 뜻이고 우리 구현을 확인하는 가장 확실한 방법이면 쓰는 것이 맞다고 정리했다.
  안내서도 Mock 을 연동 동작 검증 수단으로는 확인한다고 적고 있다
- **AI 가 뒤늦게 확인한 것** — 50개는 내부 기준이 아니라 공급사가 오류로 거절하는 제약이다. 호출 한도 오류가 따로 있는 것도 이때 처음 봤다

## Verification

요청 하나에 숙소 코드가 50개를 넘을 수 없는지
  → `AvailabilityRequestTest.숙소 코드가 50개를 넘으면 만들 수 없다`
  → `AvailabilityRequestTest.숙소 코드 50개까지는 만들어진다`

숙소 코드가 50개를 넘으면 묶음으로 나눠 부르는지. Mock 이 50개 초과를 공급사처럼 거절하는지.
동시 실행 수가 `flatMap` 인자로 드러나 있는지. 한 공급사가 시간 한계를 넘겨도 나머지 결과로 응답하는지.
검색 서비스를 만들 때 확인하고 그 테스트 이름을 여기에 적는다.
