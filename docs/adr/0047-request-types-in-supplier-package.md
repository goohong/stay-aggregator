# 0047. 재고·요금 조회의 요청 형태를 supplier 패키지에 두기로 결정

## Context

[ADR-0040](0040-package-structure.md) 이 의존 방향을 한 줄로 정했다.

> `catalog` 와 `search` 는 `supplier` 와 `mapping` 을 보고, 서로는 보지 않으며, `supplier` 와 `mapping` 은 아무것도 보지 않는다.

검색 구현 단위가 재고·요금 경계를 더하면서 값 객체 넷이 생긴다.
금액과 요금([ADR-0042](0042-rate-as-tax-included-total.md)), 숙박 구간([ADR-0043](0043-stay-period-value-object.md)),
판매 조건([ADR-0044](0044-rate-conditions-as-value-object.md))이다. 이것들이 어느 패키지에 사는지가 정해지지 않았다.

**셋은 자리가 따라온다.** 금액·판매 조건·요금은 정규화를 마친 표준 모델이다. 어댑터는 이것들을 만들지 않는다.
어댑터가 내놓는 것은 값이 없을 수 있는 `Fetched…` 형태이고([ADR-0030](0030-supplier-response-dto-receives-without-validation.md)),
값이 유효한지는 그 값을 담는 객체의 생성자가 본다([ADR-0041](0041-validate-in-constructors.md)).
검증을 통과한 객체를 정규화 전 단계에서 만들면 두 결정이 함께 어긋난다. 그래서 이 셋은 어댑터 밖, 즉 `search` 것이다.
목록 동기화에서 `NormalizedHotel` 이 `mapping` 에 있는 것과 같은 모양이다.

**남는 것은 숙박 구간이다.** 이것은 받은 값이 아니라 **물어볼 조건**이다.
어댑터가 인자로 받아 공급사 URL 에 체크인·체크아웃을 넣는다. 인원도 같다.
그래서 `supplier` 가 이 타입들을 보게 되고, 위의 한 줄과 부딪힌다.

## Options

- **(가) 재고·요금 조회의 요청 형태를 `supplier` 에 두고 그 안에 숙박 구간을 넣는다** ← 채택 —
  `supplier` 가 이미 응답 공통 형태(`FetchedCatalog`)를 들고 있으므로 경계의 양쪽이 한곳에 모인다.
  의존 방향 한 줄을 고치지 않는다. 대신 우리 검색 API 가 받는 개념이 공급사 패키지에 산다
- **(나) 공용 패키지를 하나 더 만들어 값 객체를 전부 모은다** — "표준 모델은 여기"가 디렉터리로 보인다.
  대신 패키지가 다섯이 되고, `NormalizedHotel` 은 `mapping` 에 남아 정규화한 값이 두 곳으로 갈린다.
  맞추려면 그것까지 옮겨 목록 동기화 코드를 건드린다
- **(다) 전부 `search` 에 두고 어댑터는 날짜 둘과 인원 수를 그대로 받는다** — ADR-0040 이 한 글자도 바뀌지 않는다.
  대신 값 객체를 만들어 놓고 경계에서 도로 푼다. ADR-0043 이 얻으려던 "잘못된 구간으로 공급사를 호출하지 않는다"가
  타입이 아니라 호출하는 쪽의 규율에 걸리고, 어댑터 인자가 넷으로 늘어난다

## Decision

- **재고·요금 조회의 요청 형태를 `supplier` 에 둔다.** 숙소 코드 목록(chunk), 숙박 구간, 인원이 든다
- **그 요청 형태에 드는 값 객체(숙박 구간, 인원)도 `supplier` 에 둔다.** 검증은 각자의 생성자가 한다 (ADR-0041)
- **표준 모델 값 객체(금액, 판매 조건, 요금)는 `search` 에 둔다.** 어댑터는 `Fetched…` 까지만 만든다
- **ADR-0040 의 의존 방향 한 줄은 그대로다.** 고치지 않는다
- 각 타입의 이름은 구현하며 굳히고 [용어](../glossary.md) 에 넣는다

**이유**

- `supplier` 는 그 경계의 응답 형태를 이미 들고 있다. 요청 형태를 같은 자리에 두면 "공급사와 만나는 것 전부"라는 그 패키지의 뜻과 맞고, 경계를 읽을 때 한 디렉터리만 본다
- 표준 모델 값 객체를 어댑터가 만들면 ADR-0030 과 ADR-0041 이 함께 어긋난다. 정규화 전 단계에서 검증을 통과한 객체가 나오기 때문이다
- 패키지를 더 만들면 정규화한 값이 `mapping` 과 새 패키지로 갈린다. 그것을 맞추려면 이번 단위와 무관한 목록 동기화 코드를 건드린다

## Consequences

**얻는 것**
- 의존 방향이 한 줄로 남는다. `supplier` 가 여전히 다른 패키지를 보지 않는다
- 어댑터 인자가 하나다. 체크아웃이 앞인 구간으로는 어댑터를 호출할 수조차 없다 (ADR-0043)
- 재고·요금 경계의 요청과 응답 형태가 한 디렉터리에 있다

**잃는 것**
- **숙박 구간과 인원은 우리 검색 API 가 받는 개념인데 공급사 패키지에 산다.** 디렉터리만 보고는 왜 거기 있는지 모른다.
  ADR-0040 이 `NormalizedHotel` 을 옮길 때와 같이 KDoc 으로 적는다
- `search` 에서 숙박 구간을 쓰는 곳마다 `supplier` 를 import 한다

**다시 볼 것**
- **이 자리가 구현하면서 불편한지.** 사용자가 확인해 알려 달라고 했다. 판단 기준은 둘이다.
  `search` 안에서 숙박 구간을 다루는 코드가 공급사 패키지를 가리키는 것이 읽기 나쁜가,
  그리고 공급사와 무관한 값이 `supplier` 에 더 쌓이는가. 쌓이기 시작하면 (나)로 옮긴다

## Discussion

- **AI 주장과 근거** — (가)를 권했다. 근거는 경계의 양쪽을 한곳에 두는 것과 ADR-0040 을 고치지 않는 것이다.
  약점으로 개념과 자리가 어긋나 디렉터리만 보고는 설명되지 않는 점을 들었다
- **사용자 판단** — "잘 모르겠어서 가에 둘게. 다만 중간에 진행하면서 불편함이 생기거나 옮기고 싶은지는 체크해서 알려줘"
- **그래서 어떻게 바뀌었나** — 결정은 (가)대로 두고, 다시 볼 것에 무엇을 보면 옮길 때인지 판단 기준을 적었다.
  구현하며 그 두 기준에 걸리는 것이 나오면 보고한다

## Verification

`supplier` 가 다른 패키지를 보지 않는지, `search` 가 `catalog` 를 보지 않는지
  → `grep -rn "import com.stayaggregator." app/src/main/kotlin/com/stayaggregator/supplier` 에
    하위 패키지(`a`·`b`)가 부모를 가리키는 줄만 나오는지
  → `grep -rn "import com.stayaggregator.catalog" app/src/main/kotlin/com/stayaggregator/search` 가 비는지

  → 2026-09-17 재고·요금 경계를 만든 뒤 확인. `supplier` 는 하위 패키지가 부모를 가리키는 줄만 있고, `search` 에는 `catalog` import 가 없다

요청 형태가 `supplier` 에 있고 숙박 구간·인원을 드는지
  → `app/src/main/kotlin/com/stayaggregator/supplier/AvailabilityRequest.kt`
