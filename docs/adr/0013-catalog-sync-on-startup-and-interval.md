# 0013. 숙소 목록은 앱 기동 시와 일정 주기마다 받아오기로 결정

## Context

매핑은 공급사의 숙소 목록 API 로 만든다. 매핑이 없으면 검색할 숙소 코드를 알 수 없다.
숙소 목록 API 는 조건 없이 공급사가 취급하는 전체 목록을 돌려주고, 자주 바뀌지 않는다.
재고·요금은 조회할 때마다 바뀐다.

응답의 이름과 최대 수용 인원은 저장해 둔 목록 값을 쓰기로 했으므로
([ADR-0012](0012-static-info-from-catalog.md)), 목록을 다시 받아오기 전까지는 공급사의 변경이
반영되지 않는다.

## Options

- **(가) 앱을 띄울 때 한 번** — 가장 단순하다. 대신 공급사 목록이 바뀌어도 앱을 다시 띄우기 전까지
  반영되지 않아, ADR-0012 의 알려진 제약이 끝나지 않는다.
- **(나) 앱을 띄울 때 한 번 + 일정 주기마다** ← AI 추천 — 목록 변경이 주기 안에 반영된다. 드물게 바뀌는
  정보는 드물게, 매번 바뀌는 요금·재고는 매번 받아온다는 성격 차이가 호출 시점에도 드러난다. 대신 주기
  값을 정하고 근거를 대야 하며, 주기 사이에는 ADR-0012 의 알려진 제약이 남는다.
- **(다) 검색할 때마다** — 매핑이 늘 최신이다. 대신 검색마다 공급사 호출이 늘고, 전체 목록을 받으므로
  숙소가 많아질수록 무겁다. 목록 API 가 실패하면 검색도 막힌다.
- **(라) 사람이 별도 명령으로 실행** — 갱신 시점을 사람이 통제한다. 대신 실행을 잊으면 갱신되지 않고,
  명령을 받는 창구가 필요하다. 관리자 기능은 범위 밖이다.

## Decision

**(나)** 를 택한다. 앱을 띄울 때 숙소 목록을 받아와 매핑을 만들고, 이후 일정 주기마다 다시 받아와
갱신한다.

## Consequences

**얻는 것**
- 숙소 목록과 재고·요금의 성격 차이가 호출 시점으로도 구분된다
- ADR-0012 에서 받아들인 제약(옛 이름, 최대 수용 인원 증가 시 모순, 새 객실 타입 누락)가 주기 안에서 끝난다

**잃는 것**
- 주기 사이에는 ADR-0012 의 알려진 제약이 그대로 남는다

**이 결정으로 새로 정해야 하는 것**
- 주기 값과 그 근거
- 조회 응답이 저장값과 다를 때(목록 불일치) 해당 공급사의 갱신을 앞당길지
- 목록 갱신 전까지 조회 응답에만 나오는 새 객실 타입을 어떻게 처리할지
- 앱을 띄울 때 목록을 받아오지 못하면 어떻게 할지 (Q11)

## Discussion

추천과 결정이 같고, 논의 중에 근거가 바뀌지 않았다.

## Verification

받아 온 목록이 매핑으로 반영되는지
  → `CatalogSyncIntegrationTest.목록을 받으면 숙소와 객실 타입 매핑이 저장된다`

기동 시 한 번과 주기 실행을 한 선언이 맡는지
  → `app/src/main/kotlin/com/stayaggregator/catalog/CatalogSyncScheduler.kt` 의 `@Scheduled(initialDelayString, fixedDelayString)`

기동 직후 실제로 도는지
  → Mock 을 띄우고 `./gradlew :app:bootRun` 했을 때 기동 로그 뒤에 두 공급사의 동기화 완료 로그가 남는다(2026-09-17 관찰).
    주기가 하루라 두 번째 실행은 관찰하지 않았다.
