# 0064. 예약 대행은 설계만 남기고 결과를 모르는 예약은 같은 멱등 키로 공급사에 물어 확정하기로 결정

## Context

요구사항의 선택 항목에 "예약 대행"이 있다. 공급사에 예약을 만들고 취소하는 일과, 실패했을 때의 보상 처리를 **설계하거나 간단히 구현**하는 것이다.
여기서 보상 처리는 **요청의 결과를 모를 때 뒤를 수습하는 일**을 말한다. 예약 요청을 보냈는데 응답이 오지 않으면, 공급사에 방이 잡혔는지 안 잡혔는지 우리는 모른다.
그 상태를 어떻게 정리할지가 이 항목의 핵심이다.

**공급사 규약에는 예약 API 가 없다.** 숙소 목록 API 와 재고·요금 API 뿐이다.
Mock 이 흉내 내는 공급사 API 도 그 둘뿐이다 (`mock-supplier/src/main/kotlin/com/stayaggregator/mocksupplier/MockSupplierController.kt` 의 `/a/v1/hotels`·`/b/api/properties`·`/a/v1/availability`·`/b/api/search`, 모두 `GET`).

이미 정해진 것 중 예약에 닿는 것

| 결정 | 예약에 주는 영향 |
|---|---|
| [ADR-0010](0010-keep-internal-id-on-merge.md) | 내부 식별자는 공급사 상품 하나를 가리키고 바뀌지 않는다. 그 ADR 의 이유가 "그 식별자로 어느 공급사에 무엇을 예약할지 알 수 있다"이다 |
| [ADR-0058](0058-same-hotel-confirmed-pairs-only.md) | `sameHotelId` 는 짝이 바뀌면 값이 바뀐다. 저장해 두고 다시 찾는 키로 쓰지 않는다 |
| [ADR-0042](0042-rate-as-tax-included-total.md) | 요금은 세금 포함 기간 전체 총액 하나다 |
| [ADR-0027](0027-spec-violation-handling-criteria.md) | 정한 시간 안에 오지 않은 것도 공급사 실패에 든다 ([용어](../glossary.md) "공급사 실패") |
| [ADR-0051](0051-retry-transient-supplier-failures.md) | 재시도는 일시적인 실패만, 여부는 consumer 가 정한다. 그 전제는 재고·요금 조회가 `GET` 이라 여러 번 불러도 같다는 것이었다 |
| [ADR-0056](0056-circuit-breaker-per-supplier-outside-retry.md) | 서킷은 공급사마다 하나이고 검색에만 있다 |

확인한 사실

| 사실 | 원문 |
|---|---|
| 호텔 연동 API 에서 검색 때 받은 요금에는 "예약 전에 다시 확인해야 하는 것"이 있고, 다시 확인하는 호출이 따로 있다 | [Hotelbeds, Booking API Workflow](https://developer.hotelbeds.com/documentation/hotels/booking-api/workflow/) 절 "Parsing the results": "If the type is RECHECK you will need to perform an extra operation called CheckRate that will return to you the updated information of that specific rate and then book it, but if the type is BOOKABLE you can immediately book it" |
| 멱등 키는 같은 작업을 두 번 하지 않고 요청을 다시 보내기 위한 것이다 | [Stripe, Idempotent requests](https://docs.stripe.com/api/idempotent_requests): "The API supports idempotency for safely retrying requests without accidentally performing the same operation twice." |
| 같은 키로 다시 보내면 처음 결과를 그대로 돌려준다. 실패였어도 그렇다 | 같은 곳: "Subsequent requests with the same key return the same result, including `500` errors." |
| 키는 영원히 남지 않는다. 지워진 뒤 같은 키를 쓰면 새 요청으로 처리한다 | 같은 곳: "You can remove keys from the system automatically after they're at least 24 hours old. We generate a new request if a key is reused after the original is pruned." |
| 키는 부르는 쪽이 만든다 | 같은 곳: "A client generates an idempotency key, which is a unique key that the server uses to recognize subsequent retries of the same request." |
| `POST` 같은 멱등하지 않은 메서드를 실패에 견디게 하려고 헤더를 표준화하려는 초안이 있다. **만료된 초안이다** | [IETF, The Idempotency-Key HTTP Header Field](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) (draft-07, Expired Internet-Draft) Abstract: "The HTTP Idempotency-Key request header field can be used to make non-idempotent HTTP methods such as POST or PATCH fault-tolerant." |

세 원문은 2026-09-17 에 열어 위 문장을 대조했다.

## Options

구현 여부
- **(가) 설계만 문서로 남긴다** ← 채택 — 없는 API 를 지어내지 않는다. 대신 동작하는 코드가 없다
- **(나) 예약 API 를 Mock 에 만들고 간단히 구현한다** — 실행해 볼 수 있다. 대신 공급사 규약에 없는 요청·응답 모양을 우리가 정하게 되고, 그 모양에 맞춘 코드는 실제 공급사가 붙을 때 맞는다는 근거가 없다

결과를 모르는 예약을 수습하는 방법
- **(ㄱ) 예약 요청에 우리가 만든 고유한 표식(멱등 키)을 붙이고, 응답이 없으면 새로 예약하지 않고 그 표식으로 "이 예약이 됐나"를 공급사에 물어 확정한다** ← 채택 —
  방이 두 번 잡히지 않고, 실제로 된 예약을 없애지도 않는다. 대신 공급사가 그 표식을 받고 조회도 할 수 있어야 한다
- **(ㄴ) 결과를 모르면 취소를 보낸다** — 공급사에 기대는 것이 적다. 대신 실제로 된 예약을 고객 모르게 없앨 수 있고,
  취소도 응답이 안 오면 "취소가 됐나"를 모르는 같은 문제가 반복된다

## Decision

**(가)와 (ㄱ)** 을 택한다. 아래는 설계이고 구현하지 않는다.

### 가정

이 설계는 공급사에 대한 가정 위에 있다. **공급사 규약으로 확인한 것이 아니다.**

1. 공급사가 예약 생성·조회·취소 API 를 준다
2. 예약 생성 요청에 우리가 만든 멱등 키를 받는다. 같은 키로 온 요청은 같은 예약으로 본다
3. 멱등 키로 예약 상태를 조회할 수 있고, 그 답은 "있다(확정)" 또는 "없다" 중 하나로 온다
4. 멱등 키를 공급사가 기억하는 기간이 정해져 있고 우리가 그 값을 안다
5. 예약이 확정되면 공급사 예약 번호를 주고, 취소는 그 번호로 한다

### 예약을 받는 값

- **내부 식별자(`hotelId`, `roomTypeId`)** 와 숙박 구간·인원, 고객이 본 요금(세금 포함 총액)을 받는다
- 내부 식별자를 매핑에서 공급사·공급사 코드로 바꿔 공급사를 부른다. 내부 식별자가 공급사 상품 하나를 가리키므로(ADR-0010) 어느 공급사인지 따로 받지 않는다
- **`sameHotelId` 로는 예약하지 않는다.** 짝이 바뀌면 값이 바뀌고(ADR-0058), 공급사 상품 하나를 가리키지도 않는다

### 우리 쪽 상태

| 상태 | 뜻 |
|---|---|
| 요청함 | 멱등 키를 만들어 기록했고 공급사에 보냈거나 보내려는 중이다 |
| 확정 | 공급사가 예약됐다고 답했다. 공급사 예약 번호를 가진다 |
| 실패 | 공급사에 예약이 없다는 것이 확실하다 |
| 확인 필요 | 보냈는데 결과를 모른다 |
| 취소 요청함 | 확정된 예약에 취소를 보냈거나 보내려는 중이다 |
| 취소됨 | 공급사가 취소됐다고 답했다 |
| 취소 확인 필요 | 취소를 보냈는데 결과를 모른다 |

### 예약 생성

1. **서킷이 열린 공급사에는 보내지 않는다.** 실패로 끝낸다. 아무것도 보내지 않았으니 수습할 것이 없다
2. **예약 직전에 요금·재고를 다시 확인한다.** 검색 때 받은 값은 그 뒤에 바뀌었을 수 있다. 요금·재고 캐시([ADR-0065](0065-availability-cache-redis.md))에서 온 값이면 더 오래됐을 수 있다. 응답 항목의 받은 시각이 그 나이다.
   재확인은 이미 있는 재고·요금 API 로 한다
3. **멱등 키를 만들고, 요청함 상태로 먼저 기록한 뒤 보낸다.** 보낸 뒤에 기록하면 그 사이에 서버가 멈췄을 때 어떤 키로 보냈는지 잃는다
4. 응답에 따라 상태를 바꾼다

   | 공급사 응답 | 상태 | 왜 |
   |---|---|---|
   | 예약됐다 | 확정 | |
   | 명확한 거절(요청이 잘못됨, 재고 없음) | 실패 | 공급사가 만들지 않았다고 말했다 |
   | 연결하지 못함 | 실패 | 요청이 공급사에 닿지 않았다 |
   | 정한 시간 안에 오지 않음, 연결이 도중에 끊김, 5xx, 본문을 읽지 못함 | 확인 필요 | 공급사가 요청을 받아 처리했는지 알 수 없다 |

   **검색과 판정이 다르다.** 검색에서 타임아웃은 그냥 공급사 실패지만(ADR-0027), 예약에서는 "안 됐다"가 아니라 "모른다"다.
   검색은 다시 조회하면 그만이지만 예약은 방이 잡혔을 수 있기 때문이다

### 확인 필요를 수습하기

- **새로 예약하지 않는다.** 같은 멱등 키로 공급사에 예약 상태를 묻는다
  - 있다 → 확정
  - 없다 → 실패
  - 이번에도 답이 없다 → 확인 필요로 두고 나중에 다시 묻는다
- **묻는 것은 공급사 상태를 바꾸지 않는 조회라 여러 번 불러도 된다.** 재시도는 ADR-0051 의 일시적인 실패 기준을 따를 수 있다
- **멱등 키를 공급사가 기억하는 기간 안에 끝내야 한다.** Stripe 의 예처럼 키가 지워진 뒤에는 같은 키도 새 요청으로 처리될 수 있다(위 확인한 사실).
  그 기간이 가까워지도록 확인 필요로 남은 예약은 자동으로 풀지 않고 사람이 보게 넘긴다

### 재시도

- **예약 생성은 멱등 키 없이 재시도하지 않는다.** ADR-0051 이 재시도를 안전하다고 본 전제는 재고·요금 조회가 `GET` 이라 여러 번 불러도 같다는 것이었다.
  예약 생성은 부를 때마다 예약이 하나씩 생길 수 있어 그 전제가 없다
- 멱등 키가 있어도 응답이 없을 때는 **다시 보내지 않고 묻는다.** 두 번 보내지 않는 쪽이 가정 2 가 어긋났을 때의 피해가 작다

### 취소

- 확정 상태의 예약만 취소한다. 공급사 예약 번호로 보낸다
- 흐름은 생성과 같다. 취소 요청함을 먼저 기록하고, 답이 없으면 취소 확인 필요로 두고 그 예약 번호로 상태를 물어 확정한다
- 서킷이 열린 공급사에는 보내지 않는다. 확정 상태를 그대로 두고 취소가 되지 않았다고 알린다

### 재확인 결과가 다를 때와 목록에서 빠진 상품

- **재확인한 요금이 고객이 본 요금과 다르면 예약하지 않고, 바뀐 요금을 알려 고객에게 다시 묻는다.** 고객이 동의한 금액으로만 예약한다
- **매핑에서 `missing_since` 가 채워진 상품은 예약을 막는다.** 검색에도 나오지 않는 상품이다 ([ADR-0037](0037-missing-catalog-entries-kept-and-marked.md))

### 이 ADR 이 정하지 않은 것

- 확인 필요를 다시 묻는 간격과 사람에게 넘기는 시점의 값
- 취소 조건(취소 가능 여부·수수료). 공급사가 주지 않는다 ([용어](../glossary.md) "판매 조건")

**이유**

- 공급사 규약에 예약 API 가 없다. 그 위에 코드를 쓰면 요청·응답 모양을 우리가 지어내게 되고, 그 코드는 설명할 근거가 없다
- 결과를 모를 때 취소를 보내면 **실제로 된 예약을 우리가 없앨 수 있다.** 고객은 예약이 됐는지도 취소됐는지도 모른다.
  그리고 취소도 응답이 안 오면 똑같이 결과를 모르게 되어 문제가 한 단계 옮겨질 뿐이다
- 같은 표식으로 물으면 사실(공급사에 예약이 있는가)을 확인한 뒤에 상태를 정한다. 추정으로 상태를 바꾸지 않는다

## Consequences

**얻는 것**
- 응답이 오지 않아도 방이 두 번 잡히지 않는다
- 실제로 된 예약을 결과를 모른다는 이유로 없애지 않는다
- 없는 API 를 가정한 코드가 저장소에 없다
- 예약이 내부 식별자로 들어와 병합(ADR-0058)과 무관하게 공급사 상품 하나에 걸린다

**잃는 것**
- **구현이 없다.** 실행해 볼 수 없고, 이 설계가 맞는지 테스트로 확인하지 못한다
- **가정에 기댄다.** 공급사가 멱등 키나 키로 조회하는 기능을 주지 않으면 확인 필요를 수습할 방법이 없다
- **확인 필요가 오래 남으면 사람이 봐야 한다.** 공급사가 계속 답하지 않으면 자동으로 끝나지 않는다. 볼 수단(관리자 기능)은 범위 밖이다
- 예약 한 건마다 재확인 호출이 하나 더 든다
- 우리 쪽에 예약 상태를 기록할 자리가 필요하다. 지금 DB 는 매핑만 저장한다([ADR-0017](0017-mapping-in-server-rdb.md))

**다시 볼 것**
- 실제 공급사의 예약 API 를 받으면 가정을 하나씩 대조한다. 특히 키로 조회하는 대신 같은 키로 다시 보내면 처음 결과를 돌려주는 방식(Stripe 의 방식)만 준다면, "묻는" 방법이 그것으로 바뀐다
- 서킷을 예약에도 둘지. 지금 서킷은 검색에만 있고 검색 결과를 센다(ADR-0056). 이 설계는 그 상태를 읽기만 한다

## Discussion

- **AI 주장과 근거** — 결과를 모를 때의 두 안을 냈다. "결과를 모르면 취소를 보낸다"와 "같은 요청 표식으로 다시 묻는다"이고,
  앞의 것은 된 예약을 없앨 수 있고 취소도 같은 문제를 겪는다는 이유로 뒤의 것을 권했다
- **질문** — 사용자가 "실패 보상이 뭔데? 또 이상한 용어 같은데" 라고 물었다
- **풀어 쓴 것** — AI 가 요청의 결과를 모를 때 뒤를 수습하는 일이라고 풀어 설명했다. 예약 요청을 보냈는데 응답이 없으면 방이 잡혔는지 모르고,
  그 상태를 어떻게 정리하느냐의 문제라는 것이다. 이 문서도 그 말을 처음 쓰는 자리에서 풀어 적었다
- **사용자 판단** — 추천안(같은 표식으로 다시 묻는다)으로 정했다. 공급사 규약에 예약 API 가 없으므로 설계만 문서로 남기기로 했다
- **이어서 정한 것** — 설계를 쓴 에이전트가 "타임아웃·5xx 는 예약에서는 확인 필요"로 판단했고, 사용자가 그 판단을 확인했다(검색과 다르게 본다).
  재확인 요금이 다르면 고객에게 다시 묻기, 목록에서 빠진 상품은 예약 막기도 사용자가 정했다
