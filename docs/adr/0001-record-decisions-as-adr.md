# 0001. 결정 기록 방식과 ADR 작성 기준 정의

## Context

이 프로젝트는 정답이 하나로 정해지지 않은 선택이 여러 번 나온다. 요금을 무엇으로 표준화할지,
공급사마다 다른 실패 표현을 어떻게 하나로 판정할지, 타임아웃 값을 얼마로 둘지 같은 것들이다.
이런 선택을 기록하지 않으면 나중에 코드만 남고 "왜 이렇게 했는지"가 사라진다.

기록을 어디에 어떤 단위로 남길지, 그리고 무엇을 기록 대상으로 볼지를 정해야 한다.

## Options

- **(가) 결정 하나에 파일 하나** ← AI 추천 — 특정 결정을 `ADR-0004` 로 가리켜 코드 주석이나
  다른 문서에서 참조할 수 있다. `git log docs/adr/0004-*.md` 로 그 결정만의 변경 이력이 보인다.
  대신 파일 수가 늘어난다.
- **(나) 한 파일에 누적** — 파일이 하나라 훑기 쉽다. 대신 결정이 쌓이면 길어져 놓치는 것이 생기고,
  개별 결정을 가리킬 방법이 없다.

## Decision

**(가)** 를 택한다. 결정 하나에 `docs/adr/NNNN-<slug>.md` 파일 하나로 남긴다.

**선택지와 대안, 그것을 버린 이유는 ADR 에만 쓴다.** 다른 문서는 결정 요약과 링크만 둔다.
README 는 결정 한 줄과 핵심 이유 한 줄, 그리고 해당 ADR 로의 링크로 쓴다.

**ADR 을 쓰는 기준**

쓴다
- 선택지가 둘 이상이고 어느 쪽을 골라도 동작하는 경우
- 바꾸려면 여러 곳을 고쳐야 하는 것
- 나중에 "왜 이렇게 했나"를 설명해야 할 것

쓰지 않는다
- 공급사 규약이 답을 정해둔 것
- 되돌리기 쉬운 것 (변수명, 메서드 분리, 로그 문구)
- 이미 내린 결정의 기계적인 결과

애매하면 쓴다.

**뒤집을 때** 는 기존 ADR 을 고치지 않는다. 새 ADR 을 쓰고 기존 것의 상태를
`superseded by ADR-NNNN` 으로 바꾼다. 커밋 메시지의 ADR 참조는 그 시점의 기록이므로 그대로 두고,
코드 주석의 참조는 현재 결정을 가리켜야 하므로 함께 고친다.

**이유** — 한 파일에 다 쌓으면 길어져서 놓치는 게 생긴다. 쪼개면 특정 결정을 가리켜 참조할 수 있다.

## Consequences

**얻는 것**
- 결정이 한 군데에만 있으므로 문서끼리 어긋날 수 없다
- 뒤집은 결정이 지워지지 않고 남는다

**잃는 것**
- 문서가 서로를 참조하는 구조라, ADR 을 고칠 때 참조하는 쪽도 같이 봐야 한다
- 읽는 사람이 어디부터 볼지 모를 수 있다. `docs/adr/README.md` 목록으로 완화한다

## Discussion

- **AI 주장과 근거** — (가) 를 권하면서 "파일을 쪼개야 뒤집은 결정을 `superseded` 로 남길 수 있다"를
  가장 큰 근거로 들었다
- **반박** — "파일이 하나여도 아래나 그 근처에 수정 로그를 남기면 되는 거지"
- **검증 결과** — 반박이 맞다. 한 파일이어도 변경 이력은 남길 수 있으므로 그 근거는 결정적이지 않다.
  남는 실질 차이는 개별 참조 가능성과 파일 단위 변경 이력뿐이고, 전부 "있으면 편한" 수준이다
- **그래서 어떻게 바뀌었나** — 결정은 유지하되 주된 근거를 "참조 가능성과 길이"로 바꿔 기록한다

## Verification

`docs/adr/` 에 결정마다 파일이 하나씩 있고, `docs/adr/README.md` 목록이 실제 파일과 일치하는지.
