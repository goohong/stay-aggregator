# 0009. 공급사 호출 흐름을 코루틴이 아닌 Reactor 로 직접 다룸

## Context

WebClient 는 Reactor 의 `Mono`/`Flux` 를 돌려주는 HTTP 클라이언트다. Kotlin 코루틴으로
감싸서 쓸 수도 있다(`.awaitBody<T>()` 같은 확장 함수).

**확인된 사실**: 요구사항은 WebClient 를 지정하면서, 여러 공급사를 동시에
호출할 때 타임아웃·재시도·병렬 호출을 어떻게 다루는지를 핵심으로 제시한다.
숙소가 수천 개로 늘어났을 때의 대응도 설계 문서에 남기도록 요구한다. 지금 예시 데이터(숙소 몇 개)로는 이 상한에
걸리지 않지만, 그걸 근거로 성능·동시성 설계를 생략하면 안 된다는 뜻이다.

숙소가 수천 개, 공급사가 수십 개로 늘면 청크(최대 50개씩) 호출이 수백~수천
번 필요하고, 이걸 전부 동시에 쏘면 우리 서버와 공급사 양쪽이 감당 못 한다.
**동시 호출 수를 제한하는 기능**이 실제로 필요해진다.

## Options

- **(가) 코루틴** — `suspend fun` + `async` + `runCatching`. 코드가 순서대로
  읽혀서 이해하기 쉽다. 대신 동시 호출 수 제한을 `Semaphore` 를 직접 만들어
  구현해야 하고(permit 획득·반납을 손으로 관리, `finally` 에서 반납을 빠뜨리면
  데드락 같은 버그가 잘 숨는다), WebClient 를 지정한 취지(Reactor 연산자로
  타임아웃·재시도·병렬을 다루는 것을 보려 함)와 실제 구현 방식이 상충한다.
- **(나) Reactor 그대로** ← AI 추천 — `Mono`/`Flux`, `onErrorResume`(부분 실패
  허용), `timeout(Duration)`(타임아웃), `flatMap(mapper, concurrency)`(동시
  호출 수 제한)이 전부 연산자 하나씩으로 표현된다. 동시 호출 수 제한이
  라이브러리가 검증한 코드로 해결된다. 대신 코루틴보다 배우기 어렵고, 코드를
  짜는 시점과 실제 실행되는 시점이 분리돼 있어(구독 시점에 실행) 그 함정을
  매번 의식해야 한다.

`Semaphore` 를 직접 쓰면 공급사별로 다른 동시성 한도, 커스텀 대기 정책 같은
세밀한 제어를 얻을 수 있다. 하지만 지금 확인된 요구사항은 "동시 호출 수를
제한한다" 하나뿐이고, 공급사별로 다른 rate limit 이 있다는 사실은 확인되지
않았다. 확인되지 않은 미래 요구를 위해 동시성 버그 위험이 있는 코드를 미리
짜는 것은 이 프로젝트의 원칙("완벽한 코드보다 상황에 맞는 필요한 만큼")과
상충한다. 필요해지면 그때도 Reactor 위에서 공급사별로 다른 `concurrency`
값을 주는 `flatMap` 을 따로 걸면 되므로, Semaphore 로 갈아타야 할 상황은
좁다.

## Decision

**(나) Reactor** 를 그대로 쓴다. `RateAdapter` 의 반환 타입은 `Mono<List<NormalizedRate>>`
로 정의한다. 동시 호출 수는 `Flux.fromIterable(chunks).flatMap(mapper, concurrency)`
의 `concurrency` 인자로 제한한다.

**이유** — 성능은 이 규모(공급사 2~3개)에서는 코루틴과 차이가 없지만, 채널
연동이라는 도메인 자체가 공급사가 수십~수백 개로 늘어나는 걸 전제한다.
요구사항도 숙소가 수천 개로 늘어나는 경우를 명시적으로 대비하라고 한다. 그 규모에서 실제로
필요한 기능(동시 호출 수 제한)이 Reactor 는 연산자 하나로 있고 코루틴은
직접 만들어야 한다는 게 실질적인 근거다.

## Consequences

**얻는 것**
- 동시 호출 수 제한이 검증된 라이브러리 코드로 해결된다
- WebClient 를 지정한 요구사항의 취지와 실제 구현 방식이 일치한다

**잃는 것**
- 둘 다 처음 써보는데 배우기 더 어려운 쪽을 택했다. 코드를 짜는 시점과
  실행되는 시점이 분리돼 있다는 점(`runCatching` 이 Reactor 체인 안에서는
  아무것도 못 잡는다는 함정 포함)을 계속 의식해야 하고, "이해하지 못한
  코드는 저장소에 두지 않는다"는 원칙에 걸릴 위험이 가장 큰 결정이다

## Discussion

- **AI 주장과 근거** — 처음엔 "이 규모(공급사 2~3개)에서는 성능 차이가 없다"고
  전제하고, 근거를 요구사항의 지정 취지 하나로만 들었다
- **반박** — 이 도메인은 공급사가 많아질 것을 전제해야 하고, "지금 규모니까
  성능은 신경 안 써도 된다"는 요구사항이 숙소가 수천 개로 늘어나는 경우를 대비하라고 명시한
  것과 정면으로 상충한다는 지적을 받았다
- **검증 결과** — 지적이 맞다. 지금 데이터로 안 걸린다는 걸 요구사항이 스스로
  인정하면서도 그걸 핑계로 넘어가지 말라고 명시했는데, 그 함정을 그대로
  밟았다. 성능 근거를 다시 짚으니, 동시 호출 수 제한이라는 구체적 기능이
  Reactor 는 연산자 하나이고 코루틴은 직접 구현이 필요하다는 차이가 있었다
- **그래서 어떻게 바뀌었나** — 결정(Reactor)은 그대로였지만 근거가
  "요구사항 취지에 맞다"에서 "수천 개 규모에서 필요한 기능을 라이브러리가
  기본 제공한다"로 바뀌었다. 무게가 다른 근거다

## Verification

`RateAdapter` 인터페이스의 반환 타입이 `Mono<...>` 인지, 공급사 병렬 호출
지점에 `flatMap` 의 `concurrency` 인자가 명시돼 있는지.
