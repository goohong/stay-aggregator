# 0028. 결정이 끝난 구현 단위부터 구현하고 남은 설계를 이어가기로 결정

## Context

ADR 이 27 개 쌓였고 코드는 앱 골격뿐이다. 남은 오픈 질문 중 요금(Q1)·날짜 구간(Q2)·어댑터(Q5)·DTO 범위(Q6)는 검색 흐름을 막고 있고,
타임아웃 값과 동시성 제한(Q23)은 측정해야 근거가 생긴다. 요구사항도 타임아웃 값을 응답 지연 Mock 으로 정하라고 제안한다.
이미 accepted 인 결정 중 일부(가상 스레드 위 `block()`, JDK 25 툴체인, HikariCP 버전 덮어쓰기)는 띄워 봐야 확인된다.

코드가 없는데도 ADR 의 Verification 이 가리키는 파일과 실제가 네 곳에서 어긋나 있다.

| ADR | Verification | 실제 |
|---|---|---|
| [0005](0005-separate-mock-module.md) | `settings.gradle.kts` 에 `mock-supplier` | `app` 만 있음 |
| [0020](0020-mvc-server-with-webclient.md) | WebClient 스타터가 있음 | 없음 |
| [0021](0021-block-on-virtual-threads.md) | `application.yml` 에 가상 스레드 설정 | 없음 |
| [0022](0022-jvm-25.md) | `jvmToolchain(25)` | `jvmToolchain(21)` |

CLAUDE.md 의 "합의되지 않은 갈림길이 남아 있으면 구현을 시작하지 않습니다"는 저장소 전체의 갈림길로도 읽혀, 이대로면 모든 설계가 끝날 때까지 구현할 수 없다.

## Options

- **(가) 결정이 끝난 구현 단위부터 구현하고, 남은 설계는 구현과 번갈아 이어간다** ← AI 추천 — 측정이 필요한 결정에 근거가 생기고, 결정과 코드·테스트가 짝지어 쌓인다.
  대신 핵심 흐름 밖의 설계가 뒤로 밀릴 수 있다.
- **(나) 남은 설계를 모두 끝낸 뒤 구현한다** — 설계 전체가 먼저 한 덩어리로 완성된다. 대신 측정이 필요한 결정은 추측으로 적거나 결국 구현 뒤로 미뤄야 하고,
  DTO 경계처럼 코드로만 확정되는 설계를 글로 설계하게 된다.

## Decision

**(가)** 를 택한다.

- "합의되지 않은 갈림길이 남아 있으면 구현을 시작하지 않는다"는 **구현 단위**로 적용한다. 구현하려는 단위가 닿는 갈림길이 모두 합의됐으면 시작하고, 열린 질문의 답을 전제하는 코드는 쓰지 않는다
- 설계는 핵심 흐름을 막는 질문(Q1·Q2·Q5·Q6)을 핵심 흐름 밖의 질문(Q17·Q18·Q19·Q25)보다 먼저 다룬다. Feature Spec 오픈 질문의 상태에 그 질문이 막고 있는 구현을 적는다
- ADR 의 Verification 이 이미 있는 파일을 가리키면, 그 ADR 커밋이나 바로 다음 커밋에서 그 파일을 맞춘다. 구현 커밋의 `확인:` 에 적은 테스트 이름은 같은 커밋에서 해당 ADR 의 Verification 에 적는다
- 구현 단위마다 JOURNAL 에 AI 가 쓴 것, 읽으며 물은 것, 바꾼 것, 설명하지 못해 뺀 것을 남긴다

**이유** — 남은 결정 일부는 측정 없이 근거를 댈 수 없고, 요구사항도 그 방법을 제안한다. 문서와 코드의 어긋남은 순서가 아니라 Verification 이 가리키는 파일을 함께 바꾸지 않은 커밋 방식에서 생겼으므로 커밋 규칙으로 막는다.

## Consequences

**얻는 것**
- 측정이 필요한 결정(타임아웃, Q23)을 측정한 값으로 적는다
- 결정과 그것을 확인하는 코드·테스트가 커밋 이력에서 짝지어 보인다
- 남은 Verification 부채를 `git grep "이 절에 이름을 적는다"` 로 볼 수 있다

**잃는 것**
- 핵심 흐름 밖의 설계(Q4, Q17·Q18, Q19)가 뒤로 밀릴 수 있다. 설계는 도메인 전체를 다룬다는 요구를 채우려면 따로 챙겨야 한다
- 검색 흐름은 Q1·Q2·Q5·Q6 이 정해지기 전까지 구현할 수 없으므로, 먼저 열리는 것은 기반 구성(JDK 25, 가상 스레드, Mock 모듈, 웹·WebClient 스타터)과 숙소 목록 동기화 → 매핑 저장이다
- 나중 결정 때문에 먼저 짠 코드를 고치는 커밋이 생길 수 있다

## Discussion

- **AI 주장과 근거** — (가)를 권하면서 약점으로 "결정이 자주 바뀌면 문서와 코드가 어긋날 기회가 는다", "대체된 ADR 이 많으면 사전 사고가 부족해 보일 수 있다"를 들었고,
  (가)면 핵심 흐름을 먼저 얻는다는 뉘앙스로 설명했다. 처음에는 사용자의 질문을 "무엇부터 구현할까"로 잘못 읽어 순서 제안부터 했다
- **반박** — 사용자는 두 과정이 남기는 과정과 결과물이 어떻게 평가될지를 물은 것이었다. 다른 AI 의 독립 의견도 결론은 (가)였으나 근거 세 곳을 반박했다
- **검증 결과** — 코드가 없는데도 Verification 어긋남이 네 곳 있어, 어긋남의 원인은 순서가 아니라 커밋 방식이었다. 대체된 ADR 은 모두 코드 없이 설계 검토에서 생겼고,
  요구사항은 시행착오 기록을 더 높게 본다고 해 두 번째 약점은 근거가 없었다. 검색 흐름은 Q1·Q2·Q5·Q6 에 막혀 있어 (가)도 먼저 여는 것은 기반 구성과 매핑 저장이다
- **그래서 어떻게 바뀌었나** — 약점을 "핵심 흐름 밖 설계가 밀리는 것"으로 바꾸고, 어긋남은 커밋 규칙으로 막기로 했다

## Verification

CLAUDE.md 의 일하는 순서에 구현 단위 적용 문장이 있고, 커밋 규칙에 Verification 짝 규칙이 있는지. 위 표의 네 ADR 이 가리키는 파일이 각 ADR 을 구현하는 커밋에서 맞춰졌는지.
