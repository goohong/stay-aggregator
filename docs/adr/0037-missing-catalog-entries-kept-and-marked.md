# 0037. 목록에서 사라진 숙소·객실 타입은 매핑을 남기고 사라진 시각을 표시하기로 결정

## Context

숙소 목록은 앱 기동 시와 주기마다 받아오고([ADR-0013](0013-catalog-sync-on-startup-and-interval.md), [ADR-0016](0016-catalog-sync-interval-default-daily.md)),
`(공급사, 공급사 숙소 코드)` 로 기존 행을 찾아 저장된 내부 식별자를 그대로 쓴다([ADR-0011](0011-internal-id-random-uuid.md), [ADR-0036](0036-mapping-tables.md)).
공급사 스펙은 같은 상품이면 언제 조회해도 같은 코드가 온다고 정한다.

문제는 지난번에 있던 코드가 이번 목록에 없을 때다. 두 공급사의 목록 API 는 조건 없이 전체 목록만 주고 **상태 필드가 없다.**
그래서 계약 종료인지, 일시 중지인지, 응답이 일부만 온 것인지 구분할 방법이 없다.

확인한 사실 (숙박 유통에서 일시적인 판매 중지는 정상적인 상태 전이로 다뤄진다)

| 사실 | 원문 |
|---|---|
| 재고가 비면 숙소가 자동으로 닫히고, 재고를 채우면 자동으로 다시 열린다 | [Booking.com, Property statuses](https://developers.booking.com/connectivity/docs/property-statuses): "We automatically closed the property because it has no rooms available for any dates in the next 365 days." / "can also go open bookable automatically within the next 24 hours after availability was replenished" |
| 닫힌 숙소도 시스템에서 지우지 않는다 | [ETG, Retrieve hotel content](https://docs.emergingtravel.com/docs/b2b-api/static-content/retrieve-hotel-content/): "the property remains in the system" |
| 일시 비활성과 영구 삭제를 서로 다른 신호로 구분한다 | [ONDA 웹훅 명세](https://developers.onda.me/docs/api/channel/webhook-specifications): "disabled: 판매상태가 비활성 상태로 변경됨을 뜻합니다" / "deleted: 더 이상 판매될 수 없도록 영구적으로 삭제됨을 뜻합니다" |

확인하지 못한 것: 어느 문서도 "비활성됐던 숙소가 같은 코드로 돌아온다"를 문장으로 말하지 않는다. 빈도 수치도 없다.
검토 과정에서 Expedia·Agoda 문서도 인용됐으나 원문을 열어 확인하지는 못했다.

## Options

사라진 행을 어떻게 할지
- **(가) 매핑 행을 남기고 지금 목록에 없다는 것을 표시한다** ← AI 추천 — 목록이 한 번 잘못 와도 식별자가 유지되고, 나중에 삭제를 더할 수 있다. 대신 행이 쌓이고 컬럼이 하나 는다.
- **(나) 바로 지운다** — 테이블이 깨끗하다. 대신 목록이 한 번만 비어 와도 그 공급사의 식별자가 전부 새로 발급되고 되돌릴 수 없다.
- **(다) 일정 기간 없으면 지운다** — (가)에 삭제 경로가 붙은 형태다. 기준 기간을 정할 근거가 지금은 없다.

무엇으로 표시할지
- **(A) 참·거짓 값** — 조건이 단순하다. 대신 언제부터 없었는지 모른다.
- **(B) 사라진 시각(`missing_since`, 값이 없으면 지금 목록에 있음)** ← AI 추천 — 조건이 단순하고 얼마나 오래 없었는지가 남는다.
- **(C) 마지막으로 본 시각** — 정보는 비슷하다. 대신 거르려면 공급사별 마지막 성공 동기화 시각을 따로 알아야 한다.

## Decision

**(가)와 (B)** 를 택한다.

- 목록에 없는 매핑 행은 지우지 않는다. `missing_since` 에 사라진 시각을 적고, 값이 있으면 검색 대상에서 뺀다
- 다시 목록에 나타나면 `missing_since` 를 지우고 이름·최대 수용 인원을 갱신한다. 내부 식별자는 그대로다
- 숙소와 객실 타입 **둘 다** 이 컬럼을 둔다. 숙소가 사라진 경우는 숙소 쪽 조건으로 걸러지지만, 숙소는 있고 객실 타입만 빠지는 경우가 있다
- 표시는 **목록을 스펙대로 다 읽은 동기화에서만** 한다. 응답을 읽지 못한 동기화는 이전 상태를 건드리지 않는다([ADR-0019](0019-first-catalog-failure-no-special-handling.md), [ADR-0027](0027-spec-violation-handling-criteria.md))
- 한 공급사의 표시 작업은 한 트랜잭션에서 한다
- 사라진 행을 지우는 수단은 지금 두지 않는다
- 스펙과 달라 값을 정할 수 없어 제외한 항목([ADR-0027](0027-spec-violation-handling-criteria.md) 의 세 번째 질문)도 이번 목록에 없는 것으로 보아 `missing_since` 가 찍힌다. 공급사가 뺀 것인지 우리가 읽지 못한 것인지는 이 컬럼만으로 구분되지 않고, 구분이 필요하면 기록 형태를 정할 때 함께 본다(Q17)

**이유** — 우리 목록 API 에는 상태 필드가 없어 일시 중지와 영구 제거를 구분할 수 없다. 구분할 수 없는 신호로 되돌릴 수 없는 삭제를 하지 않는다.
고객이 보는 결과는 세 선택지가 같고(모두 즉시 검색에서 빠진다), 차이는 나중에 무엇을 알 수 있고 무엇을 되돌릴 수 있는가뿐이다.
이 설계는 같은 상황을 이미 같은 방식으로 다뤄 왔다. 매핑에 없는 객실 타입([ADR-0015](0015-exclude-unmapped-room-types.md)), 스펙과 다른 응답(ADR-0027), 예약 불가 상품([ADR-0026](0026-expose-unbookable-as-zero.md)) 모두 데이터를 부수지 않고 빼고 기록했다.

## Consequences

**얻는 것**
- 목록이 비거나 크게 줄어 와도 다음 동기화에 회복된다. 식별자가 공급사 응답 품질에 흔들리지 않는다
- 얼마나 오래 없었는지가 남아, 나중에 정리 기준을 관측값으로 정할 수 있다
- 사라졌다 돌아온 상품이 같은 내부 식별자로 돌아온다

**잃는 것**
- 행이 쌓이고 컬럼이 하나 는다. 모니터링(Q18)에 공급사별 사라진 행 수와 돌아오기까지 걸린 기간을 넣지 않으면 쌓이기만 한다
- 조회할 때 조건을 빠뜨리면 사라진 숙소가 검색에 섞인다. 매핑 조회를 한곳에 모으고 테스트로 확인한다
- **공급사나 숙박업자가 기록 삭제를 요구해도 자동으로 처리할 수단이 없다.** 고객 노출은 즉시 멈추지만, 남은 매핑을 지우려면 운영 작업이 필요하다. 관리자 기능은 요구사항이 범위 밖으로 둔 항목이다
- 공급사가 같은 코드를 다른 숙소에 재사용하면 남아 있던 식별자에 새 숙소가 붙는다. 세 선택지 모두 이를 감지하지 못한다. 재등장 시 이름이 저장값과 다르면 남기는 식으로 신호를 만들 수 있다(Q17)

**넘기는 것**
- 사라진 행의 정리 기준과 삭제 수단
- 목록이 통째로 비거나 급감해 온 경우를 따로 방어할지 (Q18 의 신호로 먼저 관측)

## Discussion

- **AI 주장과 근거** — 지우면 "같은 공급사 상품은 항상 같은 내부 식별자"라는 요구가 깨진다고 말했다
- **반박** — 그 문장은 동기화할 때마다 식별자가 섞이지 않게 하라는 뜻 아닌가. 사라졌다 돌아온 경우까지 포함한다고 볼 근거가 있나.
  그리고 사라졌다 같은 코드로 돌아오는 일이 흔한지에 따라 답이 갈릴 것 같다
- **검증 결과** — 과한 읽기였다. ADR-0011 도 매핑 데이터를 잃으면 식별자가 바뀐다는 점을 이미 받아들였다.
  남기자는 근거를 요구사항이 아니라 "상태 필드가 없어 구분할 수 없고 삭제는 되돌릴 수 없다"로 다시 세웠다.
  빈도는 문서에서 수치를 찾지 못했지만, 위 세 곳의 문서가 일시 중지와 영구 삭제를 구분해 다루고 자동으로 닫혔다 열리는 경우까지 있어 "드물어서 무시해도 된다"고 볼 근거는 없었다
- **또 다른 반박** — 그러면 공급사나 숙박업자가 즉시 삭제를 원해도 못 하는데 그게 맞는 기획인가
- **검증 결과** — 고객 노출은 목록에서 빠지는 즉시 멈추므로 "판매 중단" 요구는 충족된다. 남는 것은 사업 정보이고 요금·재고는 저장하지 않는다.
  다만 기록 삭제 요구를 자동으로 처리할 수단이 없다는 점은 잃는 것에 적었다

## Verification

목록에서 빠진 코드의 매핑 행이 남고 `missing_since` 가 채워지는지, 다시 나타나면 같은 내부 식별자로 비워지는지
  → `CatalogSyncIntegrationTest.목록에서 빠지면 사라진 시각이 찍히고 다시 나타나면 풀린다`

목록 응답을 읽지 못한 동기화가 기존 표시를 바꾸지 않는지
  → `CatalogSyncIntegrationTest.응답을 읽지 못한 동기화는 기존 표시를 건드리지 않는다`

숙소는 있고 객실 타입만 빠진 경우에도 그 객실 타입만 표시되는지
  → `CatalogSyncIntegrationTest.숙소는 남고 객실 타입만 빠지면 그 객실 타입에만 사라진 시각이 찍힌다`

숙소가 빠지면 그 숙소의 객실 타입도 표시되고, 돌아오면 같은 내부 식별자로 풀리는지
  → `CatalogSyncIntegrationTest.숙소가 빠지면 그 숙소의 객실 타입도 표시되고 다시 나타나면 같은 식별자로 풀린다`

표시가 남은 행이 검색 대상에서 빠지는지
  → `MappingReadIntegrationTest.missing_since 가 찍힌 숙소는 읽지 않는다`
  → `MappingReadIntegrationTest.missing_since 가 찍힌 객실 타입만 빠지고 숙소는 남는다`
