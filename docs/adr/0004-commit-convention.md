# 0004. 커밋 규약 채택

## Context

커밋 하나가 무엇을 담고 메시지를 어떻게 쓸지 정하지 않으면 이력이 제각각이 된다.
혼자 작업하므로 리뷰어가 규약을 강제해 주지 않는다. 첫 커밋 전에 정해야 한다.

## Options

- **(가) Conventional Commits, `type(scope): 제목`** ← AI 추천 — `git log --oneline` 에서
  어느 영역 작업인지 한눈에 보인다. 이 프로젝트는 도메인·공급사 연동·검색·문서로 영역이
  뚜렷해서 scope 가 실제로 도움이 된다. 대신 scope 를 매번 정해야 한다.
- **(나) `type: 제목`** — 단순하다. 대신 커밋이 늘어나면 제목만으로 영역 구분이 덜 된다.

## Decision

**(가)** 를 택한다. 제목은 한국어로 쓰고 동사로 끝낸다.
커밋 하나는 "그리고" 없이 한 문장으로 말할 수 있는 것 하나로 한다.

**규약 본문은 `CLAUDE.md` 의 커밋 절에 둔다.** ADR 은 무엇을 왜 정했는지를 담고,
작업하면서 계속 참조하는 규칙 본문은 작업 규칙 문서가 맡는다.

**이유** — 영역이 뚜렷해서 scope 가 이력을 읽는 데 실제로 도움이 된다.

## Consequences

**얻는 것**
- `git log --oneline` 만으로 작업 흐름이 읽힌다

**잃는 것**
- 영역이 애매한 커밋에서 scope 를 정하느라 멈추는 순간이 생긴다

## Discussion

- **AI 주장과 근거** — 처음 정한 결정들을 한 커밋으로 묶자고 했다.
  근거는 "여러 결정을 한 자리에서 정했으므로, 쪼개면 여러 번에 나눠 결정한 것처럼 보인다"
- **반박** — "다섯 번에 나눠 결정한 게 맞지 않아? 하나씩 정하고 있잖아"
- **검증 결과** — 반박이 맞다. 각 결정은 서로 다른 대화 차례에서 따로 내려졌다.
  "한 자리"라고 뭉뚱그린 것이 사실 오인이었다
- **그래서 어떻게 바뀌었나** — 커밋 하나에 결정 하나로 정했다

## Verification

`git log --oneline` 의 각 줄이 `type(scope): 제목` 형식이고 제목이 동사로 끝나는지.
