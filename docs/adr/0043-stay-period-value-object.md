# 0043. 숙박 구간을 체크인·체크아웃 두 날짜의 값 객체로 표현하기로 결정

## Context

날짜가 세 자리에서 쓰인다.

- **들어올 때** — 우리 검색 API 는 체크인일과 체크아웃일을 받는다
- **나갈 때** — 두 공급사의 재고·요금 조회도 체크인일과 체크아웃일을 받는다. 둘 다 **체크아웃일은 숙박에 넣지 않고**, 체크아웃이 체크인보다 뒤가 아니면 오류를 준다
- **가운데** — 정규화에는 **날짜 하나하나**가 필요하다. 연박 예약 가능 수는 날짜별 잔여 수의 최솟값이고([ADR-0023](0023-multi-night-availability-minimum.md)),
  응답에 빠진 숙박일이 있으면 그 날을 0 으로 본다([ADR-0024](0024-missing-night-as-zero-and-record.md)). 둘 다 "요청한 날짜들"과 응답을 대조해야 한다

즉 **바깥은 두 날짜, 안쪽은 날짜 목록**을 쓴다. 3박이면 목록은 체크인일부터 사흘이고 체크아웃일은 들어가지 않는다.

이 변환을 어디서 할지, 그리고 "체크아웃이 뒤여야 한다"를 누가 지킬지가 이 결정이다.

## Options

- **(가) 두 날짜를 담는 값 객체 하나를 두고, 날짜 목록은 그 객체가 만들어 준다** ← 채택 — 바깥과 같은 모양을 들고 다니면서 안쪽이 필요한 목록을 얻는다.
  대신 "며칠 묵는가"와 "어느 날짜들인가"가 한 타입에 섞이고, 연속하지 않는 숙박은 표현할 수 없다
- **(나) 날짜 목록만 담는다** — 정규화에서 쓰기가 가장 직접적이다. 대신 공급사를 부를 때마다 목록에서 첫날과 마지막날 다음을 되돌려야 하고,
  목록이 비었거나 중간이 비었을 때 무엇을 뜻하는지 애매하다
- **(다) 두 날짜를 그대로 들고 다니고 값 객체를 만들지 않는다** — 타입이 늘지 않는다.
  대신 "체크아웃이 뒤여야 한다"를 검사하는 곳이 여러 군데 생기거나 아무 데도 없다. [ADR-0041](0041-validate-in-constructors.md) 과 어긋난다

## Decision

- 숙박 구간은 **체크인일과 체크아웃일 두 날짜를 담는 값 객체** 하나로 표현한다
- **불변식은 그 생성자가 지킨다** (ADR-0041). 체크아웃일은 체크인일보다 뒤여야 한다. 같은 날도 안 된다
- **날짜 목록은 그 객체가 만들어 준다.** 체크아웃일은 넣지 않는다. 박수도 그 객체가 센다
- 공급사 호출과 우리 API 는 두 날짜를 그대로 쓴다. 목록은 정규화에서만 쓴다

**이유**

- 바깥이 두 날짜로 주고받으므로, 두 날짜를 들고 다니면 되돌리는 계산이 없다. 반대로 목록만 들면 공급사를 부를 때마다 두 날짜를 되돌려야 한다
- 체크아웃일을 넣지 않는다는 규칙이 한 곳에만 있게 된다. 날짜 목록을 쓰는 정규화 코드마다 그 규칙을 알 필요가 없다
- 잘못된 구간으로 공급사를 부르는 일이 생기지 않는다. 그런 요청은 객체를 만드는 자리에서 멈춘다

## Consequences

**얻는 것**
- 체크아웃일을 넣는지 마는지가 한 곳에서 정해진다. 날짜 목록을 쓰는 쪽은 그 규칙을 모른 채로 맞는 목록을 받는다
- 체크아웃이 앞인 요청이 공급사까지 가지 않는다
- 우리 API 와 공급사 호출이 같은 모양을 쓴다

**잃는 것**
- 연속하지 않는 숙박(중간 하루를 비우는 예약)은 표현할 수 없다. 지금 요구에 없고 공급사도 두 날짜만 받는다
- 날짜 목록을 부를 때마다 새로 만든다. 숙소 수천 개를 나눠 부르는 흐름에서 같은 목록을 반복 생성할 수 있어, 필요해지면 한 번만 만들어 두는 쪽으로 바꾼다
- 타입이 하나 늘어난다

**넘기는 것**
- 체크인일이 지난 날짜이거나 너무 먼 미래일 때 어떻게 볼지. 이 값 객체는 두 날짜의 앞뒤만 본다. 검색 입력을 어디서 어디까지 검사할지는 검색 구현 단위에서 정한다
- 숙박 일수의 상한을 둘지. 공급사 스펙에 상한이 없어 지금은 두지 않는다

## Discussion

- **AI 주장과 근거** — (가)를 권하면서 근거로 바깥과 안쪽의 필요가 다르다는 점을 들었다. 약점으로 연속하지 않는 숙박을 표현할 수 없다는 점과 목록의 반복 생성을 들었다
- **사용자 판단** — (가) 로 합의했다
- 반박은 없었다

## Verification

체크아웃일이 체크인일보다 앞이거나 같으면 값 객체를 만들 수 없는지
  → `StayPeriodTest.체크아웃일이 체크인일과 같으면 만들 수 없다`
  → `StayPeriodTest.체크아웃일이 체크인일보다 앞이면 만들 수 없다`

날짜 목록이 체크아웃일을 넣지 않는지
  → `StayPeriodTest.날짜 목록에 체크아웃일은 들어가지 않는다`
  → `StayPeriodTest.1박이면 날짜는 체크인일 하나다`

박수가 목록 크기와 같은지
  → `StayPeriodTest.박수는 날짜 목록의 크기와 같다`
