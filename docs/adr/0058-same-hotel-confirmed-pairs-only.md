# 0058. 동일 숙소는 사람이 확인한 짝만 응답에서 같은 값으로 묶기로 결정

## Context

요구사항의 선택 항목에 "중복 상품 병합"이 있다. 같은 숙소를 공급사들이 각자 코드로 팔 때 합칠지 따로 노출할지 **판단하고 구현**하는 일이다.
서킷 브레이커는 "구현 또는 설계", 예약 대행은 "설계 또는 간단한 구현"이라고 적혀 있는데, 이 항목만 "판단과 구현"이다.

[ADR-0010](0010-keep-internal-id-on-merge.md) 이 병합해도 내부 식별자는 바꾸지 않고 "묶음 정보를 어디에 어떤 형태로 둘지는 병합을 설계할 때 따로 정한다"고 넘겼다.

확인한 사실

| 사실 | 원문 |
|---|---|
| 공급사가 주는 숙소 정보는 코드·숙소명·객실 타입(코드·이름·최대 수용 인원)뿐이다. 주소·좌표·전화번호가 없다 | 공급사 규약. 지역 필터를 범위 밖으로 둔 이유를 "공급사가 지역 정보를 주지 않으므로"라고 적는다 |
| 같은 숙소·같은 객실인데 공급사마다 객실 이름 표기가 다르고, 총액과 조식 조건이 다르다 | 공급사 규약 부록 |
| 매핑 업계 최대 사업자는 매핑의 최소 요건으로 특정한 이름과 **물리 주소**를 요구하고, 그렇지 않은 숙소는 수동 검토에서 제외한다 | [GIATA, Understanding Our Mapping Process](https://info.giata.com/en/knowledge/our-mapping-process) 절 "3. Minimum Requirements for Mapping a Supplier Code": "There must be a specific physical address" / "we identify and exclude properties that do not meet our qualification criteria" |
| 필드 하나로는 같은 숙소를 판단하지 못하고, 정규화한 이름·좌표·주소·우편번호·성급·유형을 함께 본다 | [DIJI.TECH, The Same Hotel Three Times](https://www.diji.tech/en/blog/multi-supplier-hotel-inventory-mapping-and-deduplication): "The matching decision cannot be made by looking at a single field." |
| 표준 숙소 식별자도 병합 때 한쪽으로 흡수되어 바뀌고, 옛 식별자를 쓰지 말라고 알린다 | [GIATA MultiCodes 웹서비스 명세](https://multicodes.giatamedia.com/webservice/specs/) §2.1.3 "List of moved properties": "The old GIATA-ID should no longer be used by the client." (독립 검토가 열어 인용한 것이고 이 ADR 을 쓰며 다시 대조하지 않았다) |

**우리 재료로는 같은 숙소를 자동으로 판단할 수 없다.** 쓸 수 있는 것은 숙소명 하나인데 동명 숙소는 흔하고, 재고·요금 값은 같은 숙소라도 다르다.

## Options

병합 방식
- **(가) 사람이 확인한 짝만 응답에서 같은 값으로 묶는다** ← 채택 — 추정을 응답에 내지 않는다. 대신 확인 전까지 병합은 0건이다
- **(나) 추정한 묶음을 "후보"로 표시해 응답에 싣는다** — 자동으로 묶인다. 대신 동명 숙소에서 틀리고, 받는 쪽이 그 후보로 할 수 있는 일이 없다
- **(다) 설계만 문서로 남긴다** — 이 항목은 "판단과 구현"이라 요구와 어긋난다

응답의 값
- **(ㄱ) 모든 숙소에 처음부터 값을 발급하고 확인된 짝은 같은 값으로 맞춘다** ← 채택 — 필드의 뜻이 항상 하나다
- **(ㄴ) 짝이 없으면 null** — 짝이 있는데 상대가 이번 응답에 없어도 짝이 있다는 걸 안다. 대신 받는 쪽이 null 처리를 해야 하고 대부분의 값이 비어 있다
- **(ㄷ) 짝이 없으면 자기 내부 숙소 식별자** — 같은 필드가 경우에 따라 숙소 식별자이기도, 묶음 식별자이기도 하다. 받는 쪽이 그 값을 숙소 조회에 쓰면 짝이 확인되는 순간부터 깨진다
- **(ㄹ) 짝 중 한쪽 내부 식별자를 대표로** — 대표를 고르는 규칙이 필요하고, 대표가 목록에서 빠지면 바꿔야 한다

## Decision

- **동일 숙소는 사람이 확인한 짝만이다.** 확인되지 않은 것은 응답에서 묶지 않는다
- **짝은 숙소 단위다.** 객실 타입끼리 짝을 짓지 않는다
- **모든 숙소 행이 동일 숙소 식별자(`same_hotel_id`, 무작위 UUID)를 처음부터 갖는다.** 짝을 확인하면 한쪽 값을 다른 쪽에 맞춘다
  - 테이블을 따로 두지 않고 `hotel_mapping` 의 칼럼으로 둔다. 검색이 이미 읽는 행이라 조인이 늘지 않는다
  - 짝 확인은 `update hotel_mapping set same_hotel_id = :남는값 where same_hotel_id = :흡수되는값` 한 문장이다. 공급사가 셋 이상이어도, 동일 숙소 둘이 합쳐져도 같다
  - 남는 값은 구성원이 많은 쪽, 같으면 값이 작은 쪽이다. 받는 쪽의 안정성이 아니라 결정적이고 테스트할 수 있는지만 보고 고른다
- **해제는 숙소 하나를 동일 숙소에서 빼는 것이다.** 그 숙소에 새 값을 준다
- **같은 공급사 숙소 둘이 동일 숙소에 들어가는 것을 막지 않는다.** [ADR-0011](0011-internal-id-random-uuid.md) 이 같은 공급사 상품을 둘로 둘 수 있는 것을 장점으로 적었다
- **응답의 모든 항목에 `sameHotelId` 를 싣는다.** 항목을 합치지 않고 평면 목록을 그대로 둔다
- **계약에 적는다: `sameHotelId` 는 이번 응답 안에서 같은 숙소끼리 모으는 데 쓰는 값이다. 짝이 바뀌면 값이 바뀔 수 있으니 저장해 두고 다시 찾는 키로 쓰지 않는다.** 숙소를 가리키는 값은 `hotelId` 다
- **동일 숙소 후보는 목록 동기화 때 계산해 테이블에만 둔다.** 응답에는 내지 않는다. 정규화한 숙소명(대소문자·공백·문장부호 제거)이 같은 다른 공급사 숙소 쌍이다
- **개발용 시드로 Mock 의 같은 숙소 쌍을 확인된 짝으로 넣는다.** 로컬 프로파일에서만 도는 Flyway 폴더에 두어 운영 DB 에는 들어가지 않는다.
  내부 식별자는 동기화 때 생기므로, 시드는 공급사 코드로 짝을 적고 동기화가 그것을 동일 숙소 식별자에 반영한다

**이유**

- 이름 하나로는 같은 숙소를 판단할 수 없다. 업계는 주소가 없으면 매핑하지 않고 사람이 확인한다. 우리는 주소도 없다
- 확인된 짝만 묶으면 **추정한 값을 사실처럼 내보내지 않는다**는 원칙을 지키면서 병합을 실제로 동작하게 할 수 있다
- 항목을 합치지 않고 같은 값만 붙이면 조식·총액이 공급사마다 그대로 남아 "조건이 다른 상품을 한쪽으로 고르는" 일을 우리가 하지 않는다 (규약 부록이 물은 "합친다면 조건 차이를 어떻게 다룰지")
- 업계도 병합 때 식별자가 바뀌는 것을 막지 않고 알린다. 우리는 알릴 수단이 없으므로 계약에 그 성질을 적는다

## Consequences

**얻는 것**
- 동명 숙소를 잘못 합치는 일이 응답에 나가지 않는다
- 받는 쪽은 `sameHotelId` 하나로 모으면 되고, 숙소를 가리킬 때는 `hotelId` 를 쓰면 된다
- 공급사가 셋 이상으로 늘어도 칼럼 하나와 update 한 문장으로 표현된다
- 개발 환경에서 실행하면 병합이 보인다

**잃는 것**
- **운영에서는 사람이 확인하기 전까지 병합이 0건이다.** 확인하는 수단은 SQL 뿐이다. 관리자 기능이 범위 밖이다
- **후보 규칙이 얼마나 맞는지 측정할 수 없다.** 정답 데이터가 규약 예시 한 쌍뿐이라, 놓치는 쌍도 잘못 잡는 쌍도 셀 수 없다
- **짝이 바뀌면 `sameHotelId` 가 바뀐다.** 계약에 적는 것으로 대응한다
- 짝이 있는데 상대 공급사가 이번에 실패하면 값만으로는 "짝 없음"과 구분되지 않는다. `suppliers[].status` 를 함께 봐야 한다
- 셋 이상 묶인 동일 숙소에서 "이 둘 사이의 짝만 틀렸다"는 표현하지 못한다. 해제는 숙소 하나를 빼는 것뿐이다

**다시 볼 것**
- 공급사가 주소나 좌표를 주게 되면 후보 규칙을 다시 본다
- 확인 수단(관리자 기능)이 범위에 들어오면 SQL 대신 그것으로 한다

## Discussion

- **AI 주장과 근거 (1차)** — 처음에는 추정한 묶음을 응답에 표시만 하자고 권했다(묶음 키와 추정 근거를 붙임)
- **반박** — 사용자가 "정말 동명의 숙소는 많을 텐데, 주소를 받거나 그런 상황은 아니지? 확정 짓기는 위험할 것 같다. 더 확실히 비교할 방법이 있을까?" 라고 물었다
- **검증 결과** — 규약에 주소가 없다는 것을 확인했고, 확인된 짝만 묶는 안으로 바꿨다. 독립 검토(Fable)에 물어 요구 문구("판단과 구현")와 업계 관행(GIATA 의 주소 요건, 수동 확인)으로 뒷받침했다.
  검토는 이 안의 진짜 약점이 SQL 이 아니라 "실행해 보는 사람이 병합을 볼 곳이 없다"는 것이라 짚었고, 후보 테이블과 개발용 시드로 메웠다
- **응답 값** — AI 는 "짝이 없으면 자기 hotelId 를 싣는다"를 권했다. 사용자가 고민해 보자며 검토를 요청했고, 검토는 같은 필드가 숙소 식별자와 묶음 식별자를 오가 받는 쪽이 깨질 수 있다고 짚었다. 처음부터 모두 발급하는 안으로 바꿨다
- **용어** — AI 는 "동일"이 확정된 사실처럼 읽힌다며 "숙소 그룹"을 권했다. 사용자가 "동일 숙소가 맞지 않나?" 라고 물었다.
  우리 설계에서는 사람이 확인한 짝만 같은 값을 가지므로 "동일"은 사실이다. AI 의 걱정은 추정 묶음을 전제로 한 것이었다. "동일 숙소", 확인 전은 "동일 숙소 후보"로 정했다

## Verification

구현할 때 확인하고 테스트 이름을 여기에 적는다.

- 확인된 짝의 숙소들이 응답에서 같은 `sameHotelId` 를 갖고, 짝이 없는 숙소는 서로 다른 값을 갖는지
- 짝을 확인해도 `hotelId`(내부 숙소 식별자)가 그대로인지 (ADR-0010 이 비워 둔 확인)
- 해제하면 다시 다른 값이 되는지
- 동기화가 정규화한 숙소명이 같은 다른 공급사 숙소를 후보로 남기고, 후보는 응답에 나가지 않는지
