# 0048. 검색 인원의 불변식은 각각 0 이상, 합이 1 이상까지만 두기로 결정

## Context

검색 API 는 인원을 성인과 아동으로 나눠 받는다. 이 값을 담는 객체를 만들면서 생성자가 무엇을 거부할지 정해야 한다 ([ADR-0041](0041-validate-in-constructors.md)).
[ADR-0043](0043-stay-period-value-object.md) 이 "검색 입력을 어디서 어디까지 검사할지"를 이 단위로 넘겨 두었다.

확인한 사실

| 사실 | 어디서 |
|---|---|
| 공급사 스펙은 `adults`·`children` 을 `int` 라고만 적었다. **범위·최소값·필수 여부는 적지 않았다.** 성인 0 일 때 공급사가 어떻게 응답하는지 우리는 모른다 | 공급사 스펙의 필드 사전과 오류 표 |
| 공급사는 `adults + children <= maxOccupancy` 인 객실 타입만 돌려준다. 인원 필터링은 공급사가 한다 | 공급사 스펙의 상품 구조 절 |
| 한국에서 청소년 단독 숙박은 법으로 금지가 아니다. 보호자 동의서가 있으면 가능하고, 거절은 업소 재량이다 | [검색 인원 조사](../research/guest-occupancy.md) §1 |
| 글로벌 연동 규격은 객실마다 성인 최소 1명을 요구한다 (Booking.com Demand API, 명문). 아동은 **나이**로 받는다 | 같은 조사 §2 |
| 아동의 나이 경계는 숙소가 정한다. 우리 공급사 스펙은 아동 수만 받고 나이는 받지 않는다 | 같은 조사 §2, 공급사 스펙 |

## Options

- **(가) 성인 최소 1명, 아동 0 이상** — 글로벌 연동 규격의 관행과 같고, API 계약에 적을 문장이 생긴다.
  대신 한국에서 합법인 요청을 막는다. 근거가 남의 규격 관행 하나뿐이다
- **(나) 각각 0 이상, 합이 1 이상** ← 채택 — 스펙도 한국 법도 막지 않는 것을 우리도 막지 않는다.
  인원 필터링은 공급사가 `maxOccupancy` 로 한다. 대신 성인 0 요청의 결과를 모른 채 공급사로 내보낸다
- **(다) 상한도 둔다** — 근거가 없다. 몇 명까지 묵을 수 있는지는 객실마다 다르고 그 판단은 공급사의 `maxOccupancy` 가 한다

## Decision

- 인원 값 객체의 불변식은 **성인 0 이상, 아동 0 이상, 합이 1 이상**이다
- 성인 최소 인원을 두지 않는다. 상한도 두지 않는다
- 아동의 나이는 받지 않는다. 공급사 스펙이 수만 받기 때문이다

**이유**

- **모르는 것에 규칙을 만들지 않는다.** 스펙은 인원의 범위를 말하지 않고, 한국 법은 아동만의 숙박을 막지 않는다.
  우리가 먼저 막으면 그 근거는 남의 규격 관행 하나다
- 음수 인원과 0명 검색은 성립하지 않는 값이라 막는다. 이것은 판단이 아니라 값의 정의다
- 인원이 그 객실에 맞는지는 공급사가 이미 걸러서 준다. 우리가 다시 판단할 일이 아니다

## Consequences

**얻는 것**
- 합법인 요청을 우리가 막지 않는다
- 불변식의 근거가 값의 정의뿐이라 설명이 짧다

**잃는 것**
- **성인 0 요청이 공급사로 나갔을 때 어떻게 되는지 모른다.** Mock 은 스펙에 오류로 적힌 것만 모사하므로([ADR-0045](0045-search-concurrency-and-budget.md)) 통과시키고,
  실제 공급사가 거절하면 그때 드러난다. 거절하면 그 공급사의 실패로 집계되어 응답에 나간다 ([ADR-0046](0046-supplier-status-in-search-response.md))
- 글로벌 연동 규격의 관행과 다르다. 그런 공급사를 붙이게 되면 성인 0 요청을 그 공급사에는 보내지 않는 처리가 그 어댑터에 필요하다

**넘기는 것**
- **아동의 나이.** 글로벌 규격은 아동 나이를 받고 요금이 나이 구간마다 다르다. 우리 공급사가 수만 받아 지금은 받지 않지만, 그런 공급사를 붙이면 API 계약이 바뀐다
- 체크인일이 지난 날짜인지를 어느 시간대 기준으로 볼지 (Q28). 한국 밖 숙소가 섞이면 서버 시각과 현지 날짜가 다를 수 있다

## Discussion

- **AI 주장과 근거 (1차)** — (가)를 권했다. 근거로 "성인 없이 아동만 묵는 예약은 성립하지 않는다"를 들었다
- **반박 (1차)** — 사용자가 "아동만 예약이 원래 불가능한가? 근거를 조사해봐" 라고 했다. 한국 밖 숙소도 나중에 나올 수 있으니 그것을 전제로 보라고 했다
- **검증 결과 (1차)** — AI 의 전제가 틀렸다. 한국에서 단독 숙박은 법 금지가 아니고 보호자 동의로 가능하다.
  글로벌 연동 규격이 성인 1명을 요구하는 것은 사실이나, 그것은 "성립하지 않는다"가 아니라 규격의 관행이다.
  조사는 [검색 인원 조사](../research/guest-occupancy.md) 에 남겼다
- **AI 주장과 근거 (2차)** — 근거를 바꿔 (가)를 다시 권하면서, (나)의 약점으로 "공급사 스펙에 성인 0 요청의 동작이 없어 거절되면 그 공급사가 실패로 집계된다"를 들었다
- **반박 (2차)** — 사용자가 "그 말이 사실이야?" 라고 물었고, 원문을 확인하니 스펙은 `int` 라고만 적고 범위를 말하지 않았다.
  AI 가 "동작이 없다"고 정정하자 사용자가 다시 짚었다. "없다는 사실이 아니지 그러면. 그냥 모르는 거지"
- **검증 결과 (2차)** — 맞다. "스펙이 말하지 않는다"는 어느 선택지의 근거도 될 수 없다. 그것을 빼면 (나)의 약점이 없어지고 (가)의 근거는 관행 하나만 남는다.
  AI 는 두 번 다 **모르는 것을 아는 것처럼** 말했다. 처음은 근거 없는 전제, 두 번째는 모르는 것을 약점으로 늘린 것이다
- **그래서 어떻게 바뀌었나** — 추천을 (나)로 바꿨고 사용자가 (나)로 정했다

## Verification

성인·아동 어느 쪽이든 음수면 만들 수 없는지
  → `GuestCountTest.성인이 음수면 만들 수 없다`
  → `GuestCountTest.아동이 음수면 만들 수 없다`

둘 다 0 이면 만들 수 없는지
  → `GuestCountTest.둘 다 0 이면 만들 수 없다`

성인 0 에 아동 1 이상이면 만들어지는지
  → `GuestCountTest.성인 0 에 아동 1 이상이면 만들어진다`
