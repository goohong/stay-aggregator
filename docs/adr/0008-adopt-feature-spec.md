# 0008. Feature Spec 을 두 층 구조의 위층으로 도입

## Context

ADR-0002 는 결정 하나를 파일 하나로 남기기로 정했다. 그런데 이 프로젝트는
하나의 기능(공급사 통합 검색)에 결정이 여러 개 몰린다. 표준 모델 하나만 봐도
금액을 무엇으로 표준화할지, 날짜를 어떻게 다룰지, 재고를 어떻게 계산할지가
전부 따로 결정될 수 있다.

ADR 만 있으면 "이 기능에 지금 뭐가 안 정해졌는지"를 모아 볼 자리가 없다.
아직 결정되지 않은 것(오픈 질문)을 어디에 적을지도 정해진 바 없었다.

## Options

- **(가) ADR 만, `status: proposed` 로 오픈 질문을 대신한다** — 새 문서 종류가
  안 늘어난다. 대신 한 기능에 걸린 오픈 질문 여러 개가 파일 여러 개로 흩어져,
  기능 하나의 전체 그림을 한눈에 보기 어렵다.
- **(나) Feature Spec 을 위층으로 둔다** ← AI 추천 — Feature Spec 은 "무엇을
  만드는가"(What)를, ADR 은 "왜 그렇게 했는가"(Why)를 담당하는 다른 관점이다.
  위계 관계가 아니라 Feature Spec 이 관련 ADR 들을 한곳에서 가리키는 인덱스에
  가깝다. 기능 하나에 오픈 질문과 결정 로그를 모아 볼 자리가 생긴다. 대신
  문서 종류가 하나 늘고, 요구사항에 없는 범위·요구사항 절까지
  쓰면 api.md·ADR 과 중복된다.

## Decision

**(나)** 를 택한다. 단, Feature Spec 은 최소 형태로 쓴다.

```
docs/features/stay-integration.md   ← 하나로 시작. 커지면 그때 쪼갠다
  ## 무엇을 하는가 (3~5줄)
  ## 오픈 질문        지금 안 정해진 것
  ## 결정 로그         풀린 것. ADR 링크만, 내용은 베끼지 않는다
```

범위·요구사항·API 스펙 절은 두지 않는다. 그 내용은 각각 `docs/architecture.md`,
`docs/domain-model.md`, `docs/api.md`, 그리고 ADR 이 맡는다.

**이유** — 표준 모델 설계에 결정이 여러 개 몰릴 것으로 보이고, 지금 하고
있는 방식(선택지 제시 → 논의 → 확정)의 "논의 중" 상태를 담을 자리가 필요하다.

## Consequences

**얻는 것**
- 기능 하나에 걸린 오픈 질문과 결정을 한 문서에서 모아 볼 수 있다
- ADR 은 그대로 결정 하나당 파일 하나를 유지한다

**잃는 것**
- 문서가 하나 늘어난다
- Feature Spec 과 ADR 사이에 같은 내용을 베껴 쓰지 않도록 매번 주의해야 한다.
  Feature Spec 의 결정 로그는 항상 링크만 두고 선택지·이유는 ADR 에만 쓴다

## Verification

`docs/features/` 에 있는 문서가 범위·요구사항·API 스펙 절을 담고 있지 않은지.
결정 로그의 각 항목이 ADR 링크로만 되어 있고 선택지나 이유를 다시 쓰지
않았는지.
