# 숙박 상품 통합 연동

## 무엇을 하는가

여러 숙박 공급사의 서로 다른 API 를 하나의 표준 모델로 통합한다. 공급사의
숙소 목록을 받아 내부 식별자로 매핑해 두고, 고객이 날짜와 인원으로 검색하면
공급사에 병렬로 재고·요금을 물어 정규화한 뒤 하나의 결과로 합쳐 돌려준다.
공급사 하나가 실패해도 나머지 결과로 응답한다.

## 오픈 질문

| # | 질문 | 상태 |
|---|---|---|
| Q1 | 요금을 표준 모델에서 어떻게 표현할지 (기준값, 통화, 최소 단위, 조건) | 논의 중 — 세금 포함 총액 기준, `Money`, `RateConditions` 방향. 미확정 |
| Q2 | 날짜·숙박 구간을 어떻게 표현할지 | 미착수 |
| Q3 | 여러 박을 검색할 때, 날짜마다 다른 잔여 객실 수로 기간 전체에 몇 실을 팔 수 있다고 볼지 | 미착수 |
| Q4 | 판매 조건(조식 포함 여부 등)을 어느 계층에 둘지 | 미착수 |
| Q5 | 새 공급사를 붙여도 표준 모델이 안 바뀌는 구조 (어댑터) | 방향만 정함 |
| Q6 | 공급사 응답 DTO 가 스펙의 필드를 어디까지 받을지 | 방향 제시됨 — 모든 필드를 받는다. ADR 전. ADR-0014 의 어긋남 감지가 이름·최대 수용 인원 필드에 의존 |
| Q7 | 예약 불가(예약 가능 객실 수 0) 상품을 응답에서 뺄지, 0으로 노출할지 | 미착수 |
| Q11 | 공급사 숙소 목록을 받아오지 못해 매핑이 준비되지 않았을 때 검색을 어떻게 처리할지 | 미착수. ADR-0017 로 매핑이 재시작 후에도 남으므로, 맨 처음이거나 새 공급사의 첫 목록을 못 받은 경우로 좁혀짐 |
| Q12 | 서버를 WebFlux 로 갈지, 서블릿 기반 Spring MVC 서버에 WebClient 호출만 둘지 | 미착수 (MVC 로 진행 중이나 근거 문서 없음) |
| Q17 | 무엇을 어긋남으로 볼지(이름 표기 차이 등), 어떤 종류로 나눠 얼마나 어떤 형태로 남길지 | 미착수. Q18 모니터링 설계에서 함께 정함. 매핑에 없는 객실 타입의 누락도 함께 분류 (ADR-0014·0015) |
| Q18 | 연동 지표·모니터링을 어떻게 설계할지 (공급사별 성공률·응답 지연·타임아웃 비율, 어긋남·누락 포함) | 미착수 |
| Q19 | 운영자가 설정하는 숙소 목록 갱신 주기에 허용 범위(최소 간격)를 둘지 | 미착수 (ADR-0016 에서 생김) |
| Q21 | 매핑을 저장할 서버형 관계형 DB 로 PostgreSQL 과 MySQL 중 무엇을 쓸지 | 미착수 (ADR-0017 에서 생김) |

## 결정 로그

| 결정 | ADR |
|---|---|
| 구현 언어 | ADR-0002 |
| Mock 공급사 모듈 분리 | ADR-0005 |
| 빌드 도구·프레임워크 버전 | ADR-0007 |
| 공급사 호출 흐름을 Reactor 로 직접 다룸 | ADR-0009 |
| 같은 숙소를 병합해도 내부 식별자 유지 | ADR-0010 |
| 내부 식별자를 무작위 UUID 로 발급해 저장 | ADR-0011 |
| 응답의 숙소·객실 타입 정적 정보는 숙소 목록 기준으로 저장해 사용 | ADR-0012 |
| 숙소 목록은 앱 기동 시와 일정 주기마다 받아옴 | ADR-0013 |
| 목록 어긋남은 검색에서 감지하고 교정은 동기화 주기에 맡김 | ADR-0014 |
| 매핑에 없는 객실 타입은 응답에서 빼고 뺀 사실을 남김 | ADR-0015 |
| 숙소 목록 갱신 주기는 기본 하루 한 번, 설정으로 변경 가능 | ADR-0016 |
| 매핑은 서버형 관계형 DB 에 저장 (Q20) | ADR-0017 |
