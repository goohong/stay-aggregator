# AI 활용 기록

AI 에게 무엇을 물었고, 그 답을 어떻게 수용·수정·거부했는지 남긴다.
결정으로 이어진 것은 해당 ADR 을 가리키고 여기서는 요지만 적는다.
ADR 로 남기기엔 작은 판단, 또는 ADR 의 근거를 검증하는 과정에서 나온 것만 자세히 적는다.

## 언어·버전 선택

| 물은 것 | AI 의 답 | 처리 | 근거 |
|---|---|---|---|
| 구현 언어 | Java 권함(AI 가 만든 Kotlin 관용구를 인터뷰에서 방어하기 어렵다는 이유) | **거부** | 설명 가능성을 구현의 기준으로 두면 지금 이해도가 코드 품질의 상한이 된다. 모자란 건 공부하면 된다. ADR-0002 |
| Kotlin 버전 근거 | "최신이고 Boot BOM 과 안 어긋난다" | **거부, 재검증 요구** | Gradle 버전에서 이미 기각당한 "최신이라서" 논리와 같다고 지적. 재검증 결과 진짜 근거(Gradle 9.7.1 을 지원 범위에 담는 유일한 KGP 라인)를 찾음. ADR-0007 |
| Gradle 을 9.7.1 로 올릴지 | 처음엔 "9.4.1 이미 검증했으니 유지" 주장 | **거부** | "9.4.1 이 9.7.1 보다 나은 점"을 대라는 반문에 답을 못함. 관성이지 근거가 아니었음. 실측 후 9.7.1 로 변경. ADR-0007 |
| Boot 3→4 로 올릴 때 무엇이 바뀌는지 | "webflux 스타터 + `web-application-type: servlet` 설정이 필요하다" | **오류 발견, 정정** | 확인해보니 Boot 3 도 webmvc+webflux 가 같이 있으면 자동으로 SERVLET 판정. 그 설정은 필요 없었음. 진짜 단점은 안 쓰는 리액티브 서버 의존성이 딸려오는 것. ADR-0007 |
| `jvmToolchain(21)` 이 없는 JDK 를 자동으로 받아오는지 | 처음엔 "없으면 빌드 실패"라고 단정, 이후 스스로 "Gradle 이 자동으로 받아온다"고 뒤집음 | **둘 다 오류, 재검증** | 직접 재확인한 결과 그 JDK 는 이번에 받아진 게 아니라 몇 달 전 다른 프로젝트 작업으로 이미 캐시에 있던 것이었다. 공식 문서 확인 결과 `foojay-resolver-convention` 플러그인 없이는 자동 다운로드 안 됨. ADR-0007 |

## 저장소·패키지 이름

| 물은 것 | AI 의 답 | 처리 | 근거 |
|---|---|---|---|
| 패키지 접두사(`dev.goohong` vs `com.stayaggregator`) | 처음엔 GitHub 핸들이 `9rrong`(숫자 시작이라 패키지 불가)이라고 전제하고 `dev.goohong` 권함 | **오류 발견, 재판단** | 실제 핸들은 `goohong`(gh api 로 확인). 전제가 틀렸다는 걸 알리고 다시 판단받음. 최종적으로 기존 프로젝트들(`com.ppiyaki`, `com.uoslife`)과 같은 방식인 `com.stayaggregator` 로 결정 |
| 이름 선택의 편향 우려 | 자신의 코드로 이미 구현된 것을 선택지에 올리면 편향될 수 있음 | **구조로 해결** | 코디네이터 코드와 결정 이력을 모르는 별도 세션에 같은 질문을 다시 물어 대조. 실제로 패키지 추천이 한 번 바뀜(자신 없다고 밝힌 그대로 편향이 있었음이 드러남) |

## 작업 방식

| 물은 것 | AI 의 답 | 처리 | 근거 |
|---|---|---|---|
| Mock 을 어디에 둘지 | "`src/test` 에 두면 모듈을 안 늘리고 스캔도 회피할 수 있다" | **거부, 함정 발견** | 재검토에서 함정이 드러남: `src/test` 클래스패스로 띄우면 앱의 main 리소스·의존성을 그대로 물려받아, H2 파일 모드에서 앱과 Mock 이 같은 DB 파일을 열려다 락 충돌로 죽는다. 별도 Gradle 모듈로 변경. ADR-0005 |
| 무응답 Mock 재현 방법 | `Thread.sleep` 이 안전한지 | **수용** | 묶이는 게 Mock 의 스레드이지 우리가 재는 앱 스레드가 아니므로 문제없다는 설명을 검증 후 받아들임 |
| 코드를 짚혔을 때 설명 못 하면 어떻게 할지 | "더 단순한 코드로 다시 쓴다"를 규칙으로 제안 | **거부** | 그러면 지금 이해도가 구현 가능한 코드의 상한이 된다. 이해 못 하는 건 나중에 공부하면 된다. 구현 기준과 이해도 확인은 별개 문제 |

## 리서치 활용

| 물은 것 | 결과 | 처리 |
|---|---|---|
| 사람 1명 + AI 협업에 맞는 개발 방법론 조사 | Spec Kit·Kiro 등 spec-driven development 도구, Walking Skeleton, ADR/RFC, teach-back 계열 실천 등을 조사 | **부분 수용** — ADR 형식과 "구현 직후 대안을 따져보기"는 채택. spec-kit 류 도구는 **거부**(목적이 사람을 검토 루프에서 빼는 것이라 이 프로젝트의 방향과 반대라는 조사 결과에 따름) |
| Mock 서버 구성 방식(독립 서버 vs 테스트 모킹) | 독립 서버는 채점 대상은 아니나 견고성을 보여주는 데 필요하다는 조사 결과 | **수용** | 별도 모듈로 확정. 다만 처음 겪는 함정(클래스패스 공유)은 재검토에서 나중에 드러남 |
